Learn

The backend is the bouncer.

Definition

In an API-based GenAI application, the model runs as a managed cloud service. The application's backend builds the request (instructions, context and user input), calls the model endpoint over HTTPS, and processes the response before returning it to the client.

In plain words

The user talks to your app; your backend talks to the model. The browser or mobile app never calls the model directly, because to do that it would need your key, and anything in a browser is public.

SecretsKeys or managed identity stay server-side. Users never see them.
Prompt assemblySystem instructions, history and retrieved data are added by your code, not typed by the user.
GuardrailsInput checks, output validation, per-user limits, content safety (Module 10).
ObservabilityLatency, tokens, cost, request IDs and errors logged on every call.
In the real world

Every serious AI product puts a service layer between users and the model. Larger organisations go further with an AI gateway in front of all model traffic (Azure API Management offers AI gateway features), giving one place for keys, quotas per team, caching, logging and failover between models. Your little FastAPI proxy in this drill is the same idea in 30 lines.

Common trap

A hackathon React app with the key in a variable like VITE_OPENAI_KEY or REACT_APP_OPENAI_KEY. Front-end build tools inline those values into the JavaScript bundle. The "hidden" key is in plain text for anyone who opens developer tools.

Interview cue

"We call the model from a backend service, never from the client, so credentials stay server-side and we get one place for prompt assembly, guardrails, logging and rate limiting."

Drill 02.1

Hide the key behind a backend proxy

~20 minAzure OpenAIFastAPI · AI assistant

Goal: a web page that asks the model questions through your own backend, with proof that the key never reaches the browser.

  1. Ask AI

    Have your assistant build the backend and the page

    In this folder, create a minimal FastAPI app in lab02_01_proxy.py and a page lab02_01_index.html.
- Reuse get_client() and MODEL from #llm.py. Never read or expose the API key in any other way.
- GET / serves lab02_01_index.html.
- POST /api/ask accepts JSON {"question": str} (1 to 2000 characters, validated with Pydantic),
  calls the chat model with a short system prompt ("You help TrainCrest learners. Be brief."),
  and returns {"answer": str}.
- The HTML page has a textarea, an Ask button and an answer area, and uses fetch() to call
  /api/ask. Plain HTML and JavaScript, no frameworks, no keys.
Tell me the uvicorn command to run it.
    Why this prompt works: it fixes the file names, reuses your existing helper instead of letting the assistant invent its own key handling, states the API contract exactly (path, JSON shape, validation), and repeats the security requirement twice.
    Reference solution (if your assistant gets stuck)

    $ uvicorn lab02_01_proxy:app --reload
    
        
    Open http://127.0.0.1:8000 and ask "What is an exam voucher?". Also open http://127.0.0.1:8000/docs: FastAPI generated interactive API documentation for you.

    Try to steal the key from the browser

Check
Quick ones.



  
1. A teammate says "the key is in an environment variable in our React app, so it's safe". Is it?
No. Front-end build tools bake environment variables into the public JavaScript bundle. Move the call to a backend and regenerate the key.

  
2. Name two things besides hiding the key that the backend gives you.
Any two of: prompt assembly, input validation and guardrails, per-user rate limits, logging and cost tracking, output checks.




Takeaway
Users talk to your backend; your backend talks to the model. Everything that matters (keys, prompts, guardrails, logs) lives in between.
