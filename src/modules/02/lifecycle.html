One POST, several gates.

Here's the Chat Completions format, which Azure OpenAI, OpenAI, Ollama and many other providers all accept.

The request 
POST https://<resource>.openai.azure.com/openai/v1/chat/completions
api-key: ••••••••
Content-Type: application/json

{
  "model": "chat",                              # deployment name on Azure
  "messages": [
    { "role": "system", "content": "You are RR Finance Assist, RR Finance Bank's customer-support assistant." },
    { "role": "user",   "content": "What does 'pending' mean on a card payment?" }
  ],
  "max_completion_tokens": 400                  # optional parameters
}
The response (trimmed) 
{
  "id": "chatcmpl-…",
  "model": "gpt-5.4-mini-2026-03-17",           # the model version that answered
  "choices": [{
    "index": 0,
    "message": { "role": "assistant", "content": "It means the payment is authorised but not yet settled…" },
    "finish_reason": "stop"                     # why generation ended
  }],
  "usage": {
    "prompt_tokens": 38,                        # you pay for these…
    "completion_tokens": 54,                    # …and these, priced higher
    "total_tokens": 92,
    "completion_tokens_details": { "reasoning_tokens": 0 }
  }
}

Read finish_reason every time

ValueMeaningWhat your code should do
stopFinished naturally or hit a stop sequenceUse the answer
lengthHit the output token cap mid-answerDon't show a half answer as complete; raise the cap or ask for brevity
content_filterOutput blocked by safety filteringShow a safe fallback message; log it
tool_callsThe model wants your code to run a functionModule 04
Chat Completions vs the Responses API

OpenAI and Azure also offer a newer Responses API (client.responses.create) with server-side conversation state and built-in tools. This handbook uses Chat Completions because it's the common format across Azure, OpenAI, Ollama and many others. Messages, parameters, streaming and usage carry over directly.

In the real world
In finance

When a customer complains "your chatbot told me there was no fee", the bank must be able to reconstruct that conversation exactly: which model version answered, with which prompt version, what it was given and what it said. That's why regulated firms log the request ID, model version, prompt version and finish_reason for every call and keep them under the same retention rules as call recordings. It also explains why a 200 response with finish_reason="length" matters: a reply cut off mid-sentence ("the fee is $") is a misleading statement, not just an ugly one.

Production teams log at least the request ID, model version, finish_reason, token usage and latency for every call. When a customer says "the bot gave me a weird answer yesterday", those five fields are how you find out what happened: which model version, whether it was truncated, how long it took.

Interview cue

"A chat request is model + messages + parameters; the response gives choices, finish_reason and usage. I always check finish_reason, because a 200 can still be a truncated or filtered answer."

Build a response inspector

~15 minAI assistant · no API cost

Goal: a script that prints the fields that matter from a saved response, including error bodies, using response.json from Drill 02.2.

  1. Ask AI 
    Look at #response.json (a saved Azure OpenAI chat completion). Write inspect_response.py that
takes an optional path argument (default response.json) and prints, one per line: model,
finish_reason, the first 200 characters of the answer, prompt and completion tokens, reasoning
tokens (0 if absent), and whether any content filter category was flagged. If the file is an
error body ({"error": {...}}), print the error code and message and exit with code 1.
Standard library only.
    Why this prompt works: it points the assistant at a real example of the data (so it doesn't guess the shape), lists exact outputs, and covers the error case and missing fields explicitly.

Check
Read the response.



  
1. A response is HTTP 200 but the answer stops mid-sentence. What do you check?
finish_reason: it's length. The output cap was hit (reasoning tokens count too).

  
2. Which five fields would you log for every call?
Request ID, model version, finish_reason, token usage and latency (plus your own prompt version, from Module 03).




Takeaway
A 200 is not the same as success. Read finish_reason and usage on every response.
