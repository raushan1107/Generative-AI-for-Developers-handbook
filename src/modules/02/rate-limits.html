Learn

Wait longer each time, never in lockstep.

Definition

Rate limits cap how much a client can use an endpoint in a time window, typically as tokens per minute (TPM) and requests per minute (RPM). Exceeding them returns HTTP 429. Exponential backoff with jitter retries after progressively longer, randomised waits.

Imagine this

A toll plaza with a fixed number of booths. When the queue is full, cars are turned back. If every turned-back car returns at exactly the same moment, the jam repeats. If each driver waits a different, growing amount of time (one minute, then two, then four, plus a random few seconds), the traffic smooths out. That random few seconds is the jitter.

Facts worth remembering

  • On Azure you assign TPM per deployment within your quota, and an RPM limit is derived from it. Limits count the maximum output tokens you request, so a huge max_completion_tokens eats budget even if unused.
  • Responses carry headers like x-ratelimit-remaining-tokens; 429s often include retry-after.
  • The OpenAI and Anthropic Python SDKs already retry 408, 409, 429 and 5xx twice with backoff by default. Tune max_retries; don't wrap a second blind retry loop around it.
  • For bulk work (summarising 40,000 complaint cases), don't retry harder: queue it and process at a steady rate, or use a batch API (Modules 08, 11).
In the real world
In finance

Banking traffic is spiky: salary day, the first of the month when bills go out, a card-network outage, or a fraud scare in the news can multiply chat volume in minutes. Teams size capacity (TPM) for those peaks, give interactive customer chat priority over back-office jobs, and push bulk work such as overnight complaint summaries or month-end statement analysis into queues or batch APIs. Some banks also reserve dedicated capacity (provisioned throughput) for customer-facing features so a busy internal team can't starve them.

Provider limits are tiered: new accounts get small limits that grow with usage and spend, and capacity for popular models can be scarce at peak times. Production teams monitor TPM utilisation, keep separate deployments (or quotas) for interactive and batch traffic, and use a gateway to spread load across regions or deployments when one is saturated.

Traditional developer view

"429? Retry in a loop until it works."

GenAI developer view

"429 is a capacity signal. Retry interactive calls with backoff and jitter, size TPM for peak traffic, cap output tokens, and move bulk work to a queue or batch."

Interview cue

"I handle 429s with exponential backoff plus jitter, honouring retry-after, with a cap on attempts, and I separate interactive traffic from batch work."

3
Check
Limits.



  
1. Why add random jitter to backoff waits?
So many clients that failed together don't retry together and cause the same overload again.

  
2. A nightly job summarising 40,000 complaint cases keeps hitting 429s and slowing the chat. What do you change?
Move it to a queue or batch API with a steady processing rate, ideally on separate capacity, instead of retrying harder.




Takeaway
Back off politely, honour retry-after, and keep bulk work out of the interactive lane.
