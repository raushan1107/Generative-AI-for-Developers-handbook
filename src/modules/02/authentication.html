Learn

House keys vs hotel key cards.

Definition

LLM APIs authenticate each request either with a static API key sent in a header, or with a short-lived access token issued by an identity provider (for Azure, a Microsoft Entra ID token checked against role-based access control).

In plain words

A key is a long password: whoever has it can spend your money, forever, until you regenerate it. A token is a temporary pass your app gets by proving who it is; it expires in about an hour and access can be removed centrally. Keys are fine for learning. Tokens are what you want in production.

Imagine this

An API key is a house key: copy it once and the copy works forever, and you'll never know who has one. A token is a hotel key card: issued at the front desk after checking your ID, it stops working at checkout, and the desk can deactivate it at any time.

Key hygiene

  • Never in code, never in the client. .env locally; Azure Key Vault or managed identity in the cloud.
  • Rotate without downtime. Azure gives each resource two keys: move apps to key 2, regenerate key 1, repeat next time.
  • One key per app and environment where possible, so a leak has a small blast radius.
  • Prefer keyless: a managed identity plus an RBAC role means there's no secret to leak at all.
In the real world
In finance

In a bank, API keys are treated like any other credential that can move money or expose data: stored in a vault, rotated on a schedule, never shared between environments, and their use logged. Most banks go further and switch keys off entirely, using managed identities so each application gets exactly the model access it needs and nothing else. Security reviews ask a simple question before go-live: "if this key leaked tonight, what could someone do with it, and how fast would we know?"

Leaked AI keys are a constant problem: bots scrape public repositories for them within minutes, and platforms such as GitHub run secret scanning that detects many provider key formats and alerts the owner. Enterprises on Azure typically disable key authentication on their AI resources altogether and use managed identities, so there is nothing to leak.

Interview cue

"In production on Azure I'd disable key auth and use managed identity with RBAC, so there's no secret to rotate or leak. Keys are for local development, in environment variables, never in the repo."

3
Check
Credentials.



  
1. Your key leaked in a public repo an hour ago and you deleted the commit. Are you safe?
No. Assume it's been copied. Regenerate the key now (Azure's two keys let you do it without downtime), then check usage for abuse.

  
2. Why is "Cognitive Services OpenAI User" better for an app than Contributor on the resource?
Least privilege: it can call deployments but not create, delete or reconfigure them, or read keys.




Takeaway
Keys for learning, identities for production. The safest secret is the one that doesn't exist.
