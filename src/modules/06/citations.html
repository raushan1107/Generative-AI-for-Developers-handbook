Learn

Every source marker should be inspectable, and checks have limits.

Definition

Citation and source attribution link statements in a generated answer to retrieved sources, typically with inline markers such as [1] that map to a document, section or URL. Verification has levels: code can check that a cited source was actually provided and apply narrow rules (such as checking numeric claims); a separate evaluator or human review is needed to assess whether the source really supports the meaning of a claim.

In plain words

Ask the model to show where a claim came from, show that source to the reader, and check what your code can check. A valid source number is only a pointer; it doesn't prove the source supports the claim.

Imagine this

A bank response says "your replacement card arrives in 5 to 7 business days [1]." The reader can open source [1] and inspect the policy. A simple code check can catch an unknown [4] or a number absent from the source; it may still miss a claim that misreads the policy's conditions.

In the real world

Citations help a banking assistant stay inspectable: a complaints handler can follow a dispute-deadline answer to the bank's help article. The Module 06 project checks that a cited section was sent to the model; the separate drill adds limited checks for numeric claims. Neither proves that a sentence follows the policy's conditions, so consequential answers need evaluation and appropriate human review.

In finance

For a card-dispute answer, a link to the exact policy section helps an agent or reviewer inspect the source and its conditions. Microsoft documents groundedness detection as an additional model-based signal in Azure AI Content Safety; it is not a guarantee of truth and does not replace evaluation or human review. See the Microsoft Learn overview.

Traditional developer view

"If the model includes a reference, the answer is sourced."

GenAI developer view

"A citation is a claim made by the model. I check source IDs against the retrieved set, add task-specific tests where they are safe, evaluate semantic support separately, and log failures as quality data."

Common trap

Showing every retrieved source as if it were cited. The reader sees four authoritative links under an answer that used one of them, or none, and assumes all four support it. Show what the answer cites; if it cites nothing, label the list honestly ("related articles"), as Milestone 6 does.

Interview cue

"I number the sources in the prompt and check citation ids in code. For bounded numeric claims, I can add narrow checks, but I don't treat a valid citation or number match as proof of entailment; I evaluate semantic support separately and route high-impact decisions to human review."

3
Check
Citations.



  
1. The answer says "express delivery is free [1]" and source 1 says "Express delivery costs $15, and is free for Premier Checking customers." Do the checks prove the answer is right for this customer?
No. The numeric checks don't test whether the customer has Premier Checking. The policy condition must be checked against trusted customer data, and the answer still needs an appropriate semantic support check.

  
2. Why does check() ignore codes like RR-10477 and CARD-503 when comparing numbers?
They're identifiers, often copied from the question or the customer's data, not amounts or durations claimed from a source. Treating them as numbers would flag correct answers.

  
3. A response passes source-ID and numeric checks but gives a wrong interpretation. What should the system do?
Those checks are not a semantic proof. Measure support with a relevant evaluator and representative test data; for a consequential answer, provide an escalation or human-review path.




Takeaway
Citations make answers inspectable, and narrow code checks catch specific failures. They do not prove an answer is true: validate source IDs, evaluate semantic support, and use human review when the stakes require it.
