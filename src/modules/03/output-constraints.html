Parsers have no sense of humour.

Definition

Output constraints specify the required form of the response (format such as JSON or markdown, length, allowed values, language, structure, and what to output when information is missing) so results are consistent and can be consumed by code or displayed reliably.

ConstraintExample instructionWhy
Format"Return only a JSON object. No markdown, no code fences, no text before or after."Models love wrapping JSON in ```json fences and adding "Here you go!"
Schema"Keys: issue_category, urgency, enrolment_id, summary. No other keys."Missing or extra keys break your code
Allowed values"urgency must be exactly one of: low, medium, high."Stops "High", "urgent!!" and "medium-high"
Missing data"If no enrolment ID is present, use null. Never invent one."Prevents plausible fabricated IDs
Length"summary: at most 20 words."Fits the UI; saves output tokens
Language"Write summary in English even if the message is in Spanish."Agents need one consistent language
Prompting gets you most of the way; Module 04 gets you all of it

Even a perfect prompt only makes valid JSON very likely. Modern APIs offer structured outputs: pass a JSON Schema and the API guarantees the shape. Module 04 covers it. Until then: constrain with the prompt and always validate in code.

In the real world

Extraction is one of the highest-value GenAI uses in business: invoices, claims, contracts, emails, support tickets turned into structured records. The teams that succeed specify the schema precisely, validate every response, retry or repair invalid ones, and track a validity rate as a production metric.

Interview cue

"For machine-read output I specify format, exact keys, allowed values and null handling, use structured outputs where available, and still validate before trusting it."

Open alternative · is your prompt portable?

      

        
A well-specified prompt usually works across providers. Check it on Claude with the same checker:


from claude_llm import client, CLAUDE_MODEL, FALLBACK, text_of
from lab03_11_json_fix import MESSAGES, RELIABLE, check   # the __main__ guard stops the runs

for message in MESSAGES:
    msg = client.beta.messages.create(
        model=CLAUDE_MODEL, max_tokens=4000,
        messages=[{"role": "user", "content": RELIABLE.format(message=message)}],
        **FALLBACK,
    )
    print(check(text_of(msg).strip()), "<-", message[:44])

        
Also try LLM_PROVIDER=ollama: small local models break constraints more often, so the same checker gives you a fair, numeric model comparison.

Constraints.



  
1. Your extraction prompt returns valid JSON 95% of the time. Production-ready?
Not on its own: 5% of 25,000 messages is 1,250 failures a month. Tighten the prompt, use structured outputs (Module 04), and always validate with a retry or repair path (Milestone 3 does this).

  
2. Why "never invent one" for the enrolment ID?
Without it, a plausible-looking but fake ID can appear, and downstream systems would act on it. Null is honest; invented is dangerous.




Takeaway
For machines, specify the exact shape, and validate every single response.
