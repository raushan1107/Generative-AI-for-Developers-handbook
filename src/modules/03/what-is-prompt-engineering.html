Learn

Half writing, half testing.

Definition

Prompt engineering is the practice of designing, testing and refining the inputs given to a language model (instructions, context, examples and output specifications) so that it reliably produces outputs that meet a defined requirement.

In plain words

Write instructions so clear that the model can't misunderstand them, then check, over many inputs, that it really doesn't.

Everything the model reads is the prompt

Beginners think the prompt is the user's question. For a developer, the prompt is the entire request, and you control most of it.

System messageYour standing instructions: role, rules, tone, output format. Written once, versioned.
ExamplesSample inputs and ideal outputs that show the pattern (few-shot).
Context / dataPolicies, documents, records: facts the model should use (RAG, Module 06).
User messageThe input for this request: the only part you don't write, and the only part you shouldn't trust.
In the real world

The system prompts behind well-known AI products are long, carefully structured documents: role, capabilities, rules, formatting, safety behaviour, often thousands of words, maintained by teams and changed through review. Some companies have published theirs. Nobody gets there by tweaking a sentence until a demo works; they get there by specifying and testing.

Common trap

Judging a prompt by one run. Models sample, so one great answer proves very little. Run on several inputs, several times, and count: how often valid, how often correct, how long. That habit alone puts you ahead of most teams.

Interview cue

"Prompt engineering is specifying the task (context, task, constraints, examples, output format) and testing it across a set of inputs. I treat prompts like code: versioned, reviewed and regression-tested."

Drill 03.1

Vague vs specified: prompt your coding assistant two ways

~20 minCopilot · Claude Code · Codexpytest

Goal: feel, on a tool you use every day, how much a specified prompt changes the result, and that it's the same skill you'll use on the model inside your app.

  1. Ask AI

    Prompt A: the vague version

    In a new folder prompt-test-a, send:

    write an email validation function

    Note what you got: which language, what rules, any tests, how it reports failures.

  2. Ask AI

    Prompt B: the specified version

    In a new folder prompt-test-b, send:

    Context: TrainCrest's sign-up form needs a simple, explainable email check (not full RFC 5322).
Task: write validate_email(address: str) -> tuple[bool, str] in validate_email.py, returning
(is_valid, reason).
Rules, in this order: strip surrounding whitespace; empty -> "empty"; longer than 254 chars ->
"too long"; contains a space -> "contains spaces"; not exactly one "@" -> "must contain exactly
one @"; nothing before "@" -> "missing name before @"; domain without a dot, starting or ending
with a dot, or containing ".." -> "invalid domain"; otherwise (True, "ok").
Constraints: standard library only, no regex, type hints, a docstring listing the rules.
Output: also write test_validate_email.py with pytest covering 3 valid addresses and every
invalid reason. Run the tests and show me the result.
    Why prompt B works: context (why and for whom), the exact signature and return shape, every rule in order, constraints, and an output that includes its own verification. That's the prompt design framework applied to a coding assistant.
    Reference result for prompt B

  3. Verify
        
    $ cd prompt-test-b
$ pytest -q
    
        
    • Prompt B's tests pass (12 cases in the reference).
    • Try Prompt B's tests against Prompt A's function. Most of them fail: not because A is "wrong", but because nobody told it what "right" meant.

  4. Think
        
    Which of the five framework blocks (context, task, constraints, examples, output format) did prompt A leave entirely to the assistant's imagination?
    
        
    Compare with my answer
    All five. It had no context (why, for whom), a vague task (no signature or return shape), no constraints (language, libraries, rules), no examples and no output format (tests? explanation?). Prompt B filled every one.

Check
Two questions.



  
1. Which part of a request is the only one you shouldn't trust, and why?
The user message: anyone can write anything in it, including instructions that try to override yours (topic 10).

  
2. A prompt gave a perfect answer in your demo. Is it ready?
Not yet. One run proves little; test it on many inputs, several times, and count the results.




Takeaway
Whether you're prompting the model in your app or the assistant in your editor, the skill is the same: specify, then verify.
