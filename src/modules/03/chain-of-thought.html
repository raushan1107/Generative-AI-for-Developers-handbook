Learn

Ask for an explanation when useful, then verify it.

Definition

Chain-of-thought (CoT) prompting asks a model to write intermediate steps before a final answer. It can help on some multi-step tasks, but results vary by task and model, and a generated explanation is not proof that the answer is correct. Some reasoning models use hidden reasoning tokens without returning those internal steps in the visible response; Azure OpenAI counts these tokens in the context window and bills them as output tokens.

Imagine this

Maths exams at school: "show your working". Written steps can help someone review a solution, but they don't guarantee the answer is right. Some reasoning models use hidden tokens that aren't returned as a readable transcript; in Azure OpenAI, these are billed as output tokens.

Model typeHow to get step-by-step reasoningWatch out for
Standard chat modelFor a learning exercise, you can ask for a brief explanation before the answer.Explanations can be incomplete or unfaithful; evaluate the answer separately.
Reasoning modelSome APIs expose an effort or thinking control. State the goal, constraints and output you need.Controls and usage accounting vary. Do not assume hidden reasoning is available or correct.

Rules for CoT in an application

  • Keep customer-facing output separate from internal records. Return the answer and any concise, evidence-based explanation you need; don't treat free-form reasoning as a verified trace.
  • Don't request long reasoning where it isn't needed. Classifying "charged twice" doesn't need five steps.
  • Reasoning isn't proof. Convincing steps can still be wrong. Verify critical results in code (dates, amounts) or with evaluation.
In the real world

Some reasoning-model APIs provide an effort or thinking control, while others use different parameters. For auditability, keep reproducible inputs, tool traces, cited evidence and a concise explanation; don't rely on raw chain-of-thought as evidence.

In finance

Fee and interest calculations, dispute deadlines and eligibility checks are multi-step problems, which is exactly where models can make confident mistakes. Banks can use a model to help interpret a case, but should keep authoritative arithmetic in tested code. For an audit trail, record the input, model and prompt versions, cited policy, tool calls, output and human decision; a generated chain of thought is not a verified record of how the model reached its answer.

Reasoning features and token accounting are model-specific. See the current OpenAI reasoning guide and Microsoft Foundry reasoning-model documentation.

Common trap

Treating raw reasoning as reliable internal notes or customer text. Return a concise explanation only when it is useful, and verify any factual claims in it.

Interview cue

"Step-by-step prompting can help on some multi-step tasks, but it doesn't prove correctness. Some reasoning models offer an effort control and don't return hidden reasoning. I verify critical results in code."

Check
Reasoning.



  
1. You ask a reasoning model to "think step by step" and print its reasoning to customers. What's wrong?
It already reasons internally, so you add visible tokens and cost; and reasoning isn't customer text. Keep reasoning separate from the answer, and tune reasoning_effort instead.

  
2. When is visible reasoning still useful?
For auditability and debugging: storing why a decision was suggested, for a human reviewer, not for the end user.




Takeaway
Let the model reason, keep the reasoning backstage, and let code do the exact maths.
