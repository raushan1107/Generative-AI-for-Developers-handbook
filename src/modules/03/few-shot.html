Learn

The senior agent sitting beside the new joiner.

Definition

Few-shot prompting includes a small number of input–output examples in the prompt so the model can infer the desired mapping, labels and format by analogy, without changing its weights (in-context learning).

Imagine this

On a new joiner's first day at RR Finance Bank support, a senior agent doesn't read out a 20-page labelling manual. They sit beside them: "This customer was charged twice by a shop they used: we tag dispute. This one doesn't recognise the payment at all: fraud, and it goes to the fraud team straight away." A few examples and the new joiner gets it. Few-shot is that senior agent.

Getting examples right

  • Two to five examples usually suffice; more costs tokens on every call.
  • Cover the tricky cases, not just the easy ones. Examples should sit on the boundaries you care about.
  • Vary and balance them. Four dispute examples and one other nudge the model towards dispute.
  • Keep the format identical. The model copies format faithfully, mistakes included.
  • Use user/assistant pairs or a clearly delimited block in the system message; both work.
In finance

Few-shot examples are how banks teach a model their internal taxonomy: complaint reason codes, dispute reason codes from the card networks, or the bank's own split between "fraud" and "dispute", which decides which team, deadline and regulation applies. The examples are chosen from reviewed historical cases (anonymised), deliberately include the borderline ones, and are versioned with the prompt, because changing an example changes how thousands of customers are routed.

In the real world

Few-shot is the workhorse of production classification and extraction pipelines: routing tickets, tagging reviews, normalising product attributes. Some teams go a step further and retrieve the most similar labelled examples for each new input (dynamic few-shot), combining this topic with the embeddings of Module 05.

Common trap

Using real customer tickets as examples, complete with names, emails and phone numbers. That's personal data sent on every request and stored in your prompt files. Write synthetic examples, or anonymise real ones first.

Interview cue

"Zero-shot first; if outputs are inconsistent or the task has company-specific conventions, add a few diverse, balanced examples that cover the edge cases. It's in-context learning: no fine-tuning needed."

  2. Verify
    • Five examples took the same small model from 5/12 to 10/12, and fixed the "money missing after a text" fraud case and the fee-refund rule.
    • One fraud message ("a payment to a shop in another country") is still labelled dispute: the examples don't cover "a payment in a place I've never been". Which example would you add?
    • Input tokens more than doubled. At 40,000 messages a month, work out the extra cost with your price (Drill 02.14). Is the accuracy gain worth it? Usually, yes.
  3. Think

    Edit FEW_SHOT_EXAMPLES to contain four dispute examples and one card example, and rerun. What happens to tickets in other categories?

    What usually happens

    Borderline messages drift towards dispute (including some fraud, which is the costly direction): the model treats the example distribution as a hint about what's common. Balanced examples matter. Restore the original list afterwards.

3

Check

Examples.

1. Zero-shot labels "money disappeared after I clicked a link" as "dispute". Cheapest fix?

Few-shot examples that include such a message labelled "fraud", in a balanced set. Fine-tuning would be overkill for a rule that examples teach instantly.

2. What's the cost of few-shot, and how do you decide if it's worth it?

More input tokens on every call. Compare the accuracy gain on your test set against the extra cost at your volume.

Takeaway

When the model keeps missing your conventions, show it a few balanced examples, and measure the gain.
