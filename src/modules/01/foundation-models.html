1

Learn

Build once, adapt many times.

Definition

A foundation model is a large model trained on broad data that can be adapted, through prompting, grounding or fine-tuning, to a wide range of downstream tasks. LLMs such as the GPT, Claude, Llama and Phi families are foundation models.

In plain words

Instead of one model per task, there are a few huge general models, and everyone adapts them. The same model can summarise a ticket, write SQL, translate Spanish and draft an email. You choose a foundation model, then shape it with prompts and data.

Imagine this

A foundation model is a fresh graduate from a top university: broadly trained, quick to learn, not yet specialised. You don't send them back to university for every new task. You give them a brief (prompt), reference material (RAG) and, for long-term roles, some on-the-job training (fine-tuning).

Name check

Model names change every few months. In the last year Azure retired whole families and added new tiers such as GPT-5.6 Sol, Terra and Luna. Don't memorise names: learn the tiers, and check the Foundry model catalogue and its retirement schedule when you start a project.

How to choose: the questions that matter

QuestionWhy it mattersLeans towards
How hard is the task?Multi-step reasoning, tricky code and nuanced writing need capable modelsFrontier for hard reasoning; small for classify, extract, route
How fast must it answer?Chat users notice delays before the first wordSmall models, streaming, low reasoning effort
How many calls a day?Cost = volume × tokens × priceSmall models for high volume; route only hard cases up
How much context?Long documents need big windowsLarge-context models, or better retrieval
Which inputs?Images, audio, PDFsMultimodal models (next topic)
Where may data be processed?Regulation and contractsData Zone or regional deployments, or self-hosted open-weight
In the real world

Many products quietly use several models. GitHub Copilot, for example, lets you pick between models from different providers for chat. Production systems often route: a small, cheap model handles routine requests and a larger one handles the hard ones (Module 11). Teams pick models from their own evaluation results, because public benchmarks rarely match a company's actual tasks.

Traditional developer view

"Use the biggest, newest model. Best is best."

GenAI developer view

"Use the smallest model that passes my evaluation for this task, and keep the model name in configuration so I can switch when a better or cheaper one ships."

Interview cue

"How do you choose a model?" "Task difficulty, latency, cost at our volume, context length, modality and data residency, validated with an evaluation set on our own data."

Drill 01.11

Same prompt, two models: measure, then extend the benchmark

~20 minAzure OpenAIOllama · Claude (optional)

Goal: compare latency, tokens and quality on a real support task, then have your assistant turn the script into a small, repeatable benchmark.

Before you start: you need a second model. Deploy a larger model in the same Foundry resource (for example a "sol" tier or gpt-5.4) as chat-big, or have Ollama running. Add COMPARE_DEPLOYMENT=chat-big and/or COMPARE_WITH_OLLAMA=1 to .env.

    Race the models

    
        
    $ python lab01_11_compare.py
    
        
    Run it twice (latency varies). Score each answer 1–5: follows the policy (no refund, offers a reschedule), kind tone, under 80 words.

  2. Your prompt
    Turn it into a benchmark
    
        
    One run proves little. Ask your assistant to extend the script: several runs per model, averages, and a table you could paste into a design document.
    
        
    Goal:        extend #lab01_11_compare.py into …
Context:     it already builds a list of (label, client, model) targets
Constraints: N runs per model; measure …; estimate cost from …;
             keep the existing targets logic; no new dependencies
Done when:   it prints a markdown table with one row per model
    
        
    Hint: ask for --runs 3, averages of latency, input tokens and output tokens, an estimated cost using PRICE_IN_PER_M / PRICE_OUT_PER_M from .env, and the shortest answer printed under the table for a quick quality check.
    
        
    Compare with my prompt
    
          
    Extend #lab01_11_compare.py into a small benchmark. Keep the existing targets logic.
Add argparse with --runs (default 3). For each target, call the model --runs times with PROMPT
and record latency, prompt_tokens and completion_tokens. Then print a markdown table with
columns: target | model | avg latency (s) | avg tokens in | avg tokens out | est. $ per call,
where cost uses PRICE_IN_PER_M and PRICE_OUT_PER_M from .env (USD per 1M tokens, defaults
0.40 and 1.60). Under the table, print each target's first answer. No new dependencies.

  3. Verify
        
    • The table has one row per target and plausible numbers (latency in seconds, not milliseconds).
    • On a reasoning model, output tokens are much higher than the visible answer suggests: they include hidden reasoning tokens, which you pay for.
    • Decide: for this focused task, is the bigger model worth its cost and latency? Write one sentence, as you would in a design review.

import time
from claude_llm import client, CLAUDE_MODEL, FALLBACK, text_of
from lab01_11_compare import PROMPT   # reuse the same prompt (this also runs the main race)

start = time.perf_counter()
msg = client.beta.messages.create(model=CLAUDE_MODEL, max_tokens=4000,
                                  messages=[{"role": "user", "content": PROMPT}], **FALLBACK)
print(f"claude · {time.perf_counter() - start:.1f}s · {msg.usage.input_tokens} in / {msg.usage.output_tokens} out")
print(text_of(msg))

Model choice.



  
1. Traincrest Assist must classify 25,000 tickets a month into 7 categories. Which tier first, and why?
A small, cheap model: focused task, high volume, latency matters. Validate on labelled samples and move up a tier only if it fails your quality bar.

  
2. Why keep the model name in configuration rather than in code?
Models are retired and replaced every few months. Configuration lets you switch or A/B test without a code change (and Module 12 adds model fallbacks).
