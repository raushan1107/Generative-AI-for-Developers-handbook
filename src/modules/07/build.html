Plan

From telling customers what to do, to doing it with their consent.

RR Finance Bank· the brief for milestone 7

Customers may need a card frozen or a transaction disputed. The brief: let RR Finance Assist prepare these actions while keeping control of execution in application code. Constraints: nothing changes without the customer's explicit approval; the customer sees the exact action and relevant amount before approving; a retry cannot apply the same change twice; fee exceptions and other cases still go to human support; and each change is logged.

    Proposals, decisions and guard rails in the chat service
    
        
    Update #file:app/chat.py for milestone 7:
1. ChatService gets self.actions = ActionStore() from #file:app/actions.py.
2. The per-turn context also has "proposals": []. After the reply is saved to history, add each
   proposal to self.actions with the session id, and put
   "approvals": [{"action_id", "summary"}] for them in the done event.
3. In the tool loop, count (name, arguments) pairs; on the third identical call, return
   {"error": "you already made this exact call; use its result or answer"} instead of running it.
4. Add looks_like_tool_call(text): true when the final reply is JSON with "name" and
   "arguments" or "parameters". If so, replace the reply with a friendly GARBLED message
   (yield a "replace" event) and log "tool_call_as_text".
5. Add learner_context(customer_id): "## Signed-in customer" with the name and their own accounts,
   cards and payments from the backend; append it to the system prompt when signed in.
6. Add decide(session_id, action_id, customer_id, approve): call self.actions.decide, append
   "[action_id status] message" to the session history as an assistant message (unless status is
   "unknown"), log it, and return the result.
Don't change anything else. Then add POST /api/actions/{action_id} to #file:app/main.py with a body
{session_id, customer_id, decision: "approve" | "decline"}, returning 404 for "unknown".
    
        
    Why this prompt works: six numbered changes, each with exact names, data shapes and the order of operations, so the result is reviewable step by step. Recording the decision in history keeps the model from later claiming an action was completed when it was declined. The session context comes from the authenticated app and is limited to the signed-in customer's own data.

        Expected behavior, covered by the offline tests

    Customer: "Freeze my Cashback Card."
Assist: prepares a proposal to freeze the signed-in customer's card ending 4821.
Before approval: card status is unchanged; no action log entry exists.
After approval: card status is frozen; one action log entry exists.
After a retry with the same action id: the write is not applied twice.
    
        
    This is deterministic behavior from the project tests, not a promise that every language model will choose the correct tool. The UI presents approval controls only for a proposal returned by the application; model-written text that merely claims a change is not treated as an action. Validate tool selection and user-facing explanations with the model and deployment you plan to use.
