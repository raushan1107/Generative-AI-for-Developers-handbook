Plan

From telling customers what to do, to doing it with their consent.

RR Finance Bank· the brief for milestone 7

Lab extensions and date changes are a large share of support tickets, and each one waits about a day for a person who follows the same rules every time. The brief: let RR Finance Assist do these two actions itself, within policy. Constraints from the support lead: nothing changes without the customer's explicit approval; the customer sees the exact effect and fee before approving; a double click or a retry can never change a booking twice; refunds and exceptions still go to people; and every change is logged with who approved it.

    Proposals, decisions and guard rails in the chat service
    
        
    Update #file:app/chat.py for milestone 7:
1. ChatService gets self.actions = ActionStore() from #file:app/actions.py.
2. The per-turn context also has "proposals": []. After the reply is saved to history, add each
   proposal to self.actions with the session id, and put
   "approvals": [{"action_id", "summary"}] for them in the done event.
3. In the tool loop, count (name, arguments) pairs; on the third identical call, return
   {"error": "you already made this exact call; use its result or answer"} instead of running it.
4. Add looks_like_tool_call(text): true when the final reply is JSON with "name" and
   "arguments" or "parameters". If so, replace the reply with a friendly GARBLED message
   (yield a "replace" event) and log "tool_call_as_text".
5. Add learner_context(customer_id): "## Signed-in customer" with the name and their own enrolments
   from backend.enrolments_of; append it to the system prompt when a customer is signed in.
6. Add decide(session_id, action_id, customer_id, approve): call self.actions.decide, append
   "[action_id status] message" to the session history as an assistant message (unless status is
   "unknown"), log it, and return the result.
Don't change anything else. Then add POST /api/actions/{action_id} to #file:app/main.py with a body
{session_id, customer_id, decision: "approve" | "decline"}, returning 404 for "unknown".
    
        
    Why this prompt works: six numbered changes, each with exact names, data shapes and the order of operations, so the result is reviewable step by step; the outcome note in history is spelled out, because it's what keeps the model from later claiming an action that was declined. The session context came from testing: even with a prompt rule, qwen2.5:7b kept asking Mei for her enrolment ID instead of looking it up. Giving the model the signed-in customer's own enrolments (data the app already owns, nothing the customer can't see) removed a tool call and the problem.
