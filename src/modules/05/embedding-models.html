Learn

Pick on your data, not on a leaderboard.

Definition

An embedding model is a neural network trained to map text (and sometimes images or code) to vectors so that related inputs are close together. Models differ in quality for a domain and language, dimensions, maximum input length, cost and where they run.

In plain words

All embedding models do the same job, like all translators do. Some are better with legal text, some with Spanish, some are cheaper, some run on your laptop. You choose by testing on your own material.

Imagine this

Choosing a map for a hiking trip. A world atlas, a country road map and a detailed trail map all show the same land at different detail, size and price. The best map isn't the most detailed one; it's the one that gets you to your trail without weighing down your bag.

The choices that matter

  • Quality on your data: build 20 to 50 real questions with known answers (like data/help_questions.json) and measure how often the right document comes first. That number beats any leaderboard.
  • Languages: if users write in Spanish and Hindi, test in Spanish and Hindi (Drill 05.2 showed a mostly-English model missing a Spanish paraphrase).
  • Dimensions and storage: 1,536 float32 numbers take about 6 KB, so a million chunks is about 6 GB of vectors before indexes. The text-embedding-3 models accept a dimensions parameter to return shorter vectors (for example 256) that keep most of the quality.
  • Input length: text-embedding-3 accepts up to 8,191 tokens per input, but retrieval usually works better on shorter, focused chunks (topic 6).
  • Task prefixes: some models (like nomic-embed-text) expect search_query: on questions and search_document: on documents. Skipping them still works, just less well.
  • Switching cost: changing model means re-embedding every document. Store the model name with the index and plan re-indexing like a database migration.
In the real world
In finance

Choosing an embedding model in a bank adds two questions to quality and cost: languages (customers write in many) and data residency (texts sent for embedding are customer data). Some banks host an open embedding model internally for exactly that reason. Changing the model means re-embedding everything, so the model name is versioned with the index.

Teams usually start with a cheap general model, build a small labelled test set from real user questions, and only move to a bigger or specialised model when the test set shows a real gain. Large indexes often use shortened vectors to cut storage and latency, accepting a small quality loss measured on that same test set.

Traditional developer view

"Pick the top model on the benchmark and move on."

GenAI developer view

"Benchmarks shortlist; my test set decides. I weigh hit rate against cost, size and languages, record the model with the index, and treat a model change as a migration."

Common trap

Changing the dimensions setting (or the deployment behind embed) for new documents only. Old and new vectors no longer match in size or space, and the index either errors or quietly returns nonsense. Any change to the model or its settings means rebuilding the whole index.

Interview cue

"I choose an embedding model by measuring retrieval on our own labelled questions, considering language coverage, dimensions (storage and latency), input limits and cost. Changing models requires re-embedding the corpus, so the model is versioned with the index."

Check
Choosing models.



  
1. Two models score 92% and 94% on a public leaderboard. How do you choose for RR Finance Bank?
Run both on RR Finance Bank's own labelled questions, in the languages customers use, and weigh the hit rate against cost, dimensions and hosting. Leaderboard gaps that small often vanish or reverse on your data.

  
2. You want to move from text-embedding-3-small to -large. What has to happen?
Re-embed every document with the new model, build a new index (dimensions change from 1,536 to 3,072), switch queries over at the same moment, and compare hit rates before and after.




Takeaway
Choose the embedding model with your own test set, version it with your index, and budget a re-index for every change.
