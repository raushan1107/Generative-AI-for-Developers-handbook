Learn

The model decides what to ask for. Your code decides everything else.

Definition

Connecting an LLM to application logic means exposing a controlled set of your existing functions as tools, and running a tool loop: call the model, execute any requested tools through a dispatcher that validates arguments and enforces permissions, return the results, and repeat until the model answers or a limit is reached.

In plain words

Your app already has functions: search the catalogue, look up a booking, open a ticket. The model becomes a smart front desk that chooses which of them to use for a conversation. It never gets the keys to the building.

Imagine this

A hospital receptionist can book appointments, check a patient's next visit and page a nurse, all through the hospital system, which checks who's logged in and what they may see. The receptionist chooses what to do for each caller; the system decides whether it's allowed. If the receptionist could type any patient's name and see their file, the problem wouldn't be the receptionist.

Rules for tools that won't hurt you

RuleWhy
Identity comes from the session, never from a tool argumentOtherwise "show me account AC-7720" reads someone else's balance (Drill 04.8)
Errors are data: return {"error": "..."}, don't raiseThe model can explain or recover; one bad call doesn't crash the chat
Small, specific tools (quote_fee_refund, not run_sql)Easier for the model to choose, easier for you to secure and test
Money, dates and rules in codeThe model explains a fee refund; policy.fee_refund_quote() calculates it
Separate reads from writes; writes need extra careReading a status is safe to retry; creating a ticket twice isn't. Module 07 adds human approval.
Limit the loop (rounds, time, tokens)A confused model can call tools forever, and you pay for every round
Log every call (tool, ok/error, duration)When an answer is wrong, the tool log tells you whether the model or the data was at fault
In the real world
In finance

Fees, interest, eligibility and deadlines are business rules with legal weight, so they live in tested code, owned by the product and risk teams. The model's job is to understand the customer's question and to explain the result; the fee refund amount, the dispute deadline or a loan payment comes from a function. When a regulator asks "why did this customer get $87 back?", the bank points to code and its test, not to a model's reasoning.

Customer-service assistants at airlines, telecoms and retailers follow exactly this pattern: a handful of narrow tools (booking lookup, change fee quote, open a case), identity from the logged-in session, money calculated by existing billing code, and every write either confirmed by the customer or reviewed by a person. The language model adds the conversation; it doesn't replace the business rules.

Traditional developer view

"The front end calls my API with the user's ID, and I return their data."

GenAI developer view

"Text from the user, documents and tool results can all steer the model. So the model is an untrusted caller: tools get identity from the authenticated session, validate every argument, and can only do what that user could do anyway."

Common trap

A tool like get_account(customer_id, account_id). It looks tidy, and it lets anyone who can talk the model into a different ID read another customer's balance. The fix isn't a better prompt; it's removing customer_id from the tool's parameters.

Interview cue

"I run a bounded tool loop through a dispatcher that validates arguments, enforces authorization from the session context, returns errors as data, and logs every call. The model chooses tools; it never chooses whose data a tool touches."

Design:
- class Toolkit with register(args_model, needs_context=False) used as a decorator; the function's

  2. Think
    Could a better system prompt have fixed Design A?
    
        
    Compare with my answer
    It would reduce how often the model makes that call; it can't make it impossible. Prompts are probabilistic, and attacks arrive through user text, documents and even tool results. Design B makes the leak impossible no matter what the model is persuaded to do, because the check runs in code with the session's identity. Notice too that Design B returns the same error for "someone else's" and "doesn't exist", so an attacker can't probe which IDs are real.

3
Check
Wiring the model in.



  
1. A tool raises an exception inside your loop. What should the user see, and what should the model see?
The model should get a tool message with {"error": "tool failed: ..."} so it can apologise or try another way; the user sees a normal reply, and your logs record the failure. The chat shouldn't crash.

  
2. Why cap the number of tool rounds?
Every round is a paid model call and adds latency; a confused model or a tool that keeps failing can loop indefinitely. A cap gives you a predictable worst case and a graceful fallback (offer a ticket).

  
3. Where should a fee refund amount be calculated: in the prompt, by the model, or in a tool? Why?
In a tool backed by policy code. Money must be exact, consistent and auditable; the model's job is to explain the result kindly.




Takeaway
Wire the model to small, validated, permission-checked functions through a bounded loop, and keep identity, money and rules in code.
