Learn

Trust the shape. Check everything else.

Definition

Output validation checks model output before your application relies on it: that it has the expected shape (schema), obeys business rules (formats, ranges, dependencies between fields), and agrees with facts from your systems (IDs that exist, amounts your code calculated). Invalid output is rejected, repaired, retried or escalated, never silently used.

In plain words

Treat model output like a form submitted by a stranger on the internet: well formatted, probably honest, and checked anyway.

Imagine this

Airport security has layers. The airline checks your ticket has the right format. The gate checks the date and flight match today. Passport control checks the photo matches you. A perfect-looking ticket for yesterday's flight passes the first check and fails the second. Each layer catches what the one before can't.

When validation fails

  • Tool arguments: return the validation message as the tool result ({"error": "invalid arguments: customer_id: must look like RR-12345"}). The model usually fixes it, or asks the customer, on the next round.
  • Structured replies: retry once with the error (Milestone 3's repair idea), then fall back to a safe default or a "couldn't process" response.
  • Facts in the final answer: block, regenerate, or flag for review, depending on the risk. A wrong fee refund amount is worth blocking; a slightly long summary isn't.
  • Always log it. A rising validation-failure rate is often the first sign a prompt, model or data change broke something (Module 09).
In the real world
In finance

Banks validate in layers exactly like this drill: the schema checks the shape, validators check business rules (a dispute date can't be in the future, an IBAN must pass its checksum, an amount must be positive), and a facts layer compares what the model said with what the systems hold. Any amount in a customer reply that no system produced is a red flag, and is blocked before the customer sees it.

Finance and insurance teams using extraction models run all three layers: schema, rules (totals add up, dates are plausible), and facts (the supplier exists in the vendor database, the policy number is active). Documents that fail go to a human queue. The validation-failure rate is a dashboard metric, just like error rates for an API.

Traditional developer view

"The schema validated, so the data is good."

GenAI developer view

"The schema means the data is well formed. Whether it's allowed and whether it's true are separate questions, answered by my validators and my systems."

Common trap

Validating at the end of the pipeline only. By then the invented ID has already been used in a lookup and the wrong amount is already in a reply. Validate at the boundary: as tool arguments arrive, and before an answer is sent.

Interview cue

"I validate in three layers: schema for shape, validators for business rules, and cross-checks against source systems for facts, at every boundary, with retry, fallback or escalation on failure, and I monitor the failure rate."

1. The schema says transaction_date is a string. The model sends "last Tuesday". Which layer catches it, and how?
Layer 2: a @field_validator that parses ISO dates (date.fromisoformat) and checks the range. Return the message to the model so it can ask the customer for a date or convert it.

  
2. Why return validation errors to the model instead of just raising?
Because the model can often fix the problem (reformat, ask the user) on the next round. Raising ends the conversation with a generic error.

  
3. Name a check that no schema or validator can do on its own.
Anything needing your data: the account exists and belongs to this customer, the fee refund amount matches the policy quote, the payment is on this customer's card.




Takeaway
Schema for shape, validators for rules, your systems for facts. Validate at every boundary and log every failure.
