Valid JSON is a low bar.

Definition

JSON mode (response_format={"type": "json_object"} in Chat Completions) constrains the model so its reply is a syntactically valid JSON object. It does not enforce any particular keys, types or values. The prompt must mention JSON, and you describe the wanted fields in words.

In plain words

JSON mode promises brackets, quotes and commas in the right places. It promises nothing about what's inside. You asked for customer_id; you might get customerIdentifier, id or a nested details object.

Imagine this

You ask five colleagues to "send me the details as a spreadsheet". You get five valid spreadsheets: one has columns Name, Issue, one has Customer, Problem, Status, one put everything in cell A1. Every file opens. None of them can be merged without manual work.

Facts worth remembering

  • The request must mention "JSON" in a message, or the API rejects it. Describe the fields too; otherwise the model invents its own.
  • JSON mode is widely supported (Azure OpenAI, OpenAI, Ollama and most OpenAI-compatible servers), so it's a useful fallback where structured outputs aren't available.
  • If the reply is cut off by max_completion_tokens, the JSON is incomplete. Check finish_reason == "length" (topic 7).
  • Claude has no JSON-mode switch; you get the same effect with a clear prompt or, better, with a tool whose input schema is your object (shown on the next page).
In the real world
In finance

Valid JSON with the wrong keys is a classic integration bug in banking: one reply says amount, the next txn_amount, a third returns the amount as the string "$412". Downstream reconciliation then silently drops records. JSON mode alone is acceptable for exploratory analyst tools; anything that feeds payments, disputes or reporting needs a schema and validation.

Teams that started with JSON mode in 2023 all built the same thing next: a validator that checks the keys and types, plus a retry loop. That pile of glue code is exactly what structured outputs replaced. You'll still meet JSON mode with local and older models, so it's worth knowing its limits.

Traditional developer view

"It's valid JSON, so the integration works."

GenAI developer view

"Valid JSON means it parses. I still need the right keys, types and values, so I either enforce a schema or validate every reply."

Common trap

json.loads() succeeds and the code moves on, then fails three functions later with KeyError: 'customer_id' because this reply called it customerIdentifier. Validate right where the JSON enters your system.

Interview cue

"JSON mode guarantees syntax, not schema. For a fixed shape I use structured outputs with a JSON Schema; I keep JSON mode as a fallback for models that don't support it, with validation."

Check
JSON mode.



  
1. JSON mode is on and json.loads() never fails. What can still go wrong?
Wrong or missing keys, wrong types ("null" as a string, numbers as text), values outside the allowed list, invented values, and truncated output if the token limit is hit.

  
2. When would you still choose JSON mode today?
When the model or server doesn't support structured outputs (some local or older models), or when the shape is genuinely open-ended. Always pair it with validation.




Takeaway
JSON mode fixes the syntax. The prompt can fix the keys. Neither fixes the types or the truth.
