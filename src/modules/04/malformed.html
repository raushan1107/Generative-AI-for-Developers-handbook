Learn

Name every failure, then handle each one on purpose.

Definition

A malformed response is any model output your code can't safely use as intended: incomplete, refused, filtered, unparseable, schema-invalid, rule-invalid, or a tool call with a bad name or arguments. Handling it means detecting the specific case (mostly from finish_reason, refusal and validation errors) and applying a deliberate policy for it.

In plain words

"It didn't work" isn't one problem. A reply that ran out of space needs more space; a refusal needs a different response to the user, not a retry; garbage needs a second try with the error shown. Different failures, different fixes.

Imagine this

A delivery driver comes back with your parcel. If the address was smudged, you rewrite it and send it again. If the van was full, you send a bigger van. If the recipient refused it, sending it again won't help. A good dispatcher checks why it came back before doing anything.

Retry only when retrying can help

  • Worth retrying: truncation (with more room), invalid or rule-breaking output (with the error), transient API errors (the SDK retries 429 and 5xx for you, Module 02).
  • Not worth retrying: refusals, content-filter blocks, authentication errors. Same input, same outcome, double the bill.
  • Always bounded: one repair round is usually enough; two at most. After that the problem is your prompt, schema or model choice, and the logs should tell you so.
In the real world

Teams running document extraction at scale typically see a small but steady fraction of replies needing repair, and a far smaller fraction refused or filtered. They track each outcome separately on a dashboard. A jump in "truncated" usually means documents got longer; a jump in "invalid" after a deploy usually means someone changed the prompt or the schema.

Traditional developer view

"Wrap the call in try/except and retry three times."

GenAI developer view

"Each failure has a name and a cause. I return a typed outcome (ok, refused, blocked, truncated, invalid), retry only the ones a retry can fix, and count each one."

Common trap

Ignoring finish_reason. A reply cut off at the limit can still look fine in prose ("Your refund will be"), and in JSON mode it fails with a confusing parse error. Check why the model stopped before you read what it wrote.

Interview cue

"I check finish_reason and refusal first, validate second, and map every case to an outcome: truncation gets more tokens, invalid output gets one repair with the error, refusals and filter blocks get a safe response and no retry. All bounded, all logged."

3
Check
Malformed responses.



  
1. Your extraction job's "truncated" count doubled overnight. First thing to check?
Whether inputs got longer (new document type, bigger attachments) or someone lowered max_completion_tokens or changed the schema to ask for more fields. Truncation is about room, not quality.

  
2. Why not retry a refusal three times?
The same input will almost always be refused again: three times the cost and latency for the same result. Handle it: safe message to the user, log it, escalate if it looks like a false positive.

  
3. With strict structured outputs, which failures can still happen?
Truncation, refusals, content-filter blocks, rule failures your validators catch, and wrong-but-valid values. Strict mode removes "not JSON" and "wrong shape", nothing else.




Takeaway
Check why the model stopped, validate what it wrote, and give every failure a name, a bounded policy and a counter.
