Learn

Don't ask for the shape. Enforce it.

Definition

Structured outputs make the model's response conform to a JSON Schema you supply (response_format={"type": "json_schema", "json_schema": {..., "strict": true}}). The service uses constrained decoding: at each step, tokens that would break the schema can't be chosen. In Python you usually write the schema as a Pydantic model and let the SDK convert it.

In plain words

JSON mode was "please use these boxes". Structured outputs is a form where the model physically can't write outside the boxes, can't skip one, and can only tick the options you printed.

Imagine this

A paper form versus an online form. On paper, people write "N/A", skip boxes and add notes in the margin. An online form has required fields, drop-down lists and a date picker, so every submission arrives in the same shape. It still can't stop someone choosing the wrong option from the list.

The rules strict mode insists on

  • Every field is required. "Optional" means may be null: write Optional[str] and the schema becomes "anyOf": [string, null]. The SDK marks every property required for you.
  • No extra keys: every object gets "additionalProperties": false.
  • Root is an object, not a list or anyOf. Wrap lists: {"items": [...]}.
  • Supported types: string, number, integer, boolean, object, array, enum, anyOf; nested models and $defs work, recursion too.
  • Limits on Azure OpenAI: up to 100 properties in total and 5 levels of nesting.

Support differs by provider and changes over time (OpenAI's own API accepts more keywords than Azure documents). Design for the strictest target and check the Azure structured outputs documentation for your model.

Descriptions are prompts

Field descriptions travel inside the schema and the model reads them. Field(description="Like RR-12345. Null if not given. Never invent one.") is an instruction exactly where it's needed. Write them as carefully as your system prompt.

In the real world
In finance

Banks extract the same fields again and again: payee, amount, currency, date and reference from payment instructions; borrower, income and employer from loan applications; counterparty and notional from trade confirmations. A strict schema per document type, with enums for currencies and categories and null for anything missing, turns those extractions into data a controls team can test. Amounts should be numbers in a stated currency, never strings with symbols.

Extraction services (invoices, insurance claims, CVs, support tickets) define one Pydantic model per document type and share it between the model call, the API response and the database layer. When the business adds a field, one class changes and the schema, the docs and the validation all follow.

Traditional developer view

"I'll describe the JSON in the prompt and write a validator for the replies."

GenAI developer view

"I'll define the shape once as a type. The API enforces the shape, and my validators only deal with business rules the schema can't express."

Common trap

Believing a schema makes answers correct. It guarantees customer_id is a string or null; it can't stop the model inventing "RR-12345". Shape is enforced; truth is not. That's topic 6.

Interview cue

"Structured outputs use constrained decoding against a strict JSON Schema: required fields, no extra properties, enums enforced. I define it with Pydantic, handle refusal, keep unsupported keywords like pattern out of the schema and enforce them in validators."

Open alternative · a schema-shaped answer from Claude

      

        
A dependable way to get schema-shaped data from Claude is to define a tool whose input_schema is your schema and require Claude to use it. The "tool call" is your structured answer; you never run anything.


import openai
from claude_llm import client, CLAUDE_MODEL, FALLBACK
from lab04_03_schema import SYSTEM, Triage
from lab04_02_json_mode import MESSAGES

record = {"name": "record_triage", "description": "Record the triage result.",
          "input_schema": openai.pydantic_function_tool(Triage)["function"]["parameters"]}

for text in MESSAGES:
    msg = client.beta.messages.create(
        model=CLAUDE_MODEL, max_tokens=1000, system=SYSTEM, tools=[record],
        tool_choice={"type": "tool", "name": "record_triage"},      # must answer through the tool
        messages=[{"role": "user", "content": text}], **FALLBACK)
    data = next(b.input for b in msg.content if b.type == "tool_use")
    t = Triage.model_validate(data)                                 # validate anyway
    print(f"{t.category:<10} urgent={t.urgent!s:<5} id={t.customer_id}  {t.summary}")

Goal: have your assistant design a nested schema for business-banking enquiries from companies, and check it against strict-mode rules before any model sees it.

    
    
      
  1. Ask AI
    Design business_enquiry.py
    
        
    Create business_enquiry.py with Pydantic v2 models for extracting a company's business-banking
enquiry from an email, for use with OpenAI/Azure strict structured outputs.

Models:
- Contact: name, company, email (each may be null)
- ProductRequest: product_type (one of "business_checking", "business_savings", "business_card",
  "business_loan", "other"), amount_usd (int or null), cards_needed (int or null)
- BusinessEnquiry (root): contact, requests (list of ProductRequest), annual_revenue_usd
  (int or null), wants_relationship_manager (bool), decision_deadline (string YYYY-MM-DD or null)

Rules:
- Every field is required; use Optional[...] for "may be null". Give each field a description.
- Do NOT use pattern, max_length, ge/le, EmailStr or date types: Azure strict mode rejects them.
  Enforce these with @field_validator instead: email looks like an address, amount_usd between
  1 and 5,000,000, cards_needed between 1 and 500, decision_deadline matches YYYY-MM-DD.
- Don't create or change any other file.
    
        
    Why this prompt works: it names every field and type, states the strict-mode rules (required fields, nullable via Optional), lists the keywords to avoid and where those rules should go instead, and fences the change to one file. Without the middle rule, assistants reach straight for EmailStr and Field(ge=1).

3
Check
Schemas.



  
1. In strict mode, how do you express "this field may be missing"?
You don't make it missing; you make it nullable. The field stays required and its type is anyOf [type, null] (in Pydantic, Optional[...]).

  
2. Your Pydantic model has Field(pattern=r"^RR-\d{5}$") and Azure rejects the request. Fix?
Remove pattern from the schema and enforce the format in a @field_validator. Put the format in the field's description so the model knows it too.

  
3. message.parsed is None. What happened?
Most likely a refusal: check message.refusal. (A cut-off reply raises LengthFinishReasonError instead; topic 7.)




Takeaway
Let the API enforce the shape; keep the schema to what strict mode supports; push every other rule into validators.
