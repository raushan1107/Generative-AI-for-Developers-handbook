Checklist before your model touches your app

  • Output that code reads is structured, never parsed from prose (Drill 04.1).
  • JSON mode is only a fallback, always with validation (Drill 04.2).
  • Schemas are Pydantic models, strict-mode compatible, linted and tested (Drills 04.3, 04.4).
  • Every tool has a precise description, a strict schema and validated arguments (Drills 04.5, 04.6).
  • Tools run through a dispatcher in a bounded loop; errors go back to the model as data (Drill 04.7).
  • Identity comes from the session; no tool parameter chooses whose data is read (Drill 04.8).
  • Business rules live in validators; facts are cross-checked against your systems (Drill 04.9).
  • Every failure mode has a name, a bounded policy and a counter (Drill 04.10).

Self-check

1. JSON mode, structured outputs, validators: what does each one guarantee?

JSON mode: valid syntax. Structured outputs: the reply matches the schema (keys, types, enums). Validators: your business rules. None of them guarantees the values are true; that takes checks against your systems.

2. Azure rejects your schema because of maxLength. What do you do with the rule?

Move it to a Pydantic @field_validator, and mention it in the field description so the model aims for it. The schema keeps only what strict mode supports.

3. Walk through one function call, message by message.

User message + tool definitions → assistant message with tool_calls (name + JSON arguments) → your code validates and runs the function → append the assistant message and a tool message with the result and the matching tool_call_id → the model answers using the result.

4. A teammate adds get_customer_profile(customer_id) as a tool "for flexibility". Your review comment?

Remove customer_id from the parameters. Take identity from the authenticated session in the tool's context, or any user can ask the model for anyone's profile.

5. A structured call fails. When do you retry, and when not?

Retry truncation (with more tokens) and invalid or rule-breaking output (once, with the error). Don't retry refusals or content-filter blocks; respond safely and log them.

6. Why does RR Finance Assist keep only the final answer in history, not the tool messages?

To keep every later request small and cheap; the final answer already contains what the customer was told. The trade-off: the model can't re-read raw tool results in later turns, so it calls the tool again if it needs fresh data, which is usually what you want anyway.
