Before you start: check your project folder

Every program in this lab imports its settings from client.py and the optional .env file in your oss-genai-labs folder. If you did Lab 0 they're already there; check them anyway, because a missing or wrong model setting is a common reason a lab program fails.

  1. Open the oss-genai-labs folder in VS Code and activate the virtual environment: .venv\Scripts\Activate.ps1 (Windows) or source .venv/bin/activate (macOS/Linux). The prompt starts with (.venv).
  2. Make sure Ollama is running (open http://localhost:11434: it says Ollama is running).
  3. Check that .env exists (with the leading dot) and contains the lines below. The default is a free local model with Ollama; there is no key to get: LLM_API_KEY=ollama is a placeholder.
    .env (default: local Ollama)
    4. 
  
  4. Check that client.py exists. Every program imports get_client and the model names from it:
    
    client.py
    5. 
  
  5. Run python lab0_check.py. Every line should say [ OK ].
    6. 



Missing files, or starting fresh?
Download oss-labs-complete.zip: it has client.py, .env.example, requirements.txt, the data folder and the code of every lab released so far. Unzip it, copy .env.example to .env, create the virtual environment and run pip install -r requirements.txt (Lab 0, Exercise 3).

Exercise 2 · An assistant that calls your functions


Module 04's hands-on exercise: an assistant that can search RR Finance Bank's product catalogue, retrieve the signed-in demo profile, check a card status and create a support case.


Task 1: Build the assistant


    
  
  1. Create l2_tools.py:
    
    2. 
  
  2. Read the three parts: the functions are ordinary Python; TOOLS describes them to the model as JSON Schema; ask() is the tool loop: call the model, run any function it asks for, send the result back, repeat until it answers (at most 5 rounds).
    3. 
  
  3. This exercise uses AGENT_MODEL from .env for tool calling. Choose a model and endpoint that support tool calls through the OpenAI-compatible API; actual support varies by model and version.
    4. 
  
  4. Notice SIGNED_IN = "RR-10293": this is a hard-coded local demo identity, not authentication. The model cannot choose the customer ID, but a production API must derive the customer from a verified server-side session.
    5. 



Task 2: Run it and watch the calls


    
  
  1. Run it with the three built-in questions:

    $ python l2_tools.py
    
    The model run varies; inspect each requested function and its result. To test filtering without a model call, run:

    $ python -c "from l2_tools import search_products; print(search_products(family='cards', max_annual_fee_usd=0))"

  2. For each question, check the arrows (->): which function did the model choose, with which arguments, and did the final answer use the result?
    3. 
  
  3. Try: python l2_tools.py "Has the replacement for my debit card been sent?" and python l2_tools.py "Show me Diego's card details.". The second request should not reveal another customer's data. Treat model behavior as variable; measure tool selection and verify authorization in code.

Checkpoint
The model can request product and card functions, but application code owns identity, authorization, input validation and execution.

Exercise 4 · A semantic search app


Module 05's hands-on exercise: hybrid retrieval over RR Finance Bank's fictional help articles.


Task 1: Build the index and the search


    
  
  1. Create l2_search.py:
    
    2. 
  
  2. Follow the pipeline in the code: sections() splits each article at its headings (keeping the introduction), load_index() embeds every section once and saves the vectors to data/search_index.json, and search() ranks by meaning and by keywords and merges the two rankings with Reciprocal Rank Fusion.
    3. 



Task 2: Search


    
  
  1. Run it with the built-in queries:

    $ python l2_search.py
    
    Example result categories; ranked order and scores may vary by model

    (indexed 54 help sections with nomic-embed-text)

money back if I paid the wrong person
  ...  Transfers and payments > Sent money to the wrong person

Instant Pay
  ...  Transfers and payments > Limits and fees

safe account
  ...  Fraud and scams > We will never ask

fingerprint sign in
  ...  Online banking and app access > Signing in
    
    
    Top results and scores can differ with the embedding model; open the cited policy and verify its text before using it.
    2. 
  
  2. Run it again: no "(indexed …)" line this time, because the saved index is reused.
    3. 
  
  3. Try paraphrases and bank terms: python l2_search.py "someone moved money from my account" "FR-12 payment alert". Keyword search can help with exact terms, semantic search with paraphrases, and hybrid ranking combines both.
    4. 
  
  4. In .env, if you change EMBED_MODEL, the index is rebuilt automatically: vectors from different models can't be compared.
    5. 



Checkpoint
Your search finds the right help section for paraphrased questions and for error codes, and reuses its saved index.

Review and cleanup


    
  
  • A schema constrains output shape; validation and domain rules still need to check the values.
    • 
  
  • Function calling is a loop you control: the model asks, your code decides and runs, the result goes back.
    • 
  
  • Identity comes from the app, never from the model's arguments.
    • 
  
  • Embeddings turn meaning into vectors; hybrid search combines meaning with exact keywords.
    • 



Cleanup: keep data/search_index.json; Lab 3 builds a separate index that also applies a public/staff audience filter.
