Multi-Step Tasks

"Move me to the next date, tell me the fee, and when will my lab open?" is four or five steps, and each needs the previous one's result: the enrolment ID, then the course ID, then dates and the fee, then the move. You'll run it through the agent, read the trace step by step, and see what the model got right, what it skipped, and what it cost.

1

Learn

Each step feeds the next; every step costs.

Definition

A multi-step task is a request whose answer needs several tool calls, where later calls depend on earlier results (an ID found in step 1 is an argument in step 3). Handling one well means decomposing the request, carrying results forward, staying within budgets (steps, tokens, time), recording a trace, and reporting partial success honestly.

In plain words

Break the request into steps, use what each step found in the next one, stop before it gets too long or expensive, keep a log, and say clearly what got done and what didn't.

Imagine this

Running errands with a list: pick up the parcel (you need the slip number from your email), then return the item in it, then buy the replacement with the refund. If the shop is closed, you come home and say "parcel collected, return done, replacement still to buy", not "all done".

What to control

ConcernControl
Runaway loopsA step budget (max_steps) and a clear message when it's hit
CostCount model calls and tokens per run; every step re-sends the growing conversation
LatencyStream progress ("Checking your enrolments…"); run independent reads in parallel where the API allows
Context growthKeep tool results small; drop or summarise old observations in long runs
Partial successReport what was done from the trace and audit log, and what's pending or failed
DebuggingA trace per run: step, tool, arguments, result, time, status
In the real world

Observability tools for agents (for example tracing in Microsoft Foundry, or OpenTelemetry-based tracing) show each run as a tree of model calls and tool calls with tokens and timings, because "the agent was slow and expensive yesterday" is unanswerable without them. Teams set budgets per request type and alert when runs regularly hit them, which usually means a tool is missing or badly described.

Traditional developer view

"A request is one transaction; it succeeds or fails."

GenAI developer view

"A request is a run of dependent steps with a budget. I trace every step, count its cost, and report partial success truthfully."

Common trap

Letting the final answer summarise a run that half-failed as "All done!". Build the answer from the trace: what succeeded, what's waiting for approval, what failed and what the learner can do next.

Interview cue

"For multi-step tasks I let the model decompose and order the steps, but enforce step and token budgets in code, keep tool results small, trace every step with timing and cost, and report partial success from the trace, not from the model's summary."

Drill 07.6

A multi-step request, step by step

~20 minAzure OpenAIPython

Goal: run Diego's three-part request through the agent (approvals granted automatically here; topic 7 makes them real), read the trace, and check the result against the audit log.

  1. Run

    The request and its trace

    """Drill 07.6: one request, several dependent steps. Watch the trace: each step uses what the
previous ones found (enrolment id -> course id -> dates and fee -> the move).
Run:  python lab07_06_multi_step.py"""
import desk
from agent import Agent, print_step
from desk_tools import SYSTEM, WRITE_TOOLS, kit
from llm import MODEL, get_client

REQUEST = ("I'm Diego. I can't make my AZ-104 class this week. Please move me to the next available date, "
           "tell me what it costs, and tell me when my lab will open.")

agent = Agent(get_client(), MODEL, kit, SYSTEM, max_steps=8, write_tools=WRITE_TOOLS,
              approve=lambda name, arguments, context: (True, "demo"), on_step=print_step)
print("TRACE")
result = agent.run(REQUEST, {"learner": "L-DIEGO"})
print(f"\nANSWER: {result.answer}")
print(f"stopped: {result.stopped or 'no, finished'} · model calls: {result.llm_calls} · tokens: {result.tokens}")
print("changes:", desk.ACTIONS or "none")

  2. Think

    Audit the run

    1. Follow the arguments: where did each ID and date in the trace come from?
    2. Compare the answer with the audit log ("changes"). Does the answer claim anything the log doesn't show?
    3. How many model calls did this one request take, and roughly how many tokens? What would you do if most requests looked like this?
    Compare with my answers
    1. In a good run, every ID and date in an argument appears in an earlier tool result (TC-20877 and C110 from my_enrolments; the new date from upcoming_sessions). Any value that appears from nowhere is a guess, and the tools reject guesses about identity.
    2. Only the log is evidence. If the answer mentions a fee or date that no tool returned, or a change that isn't in the log, that's exactly the hallucinated action from Drill 07.1, now inside an agent.
    3. Each step is a model call that re-sends the whole conversation, so tokens grow quickly. For a common request type, consider a workflow (topic 4), smaller tool results, or a faster model for routine steps (Module 11).
  3. Your prompt

    Write the answer from the trace

    Make the final report trustworthy: build a short "what happened" summary in code from the steps, and show it under the model's answer.

    Goal: add summarise(result: RunResult) -> str to #file:agent.py
Context: each Step has tool, arguments, result (JSON text) and status
Constraints: one line per write step ...; pending/rejected/failed ...; no model call
Done when: lab07_06_multi_step.py prints it after ANSWER, and a test in #file:test_agent.py ...

    Hint: only write tools matter for "what changed". For each, report status and the key fields from its JSON result (new date, fee, lab end date); for rejected or failed ones, say so. Read tools can be counted, not listed.

FakeLLM: an approved extend_lab produces a line starting "✓ extend_lab".
3

Check

Multi-step tasks.

1. Why does each extra step cost more than the one before?

Every model call re-sends the system prompt, the tools and the whole conversation so far, including all previous tool results, so input tokens grow with each step.

2. The agent hits its step budget after moving the date but before checking the lab. What should the learner see?

The truth from the trace: the date was moved (with the fee), the lab check didn't complete, and a next step (ask again, or a ticket). Never a generic success or a generic failure.

3. How do you tell whether an argument was guessed?

Check whether the value appears in an earlier tool result or in the user's message. Values from nowhere are guesses; identity-bearing ones are rejected by the tools, which is why identity checks live in code.

Takeaway

Multi-step tasks are runs: dependent steps, a budget, a trace, and an honest report of what changed, built from the log rather than from the model's summary.
