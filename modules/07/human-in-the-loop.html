Human-in-the-Loop Workflows

The safest agent proposes and a person decides. But an approval is only as good as what the person is shown: "approve extend_lab({...})?" teaches people to click yes. Show the real effect, computed by code ("lab open until 16 Oct becomes 23 Oct, free"), and make sure that exactly what was approved is what runs. You'll decline once and approve once, and check the audit log both times.

1

Learn

The model proposes; a person decides; code executes.

Definition

A human-in-the-loop (HITL) workflow pauses an agent before selected actions and asks a person to approve, reject or edit them. A sound design shows the action's real effect, freezes the approved arguments, executes only after approval (in code, not by the model), expires stale requests, accepts one decision per request, and records who decided what.

In plain words

Before anything changes, show the person exactly what will happen and let them say yes or no. Then do exactly that, once, and write it down.

Imagine this

Paying by card in a shop. The terminal shows the exact amount and merchant; you confirm with your PIN; the charge is what was on the screen, not what the cashier types afterwards; if you walk away, the request times out; and the receipt is your record. Agents need the same ritual.

Rules that make approval meaningful

RuleWhat goes wrong without it
Preview computed by code from current dataThe model describes "$50" as "a small fee", or gets the date wrong
Arguments frozen at proposal timeThe model changes the date after the person approved
Re-check rules at executionThe fee changed overnight; the approved price is no longer the real one
ExpiryA week-old "yes" executes in a different situation
One decision per proposal; idempotent executionA double-click or retry moves the booking twice
Only the right person can decideAnother user, or the model itself, approves it
Declines are told to the modelThe agent proposes the same thing again, or claims it happened
Audit logNo answer to "who approved this?"
In the real world

Coding agents ask before running shell commands or editing files outside the workspace, and let you allow-list safe commands so approvals stay meaningful. Expense and procurement agents prepare a purchase and route it to the budget holder. Support agents issue small goodwill credits on their own but escalate refunds above a limit to a person, mirroring the approval table in TrainCrest's internal wiki from Module 06. Too many approval prompts and people click yes without reading; place them where the risk is.

Traditional developer view

"Confirmation dialogs are UX polish."

GenAI developer view

"Approval is a security control between a probabilistic decision and a real change: computed preview, frozen arguments, expiry, one decision, re-check, idempotent execution, audit."

Common trap

Letting the model execute after "the user said yes" in chat. A message saying "yes" can be ambiguous, injected or about something else. Approval should be an out-of-band, structured decision (a button, a signed request) bound to one proposal id.

Interview cue

"I classify actions by risk: reads run freely, reversible self-service changes need the user's approval, money and exceptions go to staff. Approvals show a code-computed preview, bind to a frozen proposal with an expiry, and execution re-checks rules, runs idempotently and is logged."

2

Do

Decline once, approve once, read the log.

Drill 07.7

Approve or decline: the learner decides

~15 minAzure OpenAIPython

Goal: run Mei's lab-extension request with a real approval step: see the preview code computes, decline it and confirm nothing changed, then approve it and confirm exactly one change.

  1. Run

    The approver

    """Drill 07.7: human in the loop. Write tools pause the agent and show the learner exactly what
will happen (computed by code), and nothing changes unless they say yes.
Run:  python lab07_07_approval.py          (you answer y/n)
      python lab07_07_approval.py --no     (decline automatically, for a scripted demo)"""
import sys

import desk
from agent import Agent, print_step
from desk_tools import SYSTEM, WRITE_TOOLS, kit, preview
from llm import MODEL, get_client


def ask_learner(name, arguments, context):
    print(f"\n  APPROVAL NEEDED: {preview(name, arguments, context)}")
    if "--no" in sys.argv or "--yes" in sys.argv:
        answer = "y" if "--yes" in sys.argv else "n"
        print(f"  Approve? [y/n] {answer}")
    else:
        answer = input("  Approve? [y/n] ").strip().lower()
    return (answer == "y", "approved" if answer == "y" else "the learner said no")


before = desk.lab_status("L-MEI", "TC-10293")["lab_until"]
agent = Agent(get_client(), MODEL, kit, SYSTEM, write_tools=WRITE_TOOLS, approve=ask_learner, on_step=print_step)
result = agent.run("Please extend my AI-102 lab.", {"learner": "L-MEI"})
print(f"\nANSWER: {result.answer}")
print(f"lab open until: {before} -> {desk.lab_status('L-MEI', 'TC-10293')['lab_until']}")
print("audit log:", desk.ACTIONS or "no changes")

    The preview comes from preview() in desk_tools.py: it reads the current lab date from the system, so the person sees facts, not the model's description. In agent.py, a declined write returns an error result to the model and never reaches desk.

  3. Think

    Where the control lives

    1. After the decline, what told the model it had been declined, and what stopped it from trying again?
    2. In this drill the approver runs inside the agent loop, so the program waits. Why doesn't that work for a web app, and what does Milestone 7 do instead?
    3. Which TrainCrest actions would you never give the agent, even with approval?
    4. In the approved run, the first approval request says "can't preview": the model had guessed an ID. What should happen instead of asking the person?
    Compare with my answers
    1. The tool result {"error": "the learner did not approve this action: ..."}, plus the system prompt rule "If they decline, don't try again". Even if the model ignored the rule, every retry would hit the approver again.
    2. A web request can't wait minutes for a click. Milestone 7 ends the turn with a stored proposal and an Approve/Decline card; a separate request executes it later. That's the pause-and-resume pattern, with the proposal as task state.
    3. Refunds and other money going out, exceptions to policy, changes to someone else's data, and anything irreversible like deleting an account. Those go to staff through a ticket (Module 06's approval limits), or stay manual.
    4. Validate first, ask second. An action that fails identity or policy checks should go straight back to the model as an error; asking a person to approve something impossible wastes their attention and trains them to click yes. (Here the tool still refused it after the "yes", so nothing broke.) Milestone 7's request_… tools check ownership and rules before a proposal ever reaches the learner.
3

Check

Human in the loop.

1. Why compute the approval preview in code instead of asking the model to describe the action?

The model can be wrong, vague or manipulated (by an injected instruction) into describing an action more favourably than it is. Code reads the real data and shows the actual effect and fee.

2. A learner approves a reschedule quoted at $0; it runs the next morning, now within 7 days of the start. What should happen?

Execution re-checks the rules, sees the fee is now $50, refuses, and asks the learner again. An approval covers the action as shown, not whatever it becomes later; the expiry also limits how stale it can be.

3. Two browser tabs click Approve on the same proposal. What prevents a double change?

One decision per proposal (the first removes it from the pending store) and idempotent execution keyed by the proposal id, so even a retry returns the first result.

Takeaway

Agents propose; people decide; code executes exactly what was approved, once, with a record. Put approvals where the risk is, and show the real effect.
