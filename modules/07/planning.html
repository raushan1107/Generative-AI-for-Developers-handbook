Reasoning and Planning

Before an agent acts, something has to decide the order: find the enrolment, then the dates, then the fee, then ask. A model can do that one step at a time, or write a whole plan first. A plan written as data can be checked by code before a single tool runs. You'll get a plan for Diego's request and let a validator check it.

1

Learn

Think about the order before you act.

Definition

Reasoning is the model working out what a request needs and in what order; planning turns that into steps. Two common patterns: ReAct (reason and act), where the model decides one step at a time from the latest observation, and plan-then-execute, where it writes a full plan first and code or the model carries it out, re-planning if a step fails.

In plain words

Either take the next sensible step and see what happens, or write the to-do list first. Both work; a written list can be checked before you start.

Imagine this

Cooking a familiar dish, you decide each step as you go (ReAct). Catering a wedding, you write the plan first (plan-then-execute), someone checks it ("you can't plate before the oven step"), and you adjust when the fish delivery is late (re-planning).

Choosing a planning style

PatternStrengthsWeaknessesUse for
ReAct (the default tool loop)Adapts to each result; simpleCan wander; no overview to check or showShort tasks, 2 to 5 steps
Plan then executeCheckable, showable, cheaper stepsPlans go stale when results surpriseLonger tasks, approvals, audit
Reasoning modelsBetter at multi-step logic, internallySlower, pricier; reasoning is hiddenHard planning; often only for the plan step
  • Reasoning happens anyway. Modern models reason before choosing a tool; reasoning models do it explicitly with a separate effort setting (Module 03's chain-of-thought topic). You don't need "think step by step" in every prompt.
  • Plans are structured output (Module 04): a list of steps with tool names, purposes and flags, which code can validate.
  • Re-planning is normal: when a step fails, give the model the plan, what's done, and the error, and ask for the rest.
In the real world
In finance

A plan checked by code is a familiar idea in finance: it's the same as a payment workflow that must pass sanctions screening before release. For an agent, checking the plan (all tools exist, writes are marked for approval, a dispute is checked before it is opened) catches mistakes before anything touches a customer's account.

Coding agents often show a plan or to-do list before editing files ("1. read the failing test, 2. fix the parser, 3. run the tests") and update it as they go, because people trust what they can follow. Travel and expense agents present the plan ("book this flight, this hotel, total $1,240") for approval before any booking. In both cases the plan is data the product can display, check and log.

Traditional developer view

"The control flow is in the code. A model just fills in text."

GenAI developer view

"The model can write the control flow at run time, as a plan I can validate: known tools, correct order, approvals marked, before anything runs."

Common trap

Executing a model's plan blindly. Plans invent tools, skip checks ("reschedule" before "reschedule_quote") or forget approvals. Validate a plan like any other untrusted input.

Interview cue

"I use a ReAct-style tool loop for short tasks, and plan-then-execute for longer or sensitive ones: the model returns a structured plan, code validates tools, order and approval flags, and the agent re-plans when a step fails."

llm.py
"""Shared helper for every drill: returns an OpenAI-compatible client for
Azure OpenAI (Microsoft Foundry), OpenAI or Ollama, chosen in .env."""
import os

from dotenv import load_dotenv
from openai import OpenAI

load_dotenv()  # reads .env from the current folder

PROVIDER = os.getenv("LLM_PROVIDER", "ollama").lower()   # default: a free local model (Ollama)


def get_client() -> OpenAI:
    if PROVIDER == "azure":
        # Azure OpenAI v1 API: the standard OpenAI client, pointed at your resource
        return OpenAI(
            base_url=os.environ["AZURE_OPENAI_BASE_URL"],
            api_key=os.environ["AZURE_OPENAI_API_KEY"],
        )
    if PROVIDER == "openai":
        return OpenAI()  # reads OPENAI_API_KEY
    if PROVIDER == "ollama":
        return OpenAI(base_url="http://localhost:11434/v1", api_key="ollama")
    raise ValueError(f"Unknown LLM_PROVIDER: {PROVIDER!r}")


# On Azure this is the DEPLOYMENT name; elsewhere it's the model name.
MODEL = {
    "azure": os.getenv("AZURE_OPENAI_DEPLOYMENT", "chat"),
    "openai": os.getenv("OPENAI_MODEL", "gpt-5.4-mini"),
    "ollama": os.getenv("OLLAMA_MODEL", "llama3.2"),
}.get(PROVIDER, "")

Plan first, then check the plan

~15 minAzure OpenAIPython · Pydantic

Goal: get a structured plan for Diego's three-part request without executing anything, and validate it in code.

  1. Run

    Plan, then validate

    """Drill 07.2: plan first, as structured output, then let code check the plan before anything runs.
Run:  python lab07_02_plan.py "I'm Mei. I was charged twice for my SkyHigh flight..." """
import sys

from pydantic import BaseModel, Field

from desk_tools import WRITE_TOOLS, kit
from llm import MODEL, get_client

REQUEST = sys.argv[1] if len(sys.argv) > 1 else (
    "I'm Mei. I was charged twice for my SkyHigh Airlines ticket on my Cashback Card. Dispute the "
    "duplicate if it's still possible, tell me when I'd get the money back, and check the card is active.")


class PlanStep(BaseModel):
    tool: str = Field(description="One of the available tool names")
    purpose: str = Field(description="Why this step is needed, in a few words")
    needs_approval: bool = Field(description="True if this step changes something for the customer")


class Plan(BaseModel):
    goal: str
    steps: list[PlanStep]
    ask_customer_first: list[str] = Field(description="Questions to ask before acting, if anything is unclear")


tools = "\n".join(f"- {t['function']['name']}: {t['function']['description']}" for t in kit.schemas())
prompt = f"""Plan how to handle this RR Finance Bank customer request with the tools below. Don't execute anything.
Order the steps so each one has the information it needs. Mark steps that change something.

Tools:
{tools}

Request: {REQUEST}"""

plan = get_client().chat.completions.parse(model=MODEL, messages=[{"role": "user", "content": prompt}],
                                            response_format=Plan).choices[0].message.parsed
print("GOAL:", plan.goal)
for n, step in enumerate(plan.steps, 1):
    print(f"  {n}. {step.tool:20} {'[needs approval] ' if step.needs_approval else ''}{step.purpose}")
for q in plan.ask_customer_first:
    print("  ask first:", q)

# Code checks the plan: the model proposes, the program disposes.
names = [s.tool for s in plan.steps]
problems = [f"unknown tool: {n}" for n in names if n not in kit.tools]
problems += [f"{s.tool} changes data but isn't marked for approval" for s in plan.steps
             if s.tool in WRITE_TOOLS and not s.needs_approval]
if "open_dispute" in names:
    before = names[:names.index("open_dispute")]
    problems += [f"open_dispute planned before {t}" for t in ("recent_transactions", "dispute_quote") if t not in before]
# Dependencies: these tools need a card or a transaction ID, which only my_cards (and then
# recent_transactions) provide.
needs_ids = [i for i, n in enumerate(names) if n not in ("my_cards", "create_case")]
if needs_ids and "my_cards" not in names[:needs_ids[0]]:
    problems.append(f"{names[needs_ids[0]]} needs a card, but my_cards isn't called before it")
problems += [f"{n} (a write) is planned more than once" for n in sorted(WRITE_TOOLS) if names.count(n) > 1]
print("\nPLAN CHECK:", "OK" if not problems else problems)

  2. Think

    Judge the plan

    1. Does the plan put the read steps before the write step? Which check in the code enforces that?
    2. Diego said "if it isn't too expensive". Where should that condition be handled: in the plan, by the model during execution, or by a person?
    3. What would you do with a plan that fails the check?
    Compare with my answers
    1. Yes: reschedule comes after reschedule_quote and upcoming_sessions, which the order check enforces. But the plan never calls my_enrolments, so it would need an enrolment ID nobody looked up, and the dependency check flags exactly that. In an earlier version of this drill, without that check, a plan with the same gap (and reschedule twice) printed "PLAN CHECK: OK". A validator only catches what you encode.
    2. By the person. "Too expensive" is Diego's judgement; the agent should find the fee and show it in the approval request (topic 7). That's why the reschedule step is marked for approval.
    3. Send the problems back to the model and ask for a corrected plan (a repair loop, as in Module 04), with a limit; or fall back to the step-by-step loop with approvals still enforced.
  3. Your prompt

    Re-plan after a failure

    Write a prompt for your assistant that adds re-planning to the script: if a (simulated) step fails, ask the model for a new plan for the remaining work.

    Goal: add a replan(plan, done_steps, error) function to #file:lab07_02_plan.py
Context: Plan and PlanStep are Pydantic models; the same validator should run on the new plan
Constraints: what the model is given ...; what it must not repeat ...; limit ...
Done when: simulating "upcoming_sessions failed: schedule service timed out" ...

    Hint: give the model the original request, the steps already done with their results, and the error, and ask for the remaining steps only. Validate the new plan with the same checks, and stop after two re-plans.

    Compare with my prompt
    In #file:lab07_02_plan.py, move the plan checks into a function check(plan) -> list[str], then add
replan(request, done, error) -> Plan. It sends the model the original request, the steps already
completed (tool + one-line result), and the error from the failed step, and asks for a Plan of the
REMAINING steps only, without repeating completed ones. Use the same parse(response_format=Plan) call.
At the end of the script, simulate: done = [my_enrolments -> TC-20877, course C110], error =
"upcoming_sessions failed: schedule service timed out"; print the new plan and check(new_plan).
Allow at most 2 re-plans. Don't change PlanStep or Plan.
3

Check

Planning.

1. What does ReAct stand for, and what does a ReAct loop look like in code?

Reason and act. In code it's the tool loop: the model reasons, calls a tool, sees the result and decides the next step, until it answers. Milestone 4's loop and agent.py are ReAct loops.

2. Give two checks you'd run on a model-written plan.

Any two: every tool exists; write steps are marked for approval; dependencies come first (quote before reschedule); the number of steps is within budget; no step uses data the plan hasn't fetched.

3. When is a separate planning call worth its cost?

For longer or sensitive tasks where a plan can be checked, shown to a person, or reused, and where a wrong first action is expensive. For a two-step look-up, the plain loop is cheaper and just as good.

Takeaway

Agents plan step by step or up front. A plan written as structured data can be validated, displayed and approved before anything runs.
