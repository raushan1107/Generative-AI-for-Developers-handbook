Agent Workflows

Not every multi-step job needs a model choosing the steps. When the path is known (classify, fetch, reply), code can follow it and use the model only where judgement or language is needed. That's a workflow: cheaper, faster, easier to test. You'll run the same three requests through a workflow and through the agent and compare.

1

Learn

Fixed paths where you can, model choices where you must.

Definition

An agent workflow (or LLM workflow) is a system in which models and tools are combined along paths defined in code. Common patterns: prompt chaining (one step's output feeds the next), routing (classify, then send to a specialised handler), parallelisation (independent steps at once), orchestrator and workers (a model splits a task, workers do the parts), and evaluator and optimiser (one model drafts, another checks, repeat). In an agent, by contrast, the model decides the path.

In plain words

If you can draw the flowchart, write it in code and let the model fill in the boxes that need language or judgement. Use a free-roaming agent only when you can't draw it.

Imagine this

A hospital's triage desk. The nurse decides which department you go to (routing); each department has its own protocol (a fixed chain); test results come back in parallel; a senior doctor reviews the junior's plan (evaluator). Only an unusual case gets a specialist who works it out from scratch: the agent.

Workflow or agent?

QuestionIf yes
Can you list the steps for this kind of request in advance?Workflow
Do the steps depend on what earlier steps discover, in ways you can't enumerate?Agent
Must every run be predictable, auditable, cheap and fast?Workflow, or an agent with tight limits
Is a wrong step costly and hard to undo?Workflow with approvals; agent only for read steps
Do requests vary widely, combining several needs in one message?Router + agent for the mixed ones
In the real world

Many "AI agents" in production are workflows with one or two model decisions: a router that classifies tickets, fixed handlers per category, a model that drafts the reply, and an evaluator check before sending. Teams start there because it's testable and cheap, then add agentic loops only for the requests the router labels "complex". Microsoft's Agent Framework and similar libraries support both graph-style workflows and free-form agents for this reason.

Traditional developer view

"Hard-code every path."

GenAI developer view

"Hard-code the paths I can predict, use a model for routing and language, and give a model the steering wheel only where the path truly varies, measuring the cost of that freedom in calls and failures."

Common trap

Building an agent for a flowchart. "Check lab status and tell the learner" is two fixed steps; an agent may take four calls, wander, or skip the check. Use the simplest pattern that works, and measure.

Interview cue

"I distinguish workflows, where code defines the path (chaining, routing, parallel, orchestrator-workers, evaluator-optimiser), from agents, where the model chooses it. I default to workflows for predictable tasks and use agents for open-ended ones, with the same tools underneath."

llm.py
"""Shared helper for every drill: returns an OpenAI-compatible client for
Azure OpenAI (Microsoft Foundry), OpenAI or Ollama, chosen in .env."""
import os

from dotenv import load_dotenv
from openai import OpenAI

load_dotenv()  # reads .env from the current folder

PROVIDER = os.getenv("LLM_PROVIDER", "ollama").lower()   # default: a free local model (Ollama)


def get_client() -> OpenAI:
    if PROVIDER == "azure":
        # Azure OpenAI v1 API: the standard OpenAI client, pointed at your resource
        return OpenAI(
            base_url=os.environ["AZURE_OPENAI_BASE_URL"],
            api_key=os.environ["AZURE_OPENAI_API_KEY"],
        )
    if PROVIDER == "openai":
        return OpenAI()  # reads OPENAI_API_KEY
    if PROVIDER == "ollama":
        return OpenAI(base_url="http://localhost:11434/v1", api_key="ollama")
    raise ValueError(f"Unknown LLM_PROVIDER: {PROVIDER!r}")


# On Azure this is the DEPLOYMENT name; elsewhere it's the model name.
MODEL = {
    "azure": os.getenv("AZURE_OPENAI_DEPLOYMENT", "chat"),
    "openai": os.getenv("OPENAI_MODEL", "gpt-5.4-mini"),
    "ollama": os.getenv("OLLAMA_MODEL", "llama3.2"),
}.get(PROVIDER, "")
Drill 07.4

Workflow vs agent: same requests, different costs

~20 minAzure OpenAIPython · Pydantic

Goal: handle three common requests with a routing workflow (one model call to classify, code for the steps, one call to write the reply) and with the agent, and compare model calls and answers.

  1. Run

    Router workflow and agent, side by side

    """Drill 07.4: a workflow vs an agent for the same requests.
Workflow: one model call routes the request into a fixed category (structured output); code runs
the steps for that category; one more call writes the reply from the facts. Predictable and cheap.
Agent: the model chooses every step. Flexible, but more calls and less predictable."""
import json
from typing import Literal, Optional

from pydantic import BaseModel

import desk
from agent import Agent
from desk_tools import SYSTEM, WRITE_TOOLS, kit
from llm import MODEL, get_client

CUSTOMER = "RR-10293"
REQUESTS = [
    "Is my Cashback Card still active?",
    "What have I spent on my Cashback Card recently?",
    "Please freeze my debit card.",
]


class Route(BaseModel):
    category: Literal["card_status", "recent_payments", "freeze_card", "other"]
    card_hint: Optional[str]


client = get_client()


def find_card(hint):
    rows = desk.my_cards(CUSTOMER)
    return next((r for r in rows if hint and hint.lower() in r["product"].lower()), rows[0])


def workflow(request):
    calls = 1
    route = client.chat.completions.parse(model=MODEL, response_format=Route, messages=[
        {"role": "system", "content": "Classify the RR Finance Bank customer request. card_hint: a word from the card "
                                      "name they mention (like 'Cashback' or 'debit'), else null."},
        {"role": "user", "content": request}]).choices[0].message.parsed
    card = find_card(route.card_hint)
    try:                                       # workflows need error handling too: systems say no
        if route.category == "card_status":
            facts = desk.card_status(CUSTOMER, card["card_last4"])
        elif route.category == "recent_payments":
            facts = {"card": card["product"], "payments": desk.recent_transactions(CUSTOMER, card["card_last4"])[:5]}
        elif route.category == "freeze_card":
            facts = desk.freeze_card(CUSTOMER, card["card_last4"])   # a real app asks for approval here (07.7)
        else:
            return route.category, calls, "I'll pass this to the support team."
    except desk.DeskError as err:
        facts = {"card": card["product"], "error": str(err)}
    reply = client.chat.completions.create(model=MODEL, messages=[
        {"role": "system", "content": "Reply to the customer in one or two sentences using only these facts."},
        {"role": "user", "content": f"Request: {request}\nFacts: {json.dumps(facts)}"}]).choices[0].message.content
    return route.category, calls + 1, reply.strip()


agent = Agent(client, MODEL, kit, SYSTEM, write_tools=WRITE_TOOLS, approve=lambda *a: (True, "demo"))
for request in REQUESTS:
    desk.reset()
    category, w_calls, w_reply = workflow(request)
    desk.reset()
    result = agent.run(request, {"customer": CUSTOMER})
    print(f"{request}\n  workflow [{category}, {w_calls} model calls]: {w_reply}")
    print(f"  agent    [{len(result.steps)} tool steps, {result.llm_calls} model calls]: {result.answer}\n")

  2. Think

    Compare

    1. How many model calls did each approach use per request? What would that mean at 25,000 requests a month?
    2. Check the categories the router chose. Which requests were misrouted, and what did the workflow then tell the learner?
    3. For "Please extend my AI-102 lab", compare both answers with what was actually done. Who told the truth?
    4. How would you make the router reliable?
    Compare with my answers
    1. The workflow always uses exactly two; the agent used two to four. At volume, that difference multiplies your model bill and latency, which is why routers handle the common cases, but only if they route correctly.
    2. "Next dates for my RAG course" went to extend_lab (the system refused, and the reply invented that dates "haven't been scheduled"), and "extend my lab" went to lab_status. A workflow fails silently when the router is wrong: every later step runs perfectly on the wrong path.
    3. Neither. The workflow only read the status, yet its reply says the extension "has been processed"; the agent looked things up and then announced a new end date without calling extend_lab. Both prove the rule from topic 1: confirmations must come from code and logs, never from a model's sentence about what happened.
    4. Describe each category in the router prompt (with an example per category), add an "unclear" category that falls back to the agent or a person, evaluate the router on a labelled set of real requests (Module 09), and add the approval step before extend_lab so a misroute can't change anything on its own.

Stretch: add an evaluator step to the workflow: after the reply is written, check in code that every date in the reply appears in the facts, and regenerate once if not.

3

Check

Workflows.

1. Name the five workflow patterns and one use of each.

Chaining (draft then polish), routing (send each ticket category to its handler), parallel (fetch lab and voucher status at once), orchestrator-workers (split a long research task), evaluator-optimiser (check a reply against rules and revise).

2. Is Milestone 6's /api/ask a workflow or an agent?

A workflow: a fixed chain (retrieve, then maybe generate, then check). The chat's search_help tool is agentic: the model decides when and how often to search.

3. Your router sends 85% of requests to fixed handlers and 15% to an agent. Why is that a good design?

Most traffic gets the cheap, fast, predictable path; the agent's extra cost and risk are spent only where flexibility is needed, and both share the same tools and guard rails.

Takeaway

If you can draw the flowchart, build a workflow. Give the model the steering wheel only where the path really varies.
