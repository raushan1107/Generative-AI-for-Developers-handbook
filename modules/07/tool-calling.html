Tool Calling for Agents

In Module 04 you called tools once per question. An agent calls them again and again, choosing among many, and reads their errors to decide what to do next. That makes tool design the main way you shape an agent's behaviour. You'll give a model the same functions twice, once with terse names and once with good descriptions, and count how often it picks the right one.

1

Learn

Tools are the agent's user interface.

Definition

In an agent, tool calling is how the model takes each step: it chooses a tool from a set by reading the tools' names, descriptions and parameter schemas, sends arguments, and reads the result or error as an observation for its next decision. Tools are either read (look-ups, safe to repeat) or write (change state, need care).

In plain words

The model only knows your tools from how you describe them. Describe them for a reader who has never seen your codebase, and make errors say what to do next.

Imagine this

A toolbox for a temporary worker. Labelled drawers ("torque wrench, 10 to 50 Nm, for wheel nuts") get the right tool used; drawers marked "misc 2" get guesses. And when a bolt won't turn, a note saying "left-hand thread, turn clockwise" beats a red light.

Design rules for agent tools

RuleWhyIn desk_tools.py
Names say what happens: verb + objectThe name is read firstextend_lab, reschedule_quote, not ext, quote
Descriptions say when to use it, and what to call firstEncodes the workflow without a fixed flow"Call reschedule_quote first."
Parameters have descriptions and examplesFewer malformed arguments"Enrolment ID like TC-12345, from my_enrolments"
Small, focused tools; separate reads from writesReads can run freely; writes get approvals and idempotencyQuote (read) and reschedule (write) are separate
Errors are observations with a next stepThe model recovers instead of looping or giving upactionable() returns the system's message
Identity never comes from the modelA prompt can't make the agent act as someone elsecontext["learner"], set by the app
Return what's needed, not everythingEvery result is tokens in the next callEnrolment rows have 5 fields, not the whole record
Keep the tool count modestChoice gets harder with dozens of similar tools7 tools; group or route when you have many more
In the real world

Teams that wrap an existing internal API for an agent usually start by exposing its endpoints one-to-one, and the agent struggles: cryptic names, dozens of parameters, error codes like E4012. The fix that works is a thin "agent-facing" layer: fewer, task-shaped tools, descriptions written for the model, and errors translated into sentences. The Model Context Protocol (MCP) has made this layer reusable across assistants, but the design rules are the same.

Traditional developer view

"An API is documented for developers; the code that calls it is fixed."

GenAI developer view

"A tool is documented for a model that decides at run time. Its name, description, parameters and error messages are part of the prompt, and I measure how well the model chooses."

Common trap

Swallowing errors into "tool failed". The model then retries the same call, guesses, or tells the user something vague. Return the reason and the next sensible step, without internal details like stack traces or other users' data.

Interview cue

"I design agent tools like a UI for the model: verb-object names, descriptions that say when to use them and what comes first, typed parameters with examples, read and write tools separated, identity from the session, and errors returned as actionable observations."

llm.py
"""Shared helper for every drill: returns an OpenAI-compatible client for
Azure OpenAI (Microsoft Foundry), OpenAI or Ollama, chosen in .env."""
import os

from dotenv import load_dotenv
from openai import OpenAI

load_dotenv()  # reads .env from the current folder

PROVIDER = os.getenv("LLM_PROVIDER", "ollama").lower()   # default: a free local model (Ollama)


def get_client() -> OpenAI:
    if PROVIDER == "azure":
        # Azure OpenAI v1 API: the standard OpenAI client, pointed at your resource
        return OpenAI(
            base_url=os.environ["AZURE_OPENAI_BASE_URL"],
            api_key=os.environ["AZURE_OPENAI_API_KEY"],
        )
    if PROVIDER == "openai":
        return OpenAI()  # reads OPENAI_API_KEY
    if PROVIDER == "ollama":
        return OpenAI(base_url="http://localhost:11434/v1", api_key="ollama")
    raise ValueError(f"Unknown LLM_PROVIDER: {PROVIDER!r}")


# On Azure this is the DEPLOYMENT name; elsewhere it's the model name.
MODEL = {
    "azure": os.getenv("AZURE_OPENAI_DEPLOYMENT", "chat"),
    "openai": os.getenv("OPENAI_MODEL", "gpt-5.4-mini"),
    "ollama": os.getenv("OLLAMA_MODEL", "llama3.2"),
}.get(PROVIDER, "")
Drill 07.3

Tool design decides tool choice

~20 minAzure OpenAIPython

Goal: measure how often a model picks the right first tool for 8 requests when the tools are terse and when they're written for a model to read.

  1. Run

    Terse vs clear tools

    """Drill 07.3: tool design decides tool choice. The same 8 requests, two tool sets with the same
functions: one with terse names and no descriptions, one written for a model to read.
Count how often the model's first call is the right tool."""
from desk import TODAY
from desk_tools import kit
from llm import MODEL, get_client
from llm_tools import TOOL_EXTRAS

CLEAR = kit.schemas()
TERSE_NAMES = {"my_cards": "crd", "card_status": "cst", "recent_transactions": "txn", "dispute_quote": "dq",
               "freeze_card": "frz", "open_dispute": "dsp", "create_case": "cs"}


def terse(tool):
    """Same function, written the way many internal APIs are: short names, no descriptions."""
    f = tool["function"]
    params = {"type": "object", "properties": {f"p{i}": {"type": "string"} for i in range(len(f["parameters"]["properties"]))},
              "required": [f"p{i}" for i in range(len(f["parameters"]["properties"]))], "additionalProperties": False}
    return {"type": "function", "function": {"name": TERSE_NAMES[f["name"]], "description": "", "parameters": params}}


TERSE = [terse(t) for t in CLEAR]
REQUESTS = [
    ("Is my card ending 4821 active or frozen?", "card_status"),
    ("Show me the recent payments on my card ending 4821.", "recent_transactions"),
    ("Can I still dispute payment TX-1006, and when would I get the money?", "dispute_quote"),
    ("Freeze my card ending 1177 right now.", "freeze_card"),
    ("Open a dispute for TX-1002, I was charged twice.", "open_dispute"),
    ("Which cards do I have?", "my_cards"),
    ("I want to complain about how a branch employee treated me.", "create_case"),
    ("Has my debit card ending 1177 been frozen?", "card_status"),
]
client = get_client()
system = f"You act for an RR Finance Bank customer. Today is {TODAY}. Call exactly one tool for the request."

for label, tools, names in (("terse", TERSE, TERSE_NAMES), ("clear", CLEAR, {k: k for k in TERSE_NAMES})):
    right = 0
    for request, expected in REQUESTS:
        msg = client.chat.completions.create(
            model=MODEL, tools=tools, parallel_tool_calls=False, **TOOL_EXTRAS,
            messages=[{"role": "system", "content": system}, {"role": "user", "content": request}]).choices[0].message
        got = msg.tool_calls[0].function.name if msg.tool_calls else "(no tool)"
        ok = got == names[expected]
        right += ok
        print(f"  [{label}] {'✓' if ok else '✗'} {request[:52]:52} -> {got}")
    print(f"{label.upper()} tools: {right}/{len(REQUESTS)} right first call\n")

  2. Think

    Read the misses

    1. Look at the terse misses. Which of them would have been dangerous if the tools had run?
    2. "Is my sandbox still running?" never says "lab". How did the clear tool set still get it right?
    3. With clear tools, llama3.2 made no call at all for two requests. Is "no tool" always wrong?
    Compare with my answers
    1. "Can I still move…?" went to move and "I want to complain about my trainer" went to ext: two write tools, for requests that should only read or raise a ticket. Short names carry almost no meaning, so the model matches surface words ("move") or guesses. Without approvals, a vague tool set turns a question into a booking change.
    2. The description of lab_status ("Lab access for one enrolment: open until which date…") lets the model connect "sandbox" and "still running" to lab access, as embeddings connected paraphrases in Module 05.
    3. Here it was wrong (both requests need facts or an action), but not always: greetings and general questions need no tool. A strict scorer counts only the ideal first step, so read each miss before "fixing" a description, and compare models: the same clear tools got 8/8 with qwen2.5:7b.
  3. Ask AI

    Improve one description, then re-measure

    With llama3.2, "Can I still move TC-20877, and how much would it cost?" got no tool call even with clear tools. Target that miss:

    In #file:desk_tools.py, improve only the docstring of reschedule_quote so that a request like
"Can I still move TC-20877, and how much would it cost?" clearly maps to it: say it answers
"can I move and what does it cost" questions, needs only the enrolment ID, and changes nothing.
Keep it under 30 words. Don't change any code or other docstrings.
    Why this prompt works: it targets one measured failure, gives the wording learners actually use, adds the reassuring fact the model needs ("changes nothing", so it's safe to call), and limits the change so the next run measures only this edit.

    Run the drill again and compare the clear-tools score. Keep the change only if it helps without breaking another request.

3

Check

Tool design.

1. Why separate reschedule_quote from reschedule instead of one tool with a confirm flag?

Reads and writes need different treatment: the quote can run any time; the change needs approval and idempotency. Separate tools let code apply those rules by tool name, and the model can't flip a flag to skip the check.

2. A tool returns {"error": "E4012"}. What should it return instead?

A sentence with the cause and a next step, for example "2026-10-29 is no longer available; use upcoming_sessions to see current dates". No stack traces or internal ids.

3. Your agent has 60 tools and picks the wrong one often. Two remedies?

Group them into fewer task-shaped tools; route first (a classifier or workflow picks a tool subset per request) so the model chooses among a handful; and improve descriptions, measuring choice accuracy as in this drill.

Takeaway

Agents choose tools by reading them. Clear names, descriptions, parameters and error messages are the cheapest way to make an agent better.
