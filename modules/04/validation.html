Validating Model Outputs

Structured outputs guarantee the shape. They can't tell an invented enrolment ID from a real one, a past date from a future one, or a refund the policy allows from one the model made up. Those checks are yours. This page sorts them into three layers and gives each one a home in your code.

1

Learn

Trust the shape. Check everything else.

Definition

Output validation checks model output before your application relies on it: that it has the expected shape (schema), obeys business rules (formats, ranges, dependencies between fields), and agrees with facts from your systems (IDs that exist, amounts your code calculated). Invalid output is rejected, repaired, retried or escalated, never silently used.

In plain words

Treat model output like a form submitted by a stranger on the internet: well formatted, probably honest, and checked anyway.

Imagine this

Airport security has layers. The airline checks your ticket has the right format. The gate checks the date and flight match today. Passport control checks the photo matches you. A perfect-looking ticket for yesterday's flight passes the first check and fails the second. Each layer catches what the one before can't.

Where each check lives

CheckLayerHow

preferred_date is in the next 12 monthsRules@field_validator using today's date

"$745 refund" matches the policy quoteFactsCompare amounts in the answer with tool results

When validation fails

  • Tool arguments: return the validation message as the tool result ({"error": "invalid arguments: enrolment_id: must look like TC-12345"}). The model usually fixes it, or asks the learner, on the next round.
  • Structured replies: retry once with the error (Milestone 3's repair idea), then fall back to a safe default or a "couldn't process" response.
  • Facts in the final answer: block, regenerate, or flag for review, depending on the risk. A wrong refund amount is worth blocking; a slightly long summary isn't.
  • Always log it. A rising validation-failure rate is often the first sign a prompt, model or data change broke something (Module 09).
In the real world

Finance and insurance teams using extraction models run all three layers: schema, rules (totals add up, dates are plausible), and facts (the supplier exists in the vendor database, the policy number is active). Documents that fail go to a human queue. The validation-failure rate is a dashboard metric, just like error rates for an API.

Traditional developer view

"The schema validated, so the data is good."

GenAI developer view

"The schema means the data is well formed. Whether it's allowed and whether it's true are separate questions, answered by my validators and my systems."

Common trap

Validating at the end of the pipeline only. By then the invented ID has already been used in a lookup and the wrong amount is already in a reply. Validate at the boundary: as tool arguments arrive, and before an answer is sent.

Interview cue

"I validate in three layers: schema for shape, validators for business rules, and cross-checks against source systems for facts, at every boundary, with retry, fallback or escalation on failure, and I monitor the failure rate."

Business rules with Pydantic validators

Goal: add layer-2 rules to the arguments of a create_support_ticket tool, add one more yourself, and use a layer-3 check to catch invented dollar amounts.

  1. Run

    The model and its rules

    """Drill 04.9: validation in layers.
Layer 1, shape: the JSON Schema (strict mode guarantees it).
Layer 2, business rules: Pydantic validators in YOUR code (formats, ranges, dates).
Layer 3, facts: compare what the model says with what your systems say."""
import re
from datetime import date, timedelta
from typing import Literal, Optional

from pydantic import BaseModel, Field, field_validator, model_validator

ENROLMENT_ID = re.compile(r"TC-\d{5}")


def today() -> date:                     # a function, so tests can pretend it's another day
    return date.today()


class TicketDraft(BaseModel):
    """Arguments the model sends to create_support_ticket."""
    category: Literal["scheduling", "billing", "exam_voucher", "certificate", "lab_access", "account", "other"]
    summary: str = Field(description="One sentence for the support team")
    enrolment_id: Optional[str] = Field(description="Like TC-12345, or null")
    urgency: Literal["low", "medium", "high"]
    preferred_date: Optional[str] = Field(description="New class date the learner wants, YYYY-MM-DD, or null")

    @field_validator("enrolment_id")
    @classmethod
    def enrolment_id_format(cls, v):
        if v is not None and not ENROLMENT_ID.fullmatch(v):
            raise ValueError("enrolment_id must look like TC-12345")
        return v

    @field_validator("summary")
    @classmethod
    def summary_length(cls, v):
        v = v.strip()
        if not 10 <= len(v) <= 200:
            raise ValueError("summary must be 10 to 200 characters")
        return v

    @field_validator("preferred_date")
    @classmethod
    def date_in_next_year(cls, v):
        if v is None:
            return v
        try:
            d = date.fromisoformat(v)
        except ValueError:
            raise ValueError("preferred_date must be YYYY-MM-DD") from None
        if not today() < d <= today() + timedelta(days=365):
            raise ValueError("preferred_date must be in the future and within 365 days")
        return v

    @model_validator(mode="after")
    def scheduling_needs_an_enrolment(self):
        if self.category == "scheduling" and self.enrolment_id is None:
            raise ValueError("a scheduling ticket needs the enrolment_id; ask the learner for it")
        return self


MONEY = re.compile(r"\$\s?(\d[\d,]*(?:\.\d{2})?)")


def unsupported_amounts(answer: str, allowed: set[float]) -> list[float]:
    """Layer 3: dollar amounts in the model's answer that our systems didn't produce."""
    found = {float(m.replace(",", "")) for m in MONEY.findall(answer)}
    return sorted(found - set(allowed))

from datetime import date

import pytest
from pydantic import ValidationError

import validators
from validators import TicketDraft, unsupported_amounts

GOOD = {"category": "scheduling", "summary": "Learner wants to move AZ-104 to a later date.",
        "enrolment_id": "TC-20877", "urgency": "medium", "preferred_date": "2026-11-16"}


@pytest.fixture(autouse=True)
def fixed_today(monkeypatch):
    monkeypatch.setattr(validators, "today", lambda: date(2026, 10, 11))


def test_good_ticket_passes():
    assert TicketDraft.model_validate(GOOD).preferred_date == "2026-11-16"


@pytest.mark.parametrize("change, message", [
    ({"enrolment_id": "20877"}, "TC-12345"),
    ({"summary": "help"}, "10 to 200"),
    ({"preferred_date": "16/11/2026"}, "YYYY-MM-DD"),
    ({"preferred_date": "2026-10-01"}, "future"),
    ({"preferred_date": "2028-01-01"}, "365 days"),
    ({"enrolment_id": None}, "needs the enrolment_id"),
])
def test_business_rules(change, message):
    with pytest.raises(ValidationError) as info:
        TicketDraft.model_validate({**GOOD, **change})
    assert message in str(info.value)


def test_facts_layer_catches_invented_amounts():
    answer = "You'll get a 50% refund of $745.00, and a $50 fee applies if you reschedule."
    assert unsupported_amounts(answer, {745.0, 50.0}) == []
    assert unsupported_amounts("Good news: a full refund of $1,490!", {745.0}) == [1490.0]

    Layer 3: amounts the model made up

    Look at unsupported_amounts() and its test. Our code knows the refund quote was $745.00 and the reschedule fee is $50; any other dollar figure in the answer wasn't produced by our systems.

    • Your new test passes and the original 8 still pass.
    • unsupported_amounts("Good news: a full refund of $1,490!", {745.0}) returns [1490.0]: a figure to block or flag before the learner sees it.
    • Think about cost: layer 2 is free (pure Python); layer 3 may need lookups. Run both on anything involving money, identity or commitments.
3

Check

Validation.

1. The schema says preferred_date is a string. The model sends "next Tuesday". Which layer catches it, and how?

Layer 2: a @field_validator that parses ISO dates (date.fromisoformat) and checks the range. Return the message to the model so it can ask the learner for a date or convert it.

2. Why return validation errors to the model instead of just raising?

Because the model can often fix the problem (reformat, ask the user) on the next round. Raising ends the conversation with a generic error.

3. Name a check that no schema or validator can do on its own.

Anything needing your data: the enrolment exists and belongs to this learner, the refund amount matches the policy quote, the course is currently offered.

Takeaway

Schema for shape, validators for rules, your systems for facts. Validate at every boundary and log every failure.
