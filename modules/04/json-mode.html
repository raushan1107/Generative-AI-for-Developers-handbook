JSON Responses: JSON Mode and Its Limits

JSON mode is the first rung up the ladder: flip one switch and the reply is always valid JSON. No code fences, no 'Here you go!'. But valid JSON isn't the JSON you wanted. You'll see the keys change from message to message, fix them with the prompt, and then catch the values still lying.

1

Learn

Valid JSON is a low bar.

Definition

JSON mode (response_format={"type": "json_object"} in Chat Completions) constrains the model so its reply is a syntactically valid JSON object. It does not enforce any particular keys, types or values. The prompt must mention JSON, and you describe the wanted fields in words.

In plain words

JSON mode promises brackets, quotes and commas in the right places. It promises nothing about what's inside. You asked for enrolment_id; you might get enrollmentId, id or a nested details object.

Imagine this

You ask five colleagues to "send me the details as a spreadsheet". You get five valid spreadsheets: one has columns Name, Issue, one has Customer, Problem, Status, one put everything in cell A1. Every file opens. None of them can be merged without manual work.

Free text + "return JSON"JSON modeStructured outputs (next topic)
Always parsesNo (fences, extra text)YesYes
Exact keysOnly if the prompt is followedOnly if the prompt is followedYes
Types and allowed valuesNoNoYes
Correct valuesNoNoNo: still validate

Facts worth remembering

  • The request must mention "JSON" in a message, or the API rejects it. Describe the fields too; otherwise the model invents its own.
  • JSON mode is widely supported (Azure OpenAI, OpenAI, Ollama and most OpenAI-compatible servers), so it's a useful fallback where structured outputs aren't available.
  • If the reply is cut off by max_completion_tokens, the JSON is incomplete. Check finish_reason == "length" (topic 7).
  • Claude has no JSON-mode switch; you get the same effect with a clear prompt or, better, with a tool whose input schema is your object (shown on the next page).
In the real world

Teams that started with JSON mode in 2023 all built the same thing next: a validator that checks the keys and types, plus a retry loop. That pile of glue code is exactly what structured outputs replaced. You'll still meet JSON mode with local and older models, so it's worth knowing its limits.

Traditional developer view

"It's valid JSON, so the integration works."

GenAI developer view

"Valid JSON means it parses. I still need the right keys, types and values, so I either enforce a schema or validate every reply."

Common trap

json.loads() succeeds and the code moves on, then fails three functions later with KeyError: 'enrolment_id' because this reply called it enrollmentId. Validate right where the JSON enters your system.

Interview cue

"JSON mode guarantees syntax, not schema. For a fixed shape I use structured outputs with a JSON Schema; I keep JSON mode as a fallback for models that don't support it, with validation."

llm.py
"""Shared helper for every drill: returns an OpenAI-compatible client for
Azure OpenAI (Microsoft Foundry), OpenAI or Ollama, chosen in .env."""
import os

from dotenv import load_dotenv
from openai import OpenAI

load_dotenv()  # reads .env from the current folder

PROVIDER = os.getenv("LLM_PROVIDER", "ollama").lower()   # default: a free local model (Ollama)


def get_client() -> OpenAI:
    if PROVIDER == "azure":
        # Azure OpenAI v1 API: the standard OpenAI client, pointed at your resource
        return OpenAI(
            base_url=os.environ["AZURE_OPENAI_BASE_URL"],
            api_key=os.environ["AZURE_OPENAI_API_KEY"],
        )
    if PROVIDER == "openai":
        return OpenAI()  # reads OPENAI_API_KEY
    if PROVIDER == "ollama":
        return OpenAI(base_url="http://localhost:11434/v1", api_key="ollama")
    raise ValueError(f"Unknown LLM_PROVIDER: {PROVIDER!r}")


# On Azure this is the DEPLOYMENT name; elsewhere it's the model name.
MODEL = {
    "azure": os.getenv("AZURE_OPENAI_DEPLOYMENT", "chat"),
    "openai": os.getenv("OPENAI_MODEL", "gpt-5.4-mini"),
    "ollama": os.getenv("OLLAMA_MODEL", "llama3.2"),
}.get(PROVIDER, "")
Drill 04.2

JSON mode: watch the keys drift, then pin them

~15 minAzure OpenAIPython

Goal: measure how many different JSON shapes a loose prompt produces, then reduce it to one with a precise prompt, and spot what's still wrong.

  1. Run

    Loose prompt, JSON mode on

    """Drill 04.2: JSON mode. The reply is always valid JSON, but which keys and types?
Run:  python lab04_02_json_mode.py            (loose prompt)
      python lab04_02_json_mode.py --tight    (prompt that lists the exact keys)"""
import json
import sys
from collections import Counter

from llm import MODEL, get_client

MESSAGES = [
    "Hi, I'm Mei. My lab for TC-10293 says quota exceeded and my exam is on Friday!",
    "Can I get a refund for TC-20877? I can't attend next week.",
    "Where is my AZ-104 exam voucher? I finished the course 5 days ago. Diego",
    "Hola, ¿puedo cambiar la fecha de mi curso? Soy Asha, inscripción TC-31002.",
    "My certificate says Omar Farouk but my name is Omar Faruk.",
]

LOOSE = "Extract the useful details from this support message as JSON."
TIGHT = """Extract details from this support message.
Return a JSON object with exactly these keys:
"learner_name" (string or null), "enrolment_id" (string or null),
"category" (one of scheduling, billing, exam_voucher, certificate, lab_access, account, other),
"urgent" (true or false)."""


def main():
    client = get_client()
    system = TIGHT if "--tight" in sys.argv else LOOSE
    shapes = Counter()

    for text in MESSAGES:
        response = client.chat.completions.create(
            model=MODEL,
            # JSON mode: the model must produce valid JSON. The prompt must mention "JSON".
            response_format={"type": "json_object"},
            messages=[{"role": "system", "content": system}, {"role": "user", "content": text}],
        )
        data = json.loads(response.choices[0].message.content)      # never fails in JSON mode...
        keys = tuple(sorted(data))
        shapes[keys] += 1
        print(json.dumps(data, ensure_ascii=False))

    print("\nDifferent key sets seen:", len(shapes))
    for keys, count in shapes.most_common():
        print(f"  {count} x {list(keys)}")


if __name__ == "__main__":
    main()

    Write a prompt that pins the shape

    Before looking at TIGHT in the script, write your own system prompt that makes every reply use the same four keys.

    Goal: extract details from a TrainCrest support message as JSON
Context: the output is parsed by a program, not read by a person
Constraints: exactly these keys and no others: ...
             allowed values for category: ...
             what to write when a value is missing: ...
Done when: all five messages produce the same key set

    Hint: name each key, its type, and the missing-value rule (null, not "null" or ""). List the seven categories from Module 03.

  3. Verify

    One shape, and still wrong

    • The key sets dropped to one: the prompt fixed the shape.
    • Now read the values in that last run: Mei's ID became "12345" (invented; hers is TC-10293), Omar's missing ID is the string "null", and Diego's voucher and Asha's reschedule were both filed as billing. JSON mode can't catch any of that.
    • Keep this output. In Drill 04.3 you'll run the same messages with a schema, and in Drill 04.9 you'll add the rules that catch invented IDs.
Open alternative · compare models fairly

Run the same script with LLM_PROVIDER=ollama and then with your Azure deployment. Counting key sets and wrong values gives you a numeric comparison instead of an impression. Small local models are great for learning exactly why the guarantees on the next page matter.

3

Check

JSON mode.

1. JSON mode is on and json.loads() never fails. What can still go wrong?

Wrong or missing keys, wrong types ("null" as a string, numbers as text), values outside the allowed list, invented values, and truncated output if the token limit is hit.

2. When would you still choose JSON mode today?

When the model or server doesn't support structured outputs (some local or older models), or when the shape is genuinely open-ended. Always pair it with validation.

Takeaway

JSON mode fixes the syntax. The prompt can fix the keys. Neither fixes the types or the truth.
