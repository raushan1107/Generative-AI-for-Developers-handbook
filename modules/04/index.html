Module 04 · Overview

Structured Outputs and Function Calling: From Text to Actions

So far the model has produced words for people to read. In this module it starts producing data for your code to use, and asking your code to do things: check an enrolment, quote a refund, raise a ticket. That's the moment a chatbot becomes part of an application, and the moment reliability stops being optional.

7 topics10 drillsMilestone 4≈ 5 hours hands-on

The mental map: the reliability ladder

Every rung up this ladder hands one more guarantee from "the model will probably do it" to "the system makes sure of it". The whole module climbs it, one rung per topic.

Takeaway

The model proposes; your code disposes. Use the API to guarantee the shape, your validators to guarantee the rules, and your own functions to do anything that matters.

Why this module changes what you build

In Milestone 3, Traincrest Assist triaged messages into JSON, and we still needed a repair loop because the model sometimes wrapped its answer in code fences. Worse, when Diego asked "how much do I get back if I cancel?", Assist could only recite policy: it couldn't see his booking, so it couldn't give him a number. Both problems have the same cure: stop treating the model as a text generator and start treating it as a component with a contract.

Imagine this

A hotel concierge doesn't walk into the kitchen and cook your dinner. They fill in a room-service form with fixed boxes (dish, quantity, room number) and hand it to the kitchen. The kitchen checks the room is real, cooks, and sends back a receipt the concierge reads to you. Structured outputs are the form. Function calling is handing it to the kitchen. Your code is the kitchen: it decides what actually gets made.

Traditional developer view

"Functions have typed parameters. Callers either pass valid arguments or get a compile error."

GenAI developer view

"My caller is a model. It can send the wrong type, an invented ID or somebody else's ID. I publish a schema, let the API enforce the shape, validate the rules myself, and never let the model decide whose data a function touches."

Lab kit for Module 04

  • New files in genai-labs/: catalogue.py and data/courses.json (20 fictional TrainCrest courses), used here and in Module 05.
  • Install: pip install pydantic (already there if you did Part I's labs with FastAPI).
  • Many drills run offline. Drills 04.1, 04.4, 04.7 (tests), 04.8, 04.9 and 04.10 need no API key, so you can practise the hard parts anywhere and get exact outputs.
  • New helper, llm_tools.py: if a tool drill fails with "Function tools with reasoning_effort are not supported", your deployment is a reasoning model that wants the Responses API for tools. For these drills, add TOOLS_REASONING_EFFORT=none to .env; this helper passes it on every tool request. Or use a non-reasoning deployment. 
    """Module 04 helper: extra arguments for requests that send tools.

"Function tools with reasoning_effort are not supported"."""
