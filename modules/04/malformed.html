Handling Malformed Responses

Even with strict schemas, replies go wrong: cut off at the token limit, refused, blocked by a content filter, or wrapped in chatter by a model that doesn't support strict mode. Production code doesn't hope these won't happen. It names each failure, detects it, and decides: retry, repair, fall back or escalate. You'll prove yours does, with a fake model built to misbehave.

1

Learn

Name every failure, then handle each one on purpose.

Definition

A malformed response is any model output your code can't safely use as intended: incomplete, refused, filtered, unparseable, schema-invalid, rule-invalid, or a tool call with a bad name or arguments. Handling it means detecting the specific case (mostly from finish_reason, refusal and validation errors) and applying a deliberate policy for it.

In plain words

"It didn't work" isn't one problem. A reply that ran out of space needs more space; a refusal needs a different response to the user, not a retry; garbage needs a second try with the error shown. Different failures, different fixes.

Imagine this

A delivery driver comes back with your parcel. If the address was smudged, you rewrite it and send it again. If the van was full, you send a bigger van. If the recipient refused it, sending it again won't help. A good dispatcher checks why it came back before doing anything.

What went wrongHow you detect itWhat to do
Cut off at the token limitfinish_reason == "length"; parse() raises LengthFinishReasonErrorRetry once with a larger max_completion_tokens, or ask for less. Never parse a cut-off JSON.
Refusalmessage.refusal is setDon't retry the same request. Show a safe message, log it, maybe escalate.
Content filterfinish_reason == "content_filter"; ContentFilterFinishReasonError; or a 400 error from the filter on the promptDon't retry unchanged. Safe message; review if it's a false positive.
Not JSON at all, or wrapped in fences and chatterValidationError / json.JSONDecodeError (non-strict models and JSON mode)Light extraction (strip fences, take {...}), then one repair round with the error
Valid JSON, breaks a rulePydantic validator errorOne repair round with the message; then fall back
Tool call: unknown name or bad argumentsDispatcher returns {"error": ...}Send the error back as the tool result; the loop limit caps retries
Empty answer after toolscontent empty and no tool_callsRetry once or use a fallback message

Retry only when retrying can help

  • Worth retrying: truncation (with more room), invalid or rule-breaking output (with the error), transient API errors (the SDK retries 429 and 5xx for you, Module 02).
  • Not worth retrying: refusals, content-filter blocks, authentication errors. Same input, same outcome, double the bill.
  • Always bounded: one repair round is usually enough; two at most. After that the problem is your prompt, schema or model choice, and the logs should tell you so.
In the real world

Teams running document extraction at scale typically see a small but steady fraction of replies needing repair, and a far smaller fraction refused or filtered. They track each outcome separately on a dashboard. A jump in "truncated" usually means documents got longer; a jump in "invalid" after a deploy usually means someone changed the prompt or the schema.

Traditional developer view

"Wrap the call in try/except and retry three times."

GenAI developer view

"Each failure has a name and a cause. I return a typed outcome (ok, refused, blocked, truncated, invalid), retry only the ones a retry can fix, and count each one."

Common trap

Ignoring finish_reason. A reply cut off at the limit can still look fine in prose ("Your refund will be"), and in JSON mode it fails with a confusing parse error. Check why the model stopped before you read what it wrote.

Interview cue

"I check finish_reason and refusal first, validate second, and map every case to an outcome: truncation gets more tokens, invalid output gets one repair with the error, refusals and filter blocks get a safe response and no retry. All bounded, all logged."

import os

from dotenv import load_dotenv
from openai import OpenAI

load_dotenv()  # reads .env from the current folder

PROVIDER = os.getenv("LLM_PROVIDER", "ollama").lower()   # default: a free local model (Ollama)


def get_client() -> OpenAI:
    if PROVIDER == "azure":
        # Azure OpenAI v1 API: the standard OpenAI client, pointed at your resource
        return OpenAI(
            base_url=os.environ["AZURE_OPENAI_BASE_URL"],
            api_key=os.environ["AZURE_OPENAI_API_KEY"],
        )
    if PROVIDER == "openai":
        return OpenAI()  # reads OPENAI_API_KEY

        return OpenAI(base_url="http://localhost:11434/v1", api_key="ollama")
    raise ValueError(f"Unknown LLM_PROVIDER: {PROVIDER!r}")

Drill 04.10

Chaos drill: a fake model that misbehaves in every way

~20 minOffline · no API keypytest

Goal: test a wrapper that turns every common failure into a clear outcome, without waiting for a real model to fail.

  1. Run

    The wrapper

    structured_call() does by hand what parse() partly does for you, so you can see each decision. It also works with JSON-mode-only providers, because it extracts and validates the JSON itself.

    """Drill 04.10: one function that turns every way a structured reply can go wrong
into a clear outcome your code can act on. .parse() does part of this for you;
here you see all of it, and it also works with providers that lack strict mode."""
import re
from dataclasses import dataclass
from typing import Any, Optional

from pydantic import BaseModel, ValidationError

from schema_lint import strict_schema

FENCE = re.compile(r"^```(?:json)?\s*|\s*```$")


@dataclass
class Outcome:
    status: str                  # ok | refused | blocked | truncated | invalid
    value: Optional[Any] = None  # the validated model instance when status == "ok"
    detail: str = ""
    attempts: int = 0


def extract_json(text: str) -> str:
    """Forgive the usual wrapping: code fences and a sentence before or after the object."""
    text = FENCE.sub("", text.strip())
    start, end = text.find("{"), text.rfind("}")
    return text[start:end + 1] if start != -1 and end > start else text


def structured_call(client, model: str, messages: list, schema: type[BaseModel],
                    max_tokens: int = 600, max_attempts: int = 2) -> Outcome:
    response_format = {"type": "json_schema",
                       "json_schema": {"name": schema.__name__, "strict": True, "schema": strict_schema(schema)}}
    messages, problem = list(messages), ""
    for attempt in range(1, max_attempts + 1):
        r = client.chat.completions.create(model=model, messages=messages, response_format=response_format,
                                           max_completion_tokens=max_tokens)
        choice = r.choices[0]
        refusal = getattr(choice.message, "refusal", None)
        if refusal:                                   # the model declined: don't retry, don't parse
            return Outcome("refused", detail=refusal, attempts=attempt)
        if choice.finish_reason == "content_filter":  # the platform's safety filter cut the reply
            return Outcome("blocked", detail="content filter", attempts=attempt)
        if choice.finish_reason == "length":          # ran out of tokens: the JSON is cut off
            problem = f"truncated at {max_tokens} tokens"
            max_tokens *= 2                           # one retry with more room, then give up
            continue
        text = choice.message.content or ""
        try:
            return Outcome("ok", value=schema.model_validate_json(extract_json(text)), attempts=attempt)
        except ValidationError as e:
            first = e.errors()[0]
            problem = f"{'.'.join(map(str, first['loc'])) or 'output'}: {first['msg']}"
            messages += [{"role": "assistant", "content": text},
                         {"role": "user", "content": f"Invalid ({problem}). Return only the corrected JSON object."}]
    status = "truncated" if problem.startswith("truncated") else "invalid"
    return Outcome(status, detail=problem, attempts=max_attempts)

from types import SimpleNamespace as NS
from typing import Literal

from pydantic import BaseModel

from robust import structured_call


class Reply(BaseModel):

GOOD = '{"category": "fees", "urgent": false}'


def says(content=None, finish="stop", refusal=None):
    return NS(choices=[NS(message=NS(content=content, refusal=refusal), finish_reason=finish)])


class FakeModel:

    def __init__(self, *responses):

SCENARIOS = {

  4. Think

    Add a scenario

    Add a tenth scenario to SCENARIOS and EXPECTED: the model returns valid JSON with an extra key, {"category": "billing", "urgent": false, "note": "hi"}. What outcome do you expect with the Reply model as written? What changes if you add model_config = ConfigDict(extra="forbid")?

    Compare with my answer

    As written, Pydantic ignores extra keys by default, so the outcome is ok on the first try and note is silently dropped. With extra="forbid", the first reply fails validation, the wrapper repairs once, and the outcome depends on the second reply. With strict structured outputs the extra key can't appear at all, but providers without strict mode can send it, so decide deliberately: ignore (tolerant) or forbid (strict). Milestone 3's Triage chose forbid.

Remember: “Don't wait for production to show you how replies fail. Write the failures yourself and test against them.”

3

Check

Malformed responses.

1. Your extraction job's "truncated" count doubled overnight. First thing to check?

Whether inputs got longer (new document type, bigger attachments) or someone lowered max_completion_tokens or changed the schema to ask for more fields. Truncation is about room, not quality.

2. Why not retry a refusal three times?

The same input will almost always be refused again: three times the cost and latency for the same result. Handle it: safe message to the user, log it, escalate if it looks like a false positive.

3. With strict structured outputs, which failures can still happen?

Truncation, refusals, content-filter blocks, rule failures your validators catch, and wrong-but-valid values. Strict mode removes "not JSON" and "wrong shape", nothing else.

Takeaway

Check why the model stopped, validate what it wrote, and give every failure a name, a bounded policy and a counter.
