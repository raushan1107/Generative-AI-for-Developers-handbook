Response Generation

With good sources in a good prompt, generation is the easy part, until it isn't. The model may add a detail the sources don't contain, ignore the 'not found' rule, or answer in English when asked in Spanish. You'll run the complete pipeline on six questions chosen to trigger each behaviour, and see what a small local model gets right and wrong.

1

Learn

Answer from the sources, all of them, only them.

Definition

Response generation is the final RAG step: the chat model reads the constructed prompt and produces an answer that should be grounded (every claim supported by a source), complete (it uses every relevant source), attributed (it cites them) and honest (it says when the sources don't answer the question), in the user's language and tone.

In plain words

The model writes the answer from the extracts, combines them if the question needs two, points to them, and admits when they don't cover it.

Imagine this

An interpreter at a meeting. A good one renders exactly what was said, in the listener's language, and says "the speaker didn't mention a date" rather than inventing one. A bad one "helps" by filling gaps. You want the first, and you check the transcript afterwards.

Behaviours to design for

SituationWhat you wantHow
Nothing relevant retrievedA polite "not found", no costSkip the model when retrieval returns nothing (floor, topic 6)
Retrieved, but no answer in it"Not found", not an improvised answerThe NOT_FOUND rule; detect the sentinel in code
Answer spans two sectionsBoth used and both citedk ≥ 3, "[1][3]" allowed in the prompt
Question in another languageAnswer in that language, from English sourcesRule in the prompt, and rewrite the query into the index language (Drill 06.7)
Two sources disagreeThe newer or more authoritative one, or say they differDates and source type in metadata; tell the model which wins
Numbers and moneyCopied exactly, never computed"Don't guess numbers", citation checks, and tools for calculations
Factual toneConsistent answersLow temperature (0 to 0.3) where the model supports it

Model choice matters more here than anywhere else in RAG. Following "only from the sources, cite each fact, else NOT_FOUND" is an instruction-following skill: larger hosted models do it reliably; small local models often skip citations, ignore the sentinel or add details. Use small models to learn and prototype; measure before shipping (Module 09).

In the real world

Support teams typically roll out RAG answers in stages: first as suggested replies that an agent edits and sends, then as automatic answers for the topics where measured accuracy is high, with a visible "Was this helpful?" and a hand-off to a person. The NOT_FOUND path isn't a failure in that setup; it's the router that sends the hard questions to people.

Traditional developer view

"The model generates the answer; if it's wrong, the model is bad."

GenAI developer view

"Generation is one controlled step with defined exits: no sources, not found, answer. I choose the model by how well it follows grounding rules, and I check its output before anyone reads it."

Common trap

Treating "the answer sounds right" as "the answer is grounded". In this drill, a model answers a refund question in fluent English with a real citation, and still adds a "1-2 billing cycles" claim that no source contains. Only the check in topic 9 notices.

Interview cue

"Generation has explicit exits: skip the model when nothing is retrieved, detect a NOT_FOUND sentinel, otherwise answer at low temperature in the user's language and verify citations. I pick the generator model by its groundedness and citation rate on my evaluation set."

llm.py
"""Shared helper for every drill: returns an OpenAI-compatible client for
Azure OpenAI (Microsoft Foundry), OpenAI or Ollama, chosen in .env."""
import os

from dotenv import load_dotenv
from openai import OpenAI

load_dotenv()  # reads .env from the current folder

PROVIDER = os.getenv("LLM_PROVIDER", "ollama").lower()   # default: a free local model (Ollama)


def get_client() -> OpenAI:
    if PROVIDER == "azure":
        # Azure OpenAI v1 API: the standard OpenAI client, pointed at your resource
        return OpenAI(
            base_url=os.environ["AZURE_OPENAI_BASE_URL"],
            api_key=os.environ["AZURE_OPENAI_API_KEY"],
        )
    if PROVIDER == "openai":
        return OpenAI()  # reads OPENAI_API_KEY
    if PROVIDER == "ollama":
        return OpenAI(base_url="http://localhost:11434/v1", api_key="ollama")
    raise ValueError(f"Unknown LLM_PROVIDER: {PROVIDER!r}")


# On Azure this is the DEPLOYMENT name; elsewhere it's the model name.
MODEL = {
    "azure": os.getenv("AZURE_OPENAI_DEPLOYMENT", "chat"),
    "openai": os.getenv("OPENAI_MODEL", "gpt-5.4-mini"),
    "ollama": os.getenv("OLLAMA_MODEL", "llama3.2"),
}.get(PROVIDER, "")
Drill 06.9

The Company Knowledge Assistant, end to end

~30 minAzure OpenAIPython

Goal: put ingestion, chunking, the index, retrieval, the prompt and the checks together in one function, run it on six questions that each test a behaviour, then use it as an interactive assistant over TrainCrest's public and internal documents.

  1. Run

    The pipeline in one function

    """Module 06: the RAG pipeline in one function, built from this module's helpers.
retrieve (with a relevance floor) -> nothing relevant? stop, no model call -> build the prompt
-> generate -> NOT_FOUND? say so -> check the citations."""
import os

import openai

from citations import check
from embed import EMBED_MODEL
from kb_index import load_or_build
from llm import MODEL, get_client
from rag_prompt import NOT_FOUND, build_messages

# Relevance floor on cosine similarity. Model-specific: calibrate it for yours with Drill 06.6.
FLOORS = {"nomic-embed-text": 0.55, "text-embedding-3-small": 0.30, "text-embedding-3-large": 0.30}
MIN_SCORE = float(os.getenv("RAG_MIN_SCORE") or FLOORS.get(EMBED_MODEL, 0.30))
NO_ANSWER = "I couldn't find that in RR Finance Bank's documents. Shall I raise a case for the support team?"


def generate(client, messages):
    """Low temperature for factual answers; some reasoning models reject the parameter, so retry without."""
    try:
        return client.chat.completions.create(model=MODEL, messages=messages, temperature=0)
    except openai.BadRequestError:
        return client.chat.completions.create(model=MODEL, messages=messages)


def answer(question: str, audience=("public",), index=None, client=None, k: int = 4) -> dict:
    index = index or load_or_build()
    hits = index.search(question, k=k, audience=audience, min_score=MIN_SCORE)
    if not hits:                                             # nothing relevant: don't let the model improvise
        return {"answer": NO_ANSWER, "found": False, "sources": [], "report": None, "llm_calls": 0}
    messages, sources = build_messages(question, hits)
    response = generate(client or get_client(), messages)
    text = (response.choices[0].message.content or "").strip()
    if not text or text.startswith(NOT_FOUND):
        return {"answer": NO_ANSWER, "found": False, "sources": sources, "report": None, "llm_calls": 1}
    return {"answer": text, "found": True, "sources": sources, "report": check(text, sources, question), "llm_calls": 1}

  3. Think

    Grade each answer

    1. The first answer cites the right section. What's wrong with it, and what caught it?
    2. The Spanish question has an answer in the help centre ($50, once). Why did it get "not found" with zero model calls, and what would fix it?
    3. The dog question passed the floor and the model said the sources don't mention it, but not with NOT_FOUND. Is that acceptable?
    4. The same $300 question gave "not found" for a learner and an answer for staff. Which component made that happen?
    Compare with my answers
    1. It invents "typically 1-2 billing cycles" and drops the actual "5 to 10 business days". The numbers check flagged 1 and 2 as unsupported by source [1]. Without it, this answer would look perfectly sourced.
    2. The English-centric embedding model scored the Spanish question below the 0.55 floor, so retrieval returned nothing and the model was never asked. Fix it at retrieval: rewrite the query into English first (Drill 06.7's stretch) or use a multilingual embedding model; the floor did its job.
    3. The content is right, but code can't tell it apart from a real answer, so it's shown as one, with no sources. A stronger model follows the sentinel more reliably; Module 09 measures how often each model does.
    4. The audience pre-filter in retrieval. For the learner, the staff-only approvals page was never a candidate, so the model saw only public refund sections and correctly said NOT_FOUND.

3

Check

Generation.

1. Why skip the model call entirely when retrieval returns nothing?

There is nothing to ground an answer in, so any answer would come from the model's memory. Skipping saves cost and latency and guarantees the "not found" path is taken.

2. Two retrieved sections give different prices for the same thing. What should the system do?

Prefer the authoritative or newest source by metadata (for example the help centre over an old FAQ, or the most recent updated date) and tell the model that rule; or have it say the sources differ and cite both. Then fix the content, because the conflict will come back.

3. When would you use temperature 0 for RAG, and when not?

For factual answers from sources, low temperature gives consistent, literal answers. Some reasoning models don't accept a temperature parameter at all (rag.py retries without it). For creative rewriting of the same facts, a little more is fine.

Takeaway

Generation needs defined exits (no sources, NOT_FOUND, answer), a model that follows grounding rules, and checks on everything it says.
