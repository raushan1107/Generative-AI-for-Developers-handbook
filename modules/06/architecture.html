RAG Architecture

RAG isn't one thing; it's two pipelines and eight components, each with its own failure modes. Name them, and you know where to look when an answer is wrong. You'll run the smallest RAG that works, about 50 lines, and time every stage.

1

Learn

Know the parts, and where answers go wrong.

Definition

A RAG architecture has an offline (indexing) pipeline that turns source documents into a searchable index (ingest, chunk, embed, store) and an online (query) pipeline that answers each question (retrieve, build the prompt, generate, check). The two meet at the index and must use the same embedding model.

In plain words

Prepare the library ahead of time; at question time, fetch the right pages, hand them over with clear instructions, and check the answer before showing it.

Imagine this

A restaurant kitchen. Before service, the prep cooks wash, cut and label ingredients into containers (indexing). During service, each order pulls exactly the containers it needs, the chef cooks, and the pass checks the plate before it leaves (query). A bad plate is usually a prep or picking problem, not a chef problem.

Two ways to wire the query side

Pipeline RAGTool-based ("agentic") RAG
Who decides to searchYour code, for every questionThe model, by calling a search tool when it needs to
Searches per questionOne (or a fixed number)Zero, one or several, with queries the model writes
Good forA help-centre search box, "ask the docs" pages, batch jobsA chat assistant that also uses other tools and handles follow-ups
Watch out forSearching for "thanks!" and greetingsThe model skipping the search and answering from memory
In Milestone 6POST /api/askThe search_help tool in chat

Facts worth remembering

  • Indexing runs when content changes, not per question: on a schedule, on a webhook from the wiki, or in a CI pipeline (Module 12).
  • Latency is dominated by generation. Embedding a question and searching takes milliseconds; the model's answer takes seconds (Drill 06.2 shows it).
  • Managed options exist for each box: Azure AI Search can ingest, chunk and vectorise documents for you (integrated vectorization), rank results semantically, and filter by user permissions. Doing it by hand once makes those settings meaningful.
  • Keep every stage observable: log which chunks were retrieved, with scores, for every answer. Without that you can't debug or evaluate (Modules 08 and 09).
In the real world

When a RAG bot gives a wrong answer, experienced teams open the trace and read the retrieved chunks first. Most of the time the answer was wrong because the right passage wasn't there: an outdated document, a table that chunked badly, a question in another language, or a filter that hid it. Teams that log retrieval fix these in hours; teams that only log the final answer end up rewriting prompts for weeks.

Traditional developer view

"It's a chatbot with a search box glued on."

GenAI developer view

"It's a data pipeline plus a question pipeline. I test and monitor each stage separately, and I always know which chunks produced which answer."

Common trap

Fixing retrieval problems with prompt changes ("ALWAYS check carefully!"). If the right chunk isn't in the context, no instruction can make the model know it. Check retrieval first.

Interview cue

"A RAG system has an offline indexing pipeline (ingest, chunk, embed, store) and an online query pipeline (retrieve, augment the prompt, generate, verify). I'd choose pipeline RAG for a single-purpose Q&A box and tool-based RAG inside an assistant that also calls other tools, and I'd log retrieved chunks for every answer."

Do

All eight boxes in one small script.

Drill 06.2

The smallest RAG that works

~15 minAzure OpenAIPython · numpy

Goal: run RAG end to end over the help centre with no framework, see each stage and its time, then map the script onto the architecture.

  1. Run

    Index and answer in one script

    """Drill 06.2: the smallest RAG that works, every stage in plain sight.
Index (ahead of time): load the help articles, chunk them by heading, embed the chunks.
Query (every question): embed the question, take the 3 nearest chunks, put them in the prompt, generate.
Run:  python lab06_02_minimal_rag.py "Can I pay for a $1,490 course in parts?" """
import re
import sys
import time
from pathlib import Path

import numpy as np

from embed import embed
from llm import MODEL, get_client

question = sys.argv[1] if len(sys.argv) > 1 else "Can I pay for a $1,490 course in parts?"
clock = time.perf_counter()


def stage(name):
    global clock
    now = time.perf_counter()
    print(f"[{now - clock:5.2f}s] {name}")
    clock = now


# ---- INDEXING: ahead of time, once per content change
chunks = []
for path in sorted((Path(__file__).parent / "data" / "help").glob("*.md")):
    text = path.read_text(encoding="utf-8")
    title = re.search(r"^# (.+)$", text, re.M).group(1)
    for part in re.split(r"^## ", text, flags=re.M)[1:]:
        heading, _, body = part.partition("\n")
        chunks.append({"source": f"{path.stem} > {heading.strip()}", "text": f"{title} > {heading}\n{body.strip()}"})
stage(f"ingest + chunk: {len(chunks)} chunks")
vectors = embed([c["text"] for c in chunks])
vectors /= np.linalg.norm(vectors, axis=1, keepdims=True)
stage(f"embed + store: {vectors.shape[0]} vectors of {vectors.shape[1]} numbers")

# ---- QUERY: every question
q = embed([question])[0]
scores = vectors @ (q / np.linalg.norm(q))
top = np.argsort(-scores)[:3]
stage("retrieve: " + ", ".join(f"{chunks[i]['source']} ({scores[i]:.2f})" for i in top))
context = "\n\n".join(f"[{n}] {chunks[i]['text']}" for n, i in enumerate(top, start=1))
messages = [{"role": "system", "content": "Answer using only the numbered sources. Cite them like [1]. "
                                          "If they don't contain the answer, say you don't know."},
            {"role": "user", "content": f"{context}\n\nQuestion: {question}"}]
stage("prompt: question + 3 sources")
answer = get_client().chat.completions.create(model=MODEL, messages=messages).choices[0].message.content
stage("generate")
print(f"\nQ: {question}\nA: {answer.strip()}")
    $ python lab06_02_minimal_rag.py "Can I pay for a $1,490 course in parts?"

    The embedding stages show 0.00s because embed.py's disk cache already had these texts from Module 05. On a first run, embedding 40 chunks takes a second or two; generation still dominates.

  2. Think

    Map it to the eight components

    1. Which lines are ingestion, chunking, embedding, the vector store, the retriever, the prompt builder and the generator? Which component is missing?
    2. The script re-embeds and rebuilds the "index" on every run. Why is that fine here and wrong in production?
    3. What happens if you ask "Can I bring my dog?", and which component should have stopped it?
    Compare with my answers
    1. The for path in ... loop is ingestion and chunking (headings only, intros dropped); embed(...) plus the normalised numpy array are embedding and the "vector store"; scores and argsort are the retriever; context and messages are the prompt builder; the create call is the generator. The citation checker is missing, and so are a relevance floor and metadata.
    2. Forty short chunks embed in seconds (and the cache makes re-runs free). With thousands of documents you index once, store the vectors, and update only what changed (topic 5).
    3. It always retrieves 3 chunks, however unrelated, and the model may improvise from them. A relevance floor in the retriever (topic 6) and a "NOT_FOUND" rule in the prompt (topic 7) should stop it.
  3. Ask AI

    Make the stages visible

    In #file:lab06_02_minimal_rag.py, after the "retrieve" stage, print the first 80 characters
of each retrieved chunk under its source, indented by four spaces. Change nothing else.
Then explain in two sentences why printing retrieved chunks is the first debugging step in RAG.
    Why this prompt works: it names the file and the exact place, limits the change ("nothing else"), and asks for the reasoning as well, so you learn the habit, not just the code.

    You should see the instalments text under the first source. Make this a habit: every RAG script you write should be able to show what it retrieved.

3

Check

Architecture.

1. A learner gets a wrong answer about voucher validity. What is the first thing you check?

Which chunks were retrieved for that question. If the "How long it is valid" section wasn't among them, it's a retrieval problem (chunking, embedding, filters or the floor), not a prompt problem.

2. Which pipeline runs when the support team edits a help article?

The offline indexing pipeline: re-ingest the article, re-chunk it, re-embed the changed chunks and update the store. The query pipeline doesn't change.

3. When would you choose tool-based RAG over a fixed pipeline?

Inside a conversational assistant that also uses other tools, needs to decide when looking things up is useful, may search more than once, and must turn follow-ups into proper search queries.

Takeaway

Two pipelines, eight components, one debugging rule: check what was retrieved before you touch the prompt.
