Build an Evaluation Set

A score is only as meaningful as the examples behind it. Build a small, reviewed set that reflects real customer questions, edge cases and policy versions before choosing a metric.

Representative casesLabelsSlicesVersioning
1Learn→2Do→3CheckLearn 12 min · Do 15 min
1

Learn

Write down the expected behavior before you inspect the score.

Definition

An evaluation set is a versioned collection of inputs and expected labels, answers or judgments used to compare system behavior. A golden set is a reviewed subset with trusted references. Keep it separate from examples used to tune prompts, and preserve the source and policy version for each case.

In plain words

Make a fair test that includes ordinary requests, difficult cases and the mistakes that would matter most. Agree on the right answer first.

Imagine this

A bank teller is assessed on routine deposits and unusual fraud reports, not on a hundred copies of the same easy transaction.

FieldExampleWhy keep it
Input and localeCustomer message, languageMeasures coverage across real use

Risk sliceUnrecognized charge, minority languageShows important failures hidden by aggregate scores
In the real world

Evaluation data should reflect intended use, known edge cases and groups affected by the system. Keep private customer data out of ad hoc test fixtures; use approved synthetic or properly governed data, with documented access and retention.

In finance

Include a recognized duplicate purchase, an unrecognized card payment, a fee-waiver request, a mistaken transfer and a multilingual fraud report. Label the cases with policy owners, and version the policy references so a rule change triggers a new evaluation.

Traditional developer view

"More rows make the test set better."

GenAI developer view

"Coverage, label quality and risk relevance matter more than raw row count; duplicate or leaked examples can inflate scores."

Common trap

Using the same examples to tune a prompt and report final performance. Keep a held-out set, record changes and avoid exposing its labels to the system being evaluated.

Interview cue

"I version the evaluation data and labels, preserve policy references, review coverage by risk and language, and separate tuning examples from a held-out release set."

Drill 09.1

Measure a high-risk classification slice

~15 minPython · pytestoffline

Goal: compute fraud precision and recall from a reviewed label list rather than relying on overall accuracy.

  1. Run

    The deterministic metric

    """Deterministic classification metrics and explicit release thresholds."""

import math
from collections.abc import Mapping, Sequence


def classification_metrics(
    expected: Sequence[str], predicted: Sequence[str], positive_label: str
) -> dict[str, float]:
    if not expected or len(expected) != len(predicted):
        raise ValueError("Expected and predicted labels must be non-empty and aligned")
    if not positive_label:
        raise ValueError("A positive label is required")

    true_positive = sum(
        actual == positive_label and guess == positive_label
        for actual, guess in zip(expected, predicted)
    )
    false_positive = sum(
        actual != positive_label and guess == positive_label
        for actual, guess in zip(expected, predicted)
    )
    false_negative = sum(
        actual == positive_label and guess != positive_label
        for actual, guess in zip(expected, predicted)
    )
    correct = sum(actual == guess for actual, guess in zip(expected, predicted))
    precision_denominator = true_positive + false_positive
    recall_denominator = true_positive + false_negative

    return {
        "accuracy": correct / len(expected),
        "precision": (
            true_positive / precision_denominator if precision_denominator else 0.0
        ),
        "recall": true_positive / recall_denominator if recall_denominator else 0.0,
    }


def release_gate(
    metrics: Mapping[str, float], minimums: Mapping[str, float]
) -> list[str]:
    """Return failed metric names; callers decide whether to block a release."""
    failures: list[str] = []
    for name, minimum in minimums.items():
        value = metrics.get(name)
        if (
            not isinstance(value, (int, float))
            or isinstance(value, bool)
            or not isinstance(minimum, (int, float))
            or isinstance(minimum, bool)
            or not math.isfinite(value)
            or not math.isfinite(minimum)
            or not 0.0 <= minimum <= 1.0
            or value < minimum
        ):
            failures.append(name)
    return failures

from app.evaluation import classification_metrics, release_gate


def test_classification_metrics_highlight_fraud_recall():
    actual = ["fraud", "fraud", "fees", "dispute"]
    predicted = ["fraud", "fees", "fraud", "dispute"]
    metrics = classification_metrics(actual, predicted, positive_label="fraud")
    assert metrics == {"accuracy": 0.5, "precision": 0.5, "recall": 0.5}


def test_release_gate_checks_each_declared_threshold():
    metrics = {"accuracy": 0.94, "fraud_recall": 0.82}
    assert release_gate(metrics, {"accuracy": 0.9, "fraud_recall": 0.8}) == []
    assert release_gate(metrics, {"accuracy": 0.9, "fraud_recall": 0.9}) == [
        "fraud_recall"
    ]


@pytest.mark.parametrize(
    ("expected", "predicted"),
    [([], []), (["fraud"], [])],
)
def test_metric_inputs_must_be_nonempty_and_aligned(expected, predicted):
    with pytest.raises(ValueError, match="non-empty and aligned"):
        classification_metrics(expected, predicted, positive_label="fraud")


def test_release_gate_fails_missing_and_nonfinite_metrics():
    assert release_gate({"accuracy": float("nan")}, {"accuracy": 0.9, "recall": 0.8}) == [
        "accuracy",
        "recall",
    ]

  2. Verify
    • Inputs must be non-empty and aligned.
    • False negatives lower recall; false positives lower precision.
    • Run the same metric by language and risk slice before comparing releases.
3

Check

Evaluation data.

1. Why should fraud recall be reported separately?

A high overall accuracy can hide a model that misses the less frequent but high-impact fraud cases.

2. Why version policy references?

When a policy changes, a reviewer needs to know which rule each expected answer reflects and whether the evaluation should be updated.

Takeaway

Representative, reviewed and versioned examples make evaluation meaningful. Protect the data and inspect high-risk slices, not just averages.
