Metrics, Judges and Release Gates

No single score describes a generative AI feature. Separate measurable task outcomes, groundedness and safety, then treat any model-based judge as another fallible measurement that must be calibrated.

Precision and recallRAG metricsLLM judgeThresholds
1Learn→2Do→3CheckLearn 15 min · Do 15 min
1

Learn

Match each metric to a product risk.

Definition

A metric is a defined measurement over system outputs. Deterministic metrics include accuracy, precision, recall and latency. RAG evaluators may score relevance or groundedness using references or a judge model. A release gate compares measured results with pre-agreed thresholds; it does not make the underlying measure infallible.

In plain words

Decide what a bad answer means, choose a test that can detect it, and set a threshold before looking at the new score.

Imagine this

One test checks whether a cashier totals a receipt correctly; another checks whether the customer was charged twice. Passing the first does not prove the second.

In the real world

Microsoft Foundry provides built-in evaluators for general response quality, RAG relevance and groundedness, safety and agent task outcomes, and supports custom evaluators. Treat these as signals to combine with representative data and human review, especially for consequential outcomes. See the Foundry observability overview.

In finance

For a dispute answer, measure whether the cited article is relevant and whether the answer preserves the deadline's conditions. An ID check or number match alone does not establish semantic support; high-impact policy answers need a reviewed rubric and escalation path.

Traditional developer view

"The test has one exact expected output."

GenAI developer view

"Some checks are exact; others use a calibrated rubric, sampling and human review because multiple phrasings can be acceptable."

Common trap

Optimizing a judge score without checking human agreement or known failure cases. A judge can be overconfident, sensitive to wording or wrong about a policy condition.

Interview cue

"I report task-specific metrics and slices, calibrate model-based evaluators against human labels, and block releases on pre-agreed thresholds with the model, prompt and dataset versions recorded."

Drill 09.2

Set an explicit release threshold

~15 minPython · pytestoffline

Goal: make missing or below-threshold measurements visible as release failures.

  1. Run

    Threshold gate

    """Deterministic classification metrics and explicit release thresholds."""

import math
from collections.abc import Mapping, Sequence


def classification_metrics(
    expected: Sequence[str], predicted: Sequence[str], positive_label: str
) -> dict[str, float]:
    if not expected or len(expected) != len(predicted):
        raise ValueError("Expected and predicted labels must be non-empty and aligned")
    if not positive_label:
        raise ValueError("A positive label is required")

    true_positive = sum(
        actual == positive_label and guess == positive_label
        for actual, guess in zip(expected, predicted)
    )
    false_positive = sum(
        actual != positive_label and guess == positive_label
        for actual, guess in zip(expected, predicted)
    )
    false_negative = sum(
        actual == positive_label and guess != positive_label
        for actual, guess in zip(expected, predicted)
    )
    correct = sum(actual == guess for actual, guess in zip(expected, predicted))
    precision_denominator = true_positive + false_positive
    recall_denominator = true_positive + false_negative

    return {
        "accuracy": correct / len(expected),
        "precision": (
            true_positive / precision_denominator if precision_denominator else 0.0
        ),
        "recall": true_positive / recall_denominator if recall_denominator else 0.0,
    }


def release_gate(
    metrics: Mapping[str, float], minimums: Mapping[str, float]
) -> list[str]:
    """Return failed metric names; callers decide whether to block a release."""
    failures: list[str] = []
    for name, minimum in minimums.items():
        value = metrics.get(name)
        if (
            not isinstance(value, (int, float))
            or isinstance(value, bool)
            or not isinstance(minimum, (int, float))
            or isinstance(minimum, bool)
            or not math.isfinite(value)
            or not math.isfinite(minimum)
            or not 0.0 <= minimum <= 1.0
            or value < minimum
        ):
            failures.append(name)
    return failures
    import pytest

from app.evaluation import classification_metrics, release_gate


def test_classification_metrics_highlight_fraud_recall():
    actual = ["fraud", "fraud", "fees", "dispute"]
    predicted = ["fraud", "fees", "fraud", "dispute"]
    metrics = classification_metrics(actual, predicted, positive_label="fraud")
    assert metrics == {"accuracy": 0.5, "precision": 0.5, "recall": 0.5}


def test_release_gate_checks_each_declared_threshold():
    metrics = {"accuracy": 0.94, "fraud_recall": 0.82}
    assert release_gate(metrics, {"accuracy": 0.9, "fraud_recall": 0.8}) == []
    assert release_gate(metrics, {"accuracy": 0.9, "fraud_recall": 0.9}) == [
        "fraud_recall"
    ]


@pytest.mark.parametrize(
    ("expected", "predicted"),
    [([], []), (["fraud"], [])],
)
def test_metric_inputs_must_be_nonempty_and_aligned(expected, predicted):
    with pytest.raises(ValueError, match="non-empty and aligned"):
        classification_metrics(expected, predicted, positive_label="fraud")


def test_release_gate_fails_missing_and_nonfinite_metrics():
    assert release_gate({"accuracy": float("nan")}, {"accuracy": 0.9, "recall": 0.8}) == [
        "accuracy",
        "recall",
    ]

  2. Verify
    • Every required metric must exist and be finite.
    • A low fraud-recall score is reported even if accuracy passes.
    • Threshold values are product decisions supported by risk review, not universal defaults.
3

Check

Evaluators and thresholds.

1. Does a groundedness score prove that a financial answer is safe?

No. It is an evaluator signal; it can miss conditions, source errors or downstream harm. Combine tests, human review and application controls.

2. Should the threshold be chosen after seeing the candidate score?

Set it before comparison where possible. Post-hoc thresholds invite tuning to a result rather than the required risk level.

Takeaway

Measure separate risks with suitable methods. Calibrate judges, predefine release gates and retain human oversight for high-impact decisions.
