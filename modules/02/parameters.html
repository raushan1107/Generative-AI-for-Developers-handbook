Temperature and Other Generation Parameters

Generation parameters are the knobs on every API call. Some shape randomness, some cap length, and on reasoning models one decides how hard the model thinks. The knobs differ between models, so the drill doesn't just turn them; it discovers which ones your deployment actually has.

1

Learn

The knobs, and when to touch them.

Definition

Generation parameters control how tokens are selected and how much is generated: temperature and top_p shape sampling randomness, max_completion_tokens caps output length, stop sequences end generation early, and on reasoning models reasoning_effort controls how much internal reasoning happens before answering.

In plain words

Temperature is "how adventurous" (you implemented it in Drill 01.7). Max tokens is "how long, at most". Reasoning effort, on thinking models, is "how hard to think before speaking". Defaults are usually fine; change a knob for a reason.

ParameterWhat it doesTypical valuesWatch out for
temperatureSampling randomness0–0.3 extraction · ~0.7 chat · 1+ creativeMany reasoning models only accept the default and reject other values
top_pSample only from the top tokens covering probability pLeave at defaultChange temperature or top_p, not both
max_completion_tokensUpper limit on generated tokens, including hidden reasoningLongest valid answer plus marginToo low: finish_reason: length; some providers and older models use max_tokens
stopStrings that end generatione.g. ["\n\n"]Not supported on some reasoning models
reasoning_effortHow much the model thinks firstnone/low simple tasks; medium/high hard onesHigher effort = more hidden tokens, slower and costlier; values vary by model
seedBest-effort repeatable samplingAny integerNot a guarantee; not supported everywhere
nNumber of alternative answers1You pay for every alternative
Name check: reasoning models changed the knobs

With reasoning models (OpenAI o-series and GPT-5 and later, current Claude models), providers increasingly fix sampling for you. Azure's documentation lists temperature, top_p, penalties, logprobs and max_tokens as unsupported on most reasoning models, with reasoning_effort and max_completion_tokens as the controls instead. Current Claude models likewise reject non-default sampling values. Check your model's parameter table, or let Drill 02.7 check it for you.

Settings by task

TaskNon-reasoning modelReasoning model
Extract fields, classify a tickettemperature 0–0.2, small output capreasoning_effort none or low
Learner chattemperature ~0.5–0.7low for speed, medium for tricky policy questions
Course descriptions, sloganstemperature ~0.9–1.2default
Multi-step reasoning, codelow temperaturemedium or high
In the real world

Teams tune these per feature, not per app. The same product might run ticket classification at the lowest reasoning effort with a 50-token cap, chat at low effort, and a "deep analysis" button at high effort, because each feature trades quality, speed and cost differently. They keep the settings in configuration so they can change them without a release.

Common trap

"Set temperature to 0 and the output will be deterministic and correct." Neither is guaranteed. Low temperature makes answers more consistent, not more true, and providers don't promise identical outputs even at 0. For reliability, constrain the format (Module 03, 04) and evaluate (Module 09).

Interview cue

"Temperature controls randomness, not accuracy. On reasoning models the main knob is reasoning effort, and I always set an output token cap and check finish_reason."

Do

Turn the knobs, and find out which ones exist.

Before you run this code

Run every drill from your genai-labs folder with its virtual environment active. Two files must be there: .env (settings) and llm.py (the shared helper every drill imports). By default they use a free local model with Ollama: install Ollama, then ollama pull llama3.2; no key is needed. To use Azure OpenAI or OpenAI instead, change LLM_PROVIDER in .env.

Easiest: download the genai-labs starter kit (every helper, data file and drill script), unzip it, copy .env.example to .env, and run pip install -r requirements.txt. Full walkthrough: Helpers and smoke test.

llm.py
"""Shared helper for every drill: returns an OpenAI-compatible client for
Azure OpenAI (Microsoft Foundry), OpenAI or Ollama, chosen in .env."""
import os

from dotenv import load_dotenv
from openai import OpenAI

load_dotenv()  # reads .env from the current folder

PROVIDER = os.getenv("LLM_PROVIDER", "ollama").lower()   # default: a free local model (Ollama)


def get_client() -> OpenAI:
    if PROVIDER == "azure":
        # Azure OpenAI v1 API: the standard OpenAI client, pointed at your resource
        return OpenAI(
            base_url=os.environ["AZURE_OPENAI_BASE_URL"],
            api_key=os.environ["AZURE_OPENAI_API_KEY"],
        )
    if PROVIDER == "openai":
        return OpenAI()  # reads OPENAI_API_KEY
    if PROVIDER == "ollama":
        return OpenAI(base_url="http://localhost:11434/v1", api_key="ollama")
    raise ValueError(f"Unknown LLM_PROVIDER: {PROVIDER!r}")


# On Azure this is the DEPLOYMENT name; elsewhere it's the model name.
MODEL = {
    "azure": os.getenv("AZURE_OPENAI_DEPLOYMENT", "chat"),
    "openai": os.getenv("OPENAI_MODEL", "gpt-5.4-mini"),
    "ollama": os.getenv("OLLAMA_MODEL", "llama3.2"),
}.get(PROVIDER, "")
Drill 02.7

Parameter playground: which knobs does your model have?

~15 minAzure OpenAIOllama recommended for temperature

Goal: try temperature, an output cap, a stop sequence and reasoning effort, and record which ones your deployment accepts. Rejections are part of the lesson.

  1. Run 
    """Drill 02.7: generation parameters, and which ones your model accepts."""
import openai

from llm import get_client, MODEL

client = get_client()


def try_call(label, prompt, **params):
    try:
        r = client.chat.completions.create(
            model=MODEL, messages=[{"role": "user", "content": prompt}], **params)
        c = r.choices[0]
        text = (c.message.content or "").strip().replace("\n", " ")
        print(f"  {label:26} -> {text[:70]!r}  [finish={c.finish_reason}, out={r.usage.completion_tokens}]")
    except openai.BadRequestError as e:
        print(f"  {label:26} -> REJECTED: {e.message[:90]}")


print("Temperature (3 samples each):")
for t in (0.0, 1.0, 1.8):
    for _ in range(3):
        try_call(f"temperature={t}", "Suggest a name for a new online cloud course. Name only.", temperature=t)

print("\nOutput cap:")
try_call("max_completion_tokens=40", "Explain what an exam voucher is in three paragraphs.", max_completion_tokens=40)

print("\nStop sequence:")
try_call("stop=['4.']", "List 5 cloud certifications, numbered 1. to 5., one per line.", stop=["4."])

print("\nReasoning effort (reasoning models only):")
for effort in ("low", "high"):
    try_call(f"reasoning_effort={effort}",
             "A course costs $1,200. The learner cancels 10 days before the start and gets 50% back, "
             "plus a $180 add-on refunded in full. Total refund? Number only.",
             reasoning_effort=effort)

  2. Verify

    Fill in your model's parameter card

    • Temperature: accepted or rejected? On a model that accepts it, 0.0 repeats the same name; 1.8 gives odd, sometimes broken names.
    • Output cap: finish=length. On a reasoning model the text may be empty, because all 40 tokens went to hidden reasoning. A too-small cap can silently eat the whole answer.
    • Stop: the list ends at item 3, if supported.
    • Reasoning effort: same answer ($780), several times more output tokens at high effort. You pay for thinking.

Remember: “Read your model's parameter table before you design around a knob. The API will tell you, loudly, if you don't.”

3

Check

Knobs.

1. You set temperature to 0.2 and get a 400 "unsupported value". Why, and what's the equivalent control?

It's a reasoning model that only accepts default sampling. Use reasoning_effort and max_completion_tokens, and get consistency from structured output and validation.

2. A classification call returns an empty string with finish_reason "length". What happened?

The output cap was too small: hidden reasoning tokens used it up before any visible answer. Raise the cap or lower reasoning effort.

Takeaway

Set parameters per feature, for a reason, and check that your model supports them.
