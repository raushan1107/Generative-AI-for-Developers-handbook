Error Handling

Some errors mean 'you did something wrong, fix it'; others mean 'not right now, try again'. Your code has to tell them apart, retry only the second kind, and always show users a calm message instead of a stack trace. You'll trigger every error on purpose, then build the tested mapper Milestone 2 relies on.

1

Learn

Fix it, or try again later?

Definition

LLM API errors fall into client errors (4xx: bad request, authentication, permission, not found, content policy) that won't succeed if repeated unchanged, and transient errors (429 rate limits, 5xx server errors, timeouts, connection failures) that often succeed on retry. A successful response can also signal a soft failure through finish_reason.

Imagine this

Calling a helpline. "Wrong department" (404) or "you don't have the right form" (400): calling again won't help; you need to change something. "All our lines are busy, please call later" (429, 503): call again, but not every two seconds, or you'll keep the lines busy for everyone.

In the real world

Mature AI products never show raw errors. They map failures to a calm message ("I'm having trouble right now, here's how to reach a human"), log the details with a request ID, alert on configuration errors, and fall back to a second model or region when the primary one is down. Status pages of the big providers show that outages and degradations do happen, so this isn't theoretical.

Common trap

One except Exception that retries everything. A wrong key gets retried forever; a too-long prompt gets retried until the user gives up. Retry only transient errors, and let configuration errors fail loudly in your logs.

Interview cue

"I split errors into retryable (429, 5xx, timeouts, connection) and non-retryable (400, 401, 403, 404), and treat finish_reason length or content_filter as failures even with HTTP 200."

Drill 02.10

Break it on purpose: read every kind of error

~10 minAzure OpenAIPython

Goal: trigger each class of failure, so you recognise the exception, status and message when they happen for real.

  1. Run 
    """Drill 02.10: break it on purpose and read the errors."""
import openai
from openai import OpenAI

from llm import get_client, MODEL

good = get_client()
hello = [{"role": "user", "content": "Hello"}]


def attempt(label, fn):
    try:
        fn()
        print(f"{label:30} OK")
    except openai.APIStatusError as e:          # the server answered with an error status
        print(f"{label:30} {type(e).__name__} (HTTP {e.status_code}): {str(e.message)[:70]}")
    except openai.APIConnectionError as e:      # no usable answer at all (includes timeouts)
        print(f"{label:30} {type(e).__name__}: {e}")


attempt("1. Wrong API key", lambda: OpenAI(base_url=good.base_url, api_key="wrong", max_retries=0)
        .chat.completions.create(model=MODEL, messages=hello))
attempt("2. Wrong deployment name", lambda: good.chat.completions.create(model="no-such-deployment", messages=hello))
attempt("3. Invalid parameter value", lambda: good.chat.completions.create(model=MODEL, messages=hello, temperature=5))
attempt("4. Unreachable endpoint", lambda: OpenAI(base_url="http://localhost:9/v1", api_key="x", max_retries=0)
        .chat.completions.create(model=MODEL, messages=hello))
attempt("5. Impossible timeout", lambda: good.with_options(timeout=0.001, max_retries=0)
        .chat.completions.create(model=MODEL, messages=hello))

# 6) Not an exception, but still a failure
r = good.chat.completions.create(model=MODEL, max_completion_tokens=30,
                                 messages=[{"role": "user", "content": "Write a long essay about cloud computing."}])
print(f"{'6. Truncated answer':30} HTTP 200, finish_reason={r.choices[0].finish_reason!r}")

Drill 02.11

Build a tested error-to-message mapper

~15 minAI assistant · pytestno API cost

Goal: one function that turns any SDK exception into a decision (retry or not) and a kind message, with tests that need no network.

  1. Ask AI 
    Create friendly_errors.py with describe_error(exc) -> (code, retryable, user_message) for
exceptions from the openai Python SDK:
- RateLimitError -> "rate_limited", retryable
- APIConnectionError (this includes APITimeoutError) -> "unreachable", retryable
- BadRequestError -> "bad_request", not retryable
- AuthenticationError, PermissionDeniedError, NotFoundError -> "config", not retryable
- any other APIStatusError -> "server", retryable only if status_code >= 500
- anything else -> "unknown", not retryable
User messages must be friendly, mention "Traincrest Assist" where it fits, and never contain
technical details. Then write test_friendly_errors.py with pytest that constructs real SDK
exceptions using httpx.Request/httpx.Response (no network calls) and checks every mapping.
Run the tests.
    Why this prompt works: it gives the exact mapping table (no room for creative interpretation), a known gotcha (timeouts are a subclass of connection errors, so order matters), and asks for tests that build real SDK exceptions offline, so the tests are fast and honest.
    Reference solution
    """Drill 02.11 (reference solution): turn SDK exceptions into decisions and kind messages."""
import openai

MESSAGES = {
    "rate_limited": "Traincrest Assist is very busy right now. Please try again in a moment.",
    "unreachable": "I couldn't reach the AI service. Please check your connection and try again.",
    "bad_request": "I couldn't process that message. Could you rephrase it?",
    "config": "Traincrest Assist is temporarily unavailable. Our team has been notified.",
    "server": "Something went wrong on our side. Please try again shortly.",
    "unknown": "Something unexpected happened. Please try again.",
}


def describe_error(exc):
    """Return (code, retryable, user_message) for an exception raised by the OpenAI SDK."""
    if isinstance(exc, openai.RateLimitError):
        code, retryable = "rate_limited", True
    elif isinstance(exc, openai.APIConnectionError):          # includes APITimeoutError
        code, retryable = "unreachable", True
    elif isinstance(exc, openai.BadRequestError):
        code, retryable = "bad_request", False
    elif isinstance(exc, (openai.AuthenticationError, openai.PermissionDeniedError, openai.NotFoundError)):
        code, retryable = "config", False
    elif isinstance(exc, openai.APIStatusError):
        code, retryable = "server", exc.status_code >= 500
    else:
        code, retryable = "unknown", False
    return code, retryable, MESSAGES[code]
    """Tests for friendly_errors.describe_error. Run with:  pytest -q test_friendly_errors.py"""
import httpx
import openai
import pytest

from friendly_errors import describe_error

REQUEST = httpx.Request("POST", "https://example.test/openai/v1/chat/completions")


def status_error(cls, status):
    return cls("boom", response=httpx.Response(status, request=REQUEST), body=None)


@pytest.mark.parametrize("exc, code, retryable", [
    (status_error(openai.RateLimitError, 429), "rate_limited", True),
    (status_error(openai.BadRequestError, 400), "bad_request", False),
    (status_error(openai.AuthenticationError, 401), "config", False),
    (status_error(openai.PermissionDeniedError, 403), "config", False),
    (status_error(openai.NotFoundError, 404), "config", False),
    (status_error(openai.InternalServerError, 503), "server", True),
    (openai.APITimeoutError(request=REQUEST), "unreachable", True),
    (openai.APIConnectionError(request=REQUEST), "unreachable", True),
])
def test_maps_sdk_errors(exc, code, retryable):
    got_code, got_retryable, message = describe_error(exc)
    assert (got_code, got_retryable) == (code, retryable)
    assert message and "Traceback" not in message and "deployment" not in message


def test_unknown_errors_are_not_retried():
    assert describe_error(ValueError("surprise"))[:2] == ("unknown", False)

3

Check

Errors.

1. Which should be retried automatically: 400, 401, 404, 429, 503, a timeout?

429, 503 and the timeout, with backoff. Not 400, 401 or 404: they need a change to the request or configuration.

2. Why must user-facing messages never include the raw error?

Raw errors leak internals (resource and deployment names, sometimes request details) and scare users. Log the details; show a calm message.

Takeaway

Retry what's transient, fix what's configuration, and keep every message human.
