Module 02 · Overview

Working with LLM APIs: Calling the Model Like a Professional

Traincrest Assist v0.1 worked until it didn't: it forgot names, froze while thinking and would crash on the first network blip. The fix isn't a better model. It's treating the LLM as what it really is: a slow, metered, rate-limited HTTPS API that sometimes fails. By the end of this module, v0.2 streams in a browser and survives failures.

9 topics15 drillsMilestone 2≈ 5 hours hands-on

The mental map

Every LLM call in every app you'll ever build goes through four stages. In class I draw them as four circles and refuse to move on until everyone can say what goes wrong at each one.

An API like no other

You've called hundreds of REST APIs. An LLM API looks like one more: POST some JSON, get JSON back. Its behaviour breaks several assumptions you've built up over the years.

PropertyA typical REST APIAn LLM APIWhat it forces you to do
Latency50–200 ms1–30+ secondsStream, show progress, set generous timeouts
DeterminismSame request, same responseSame request, different responseValidate outputs; test with datasets, not one example
BillingPer call, or flatPer token; input and output priced differentlyCount tokens, cap output, watch prompt size
Rate limitsRequests per secondTokens per minute and requests per minuteBack off and retry; queue background work
StateOften session-basedStateless: resend the conversation every timeManage history yourself
"Success"200 means it worked200 can still be truncated, filtered or wrongCheck finish_reason; validate content
Imagine this

A normal API is a vending machine: press B4, get the same snack in a second, every time. An LLM API is a busy restaurant kitchen: your order takes a while, the dish tastes slightly different each time, the bill depends on how much you ordered, and on a Saturday night the kitchen says "come back in ten minutes". You don't stop going to the restaurant. You just order differently.

Traditional developer view

"It's an HTTP call. Wrap it in try/except, done."

GenAI developer view

"It's a slow, probabilistic, metered, rate-limited dependency. I design the UX for latency, the code for retries, the budget for tokens, and the tests for variability."

Lab kit for Module 02

  • You'll need: the genai-labs folder and your chat deployment; for Drill 02.12, permission to lower the deployment's tokens-per-minute limit temporarily; for Drill 02.3, the Azure CLI.
  • New packages: fastapi, uvicorn and pytest (already in requirements.txt).
  • Unit tests without an API: Drills 02.6, 02.11 and 02.13 have you build tested utilities (history trimming, error mapping, retries) that the milestone reuses.
  • Build: Milestone 2 turns Traincrest Assist into a FastAPI service with a streaming web chat.
