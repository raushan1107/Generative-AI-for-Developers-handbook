Rate Limits and Retries

Your deployment has a token budget per minute. Spend it and the API says 429, slow down. The right answer is to wait a bit, then longer, with a little randomness, so a thousand clients don't retry at the same instant. You'll hit a real 429, then write the reusable retry decorator.

1

Learn

Wait longer each time, never in lockstep.

Definition

Rate limits cap how much a client can use an endpoint in a time window, typically as tokens per minute (TPM) and requests per minute (RPM). Exceeding them returns HTTP 429. Exponential backoff with jitter retries after progressively longer, randomised waits.

Imagine this

A toll plaza with a fixed number of booths. When the queue is full, cars are turned back. If every turned-back car returns at exactly the same moment, the jam repeats. If each driver waits a different, growing amount of time (one minute, then two, then four, plus a random few seconds), the traffic smooths out. That random few seconds is the jitter.

Facts worth remembering

  • On Azure you assign TPM per deployment within your quota, and an RPM limit is derived from it. Limits count the maximum output tokens you request, so a huge max_completion_tokens eats budget even if unused.
  • Responses carry headers like x-ratelimit-remaining-tokens; 429s often include retry-after.
  • The OpenAI and Anthropic Python SDKs already retry 408, 409, 429 and 5xx twice with backoff by default. Tune max_retries; don't wrap a second blind retry loop around it.
  • For bulk work (summarising 25,000 tickets), don't retry harder: queue it and process at a steady rate, or use a batch API (Modules 08, 11).
In the real world

Provider limits are tiered: new accounts get small limits that grow with usage and spend, and capacity for popular models can be scarce at peak times. Production teams monitor TPM utilisation, keep separate deployments (or quotas) for interactive and batch traffic, and use a gateway to spread load across regions or deployments when one is saturated.

Traditional developer view

"429? Retry in a loop until it works."

GenAI developer view

"429 is a capacity signal. Retry interactive calls with backoff and jitter, size TPM for peak traffic, cap output tokens, and move bulk work to a queue or batch."

Interview cue

"I handle 429s with exponential backoff plus jitter, honouring retry-after, with a cap on attempts, and I separate interactive traffic from batch work."

"""Shared helper for every drill: returns an OpenAI-compatible client for
Azure OpenAI (Microsoft Foundry), OpenAI or Ollama, chosen in .env."""
import os

from dotenv import load_dotenv
from openai import OpenAI

load_dotenv()  # reads .env from the current folder

PROVIDER = os.getenv("LLM_PROVIDER", "ollama").lower()   # default: a free local model (Ollama)


def get_client() -> OpenAI:
    if PROVIDER == "azure":
        # Azure OpenAI v1 API: the standard OpenAI client, pointed at your resource
        return OpenAI(
            base_url=os.environ["AZURE_OPENAI_BASE_URL"],
            api_key=os.environ["AZURE_OPENAI_API_KEY"],
        )
    if PROVIDER == "openai":
        return OpenAI()  # reads OPENAI_API_KEY
    if PROVIDER == "ollama":
        return OpenAI(base_url="http://localhost:11434/v1", api_key="ollama")
    raise ValueError(f"Unknown LLM_PROVIDER: {PROVIDER!r}")


# On Azure this is the DEPLOYMENT name; elsewhere it's the model name.
MODEL = {
    "azure": os.getenv("AZURE_OPENAI_DEPLOYMENT", "chat"),
    "openai": os.getenv("OPENAI_MODEL", "gpt-5.4-mini"),
    "ollama": os.getenv("OLLAMA_MODEL", "llama3.2"),
}.get(PROVIDER, "")
Drill 02.12

Hit a real 429 and recover with backoff

~15 minAzure OpenAI · FoundryPython

Goal: read your remaining budget from headers, trigger a real 429, and recover with your own backoff.

  1. Portal

    In Foundry, open your chat deployment, choose Edit, and lower tokens per minute to about 1K–2K. You'll restore it at the end.

  2. Run 
    """Drill 02.12: rate-limit headers, a real 429, and exponential backoff with jitter."""
import random
import time

import openai

from llm import get_client, MODEL

client = get_client().with_options(max_retries=0)   # SDK retries off, so we see the 429s

# A) How much budget is left? Read the headers.
raw = client.chat.completions.with_raw_response.create(
    model=MODEL, messages=[{"role": "user", "content": "Hi"}])
for h in ("x-ratelimit-limit-tokens", "x-ratelimit-remaining-tokens",
          "x-ratelimit-limit-requests", "x-ratelimit-remaining-requests"):
    print(f"{h}: {raw.headers.get(h)}")
raw.parse()   # the normal response object is still available


# B) Our own retry loop
def call_with_backoff(messages, max_attempts=6, base=1.0, cap=30.0):
    for attempt in range(1, max_attempts + 1):
        try:
            return client.chat.completions.create(model=MODEL, messages=messages)
        except (openai.RateLimitError, openai.InternalServerError, openai.APIConnectionError) as e:
            if attempt == max_attempts:
                raise
            response = getattr(e, "response", None)
            retry_after = response.headers.get("retry-after") if response is not None else None
            wait = float(retry_after) if retry_after else min(cap, base * 2 ** (attempt - 1))
            wait += random.uniform(0, wait * 0.25)   # jitter: don't retry in lockstep
            print(f"   attempt {attempt}: {type(e).__name__}, waiting {wait:.1f}s")
            time.sleep(wait)


# C) Spend the budget fast to trigger 429s
print()
for i in range(12):
    r = call_with_backoff([{"role": "user", "content": "Write 150 words about cloud certifications."}])
    print(f"request {i + 1:2} ok · {r.usage.total_tokens} tokens")

Drill 02.13

Write a tested retry decorator with backoff and jitter

~15 minAI assistant · pytestno API cost

Goal: turn the loop from Drill 02.12 into a reusable decorator, with tests that run in milliseconds because the sleep is injected.

  1. Your prompt 
    Goal:        retry.py with a decorator retry(...) and test_retry.py
Context:     generic: it retries any function that raises the given exception types
Constraints: parameters …; wait formula …; jitter …; cap …; re-raise after …;
             make the sleep function injectable so tests don't actually sleep
Done when:   pytest passes tests for: success after failures, giving up, not retrying
             other exceptions, and the cap

    Hint: the key design trick is sleep=time.sleep as a parameter. Tests pass sleep=waits.append and then assert on the recorded waits.

    Compare with my prompt
    Write retry.py with a decorator retry(retry_on, max_attempts=5, base=1.0, cap=30.0,
sleep=time.sleep). It retries the wrapped function when it raises one of retry_on. Between
attempts it waits min(cap, base * 2**(attempt-1)) seconds plus random jitter of up to 25% of
that wait, and re-raises the last exception after max_attempts. Use functools.wraps. Then write
test_retry.py (pytest) that injects sleep=waits.append so nothing really sleeps, and tests:
succeeds after 2 failures with waits in [1, 1.25] and [2, 2.5]; gives up after max_attempts;
does not retry other exception types; waits never exceed cap * 1.25. Run the tests.
    Reference solution
    """Drill 02.13 (reference solution): a reusable retry decorator with exponential backoff and jitter."""
import functools
import random
import time


def retry(retry_on, max_attempts=5, base=1.0, cap=30.0, sleep=time.sleep):
    """Retry the wrapped function when it raises one of the `retry_on` exceptions.

    Waits base * 2**(attempt-1) seconds (never more than `cap`) plus up to 25% random
    jitter between attempts, and re-raises after `max_attempts`. `sleep` is injectable
    so tests can run instantly.
    """
    def decorator(fn):
        @functools.wraps(fn)
        def wrapper(*args, **kwargs):
            for attempt in range(1, max_attempts + 1):
                try:
                    return fn(*args, **kwargs)
                except retry_on:
                    if attempt == max_attempts:
                        raise
                    wait = min(cap, base * 2 ** (attempt - 1))
                    sleep(wait + random.uniform(0, wait * 0.25))
        return wrapper
    return decorator
    """Tests for retry.retry. They never call a real API and run in milliseconds.
Run with:  pytest -q test_retry.py"""
import pytest

from retry import retry


class Flaky(Exception):
    pass


def test_succeeds_after_transient_failures():
    calls, waits = [], []

    @retry(Flaky, max_attempts=4, base=1, sleep=waits.append)
    def sometimes():
        calls.append(1)
        if len(calls) < 3:
            raise Flaky()
        return "ok"

    assert sometimes() == "ok"
    assert len(calls) == 3
    assert len(waits) == 2
    assert 1 <= waits[0] <= 1.25 and 2 <= waits[1] <= 2.5   # exponential, plus jitter


def test_gives_up_after_max_attempts():
    calls = []

    @retry(Flaky, max_attempts=3, sleep=lambda s: None)
    def always_fails():
        calls.append(1)
        raise Flaky()

    with pytest.raises(Flaky):
        always_fails()
    assert len(calls) == 3


def test_does_not_retry_other_errors():
    calls = []

    @retry(Flaky, sleep=lambda s: None)
    def wrong_input():
        calls.append(1)
        raise ValueError("bad request")

    with pytest.raises(ValueError):
        wrong_input()
    assert len(calls) == 1


def test_wait_is_capped():
    waits = []

    @retry(Flaky, max_attempts=8, base=10, cap=30, sleep=waits.append)
    def always_fails():
        raise Flaky()

    with pytest.raises(Flaky):
        always_fails()
    assert max(waits) <= 30 * 1.25

Check

Limits.

1. Why add random jitter to backoff waits?

So many clients that failed together don't retry together and cause the same overload again.

2. A nightly job summarising 25,000 tickets keeps hitting 429s and slowing the chat. What do you change?

Move it to a queue or batch API with a steady processing rate, ideally on separate capacity, instead of retrying harder.

Takeaway

Back off politely, honour retry-after, and keep bulk work out of the interactive lane.
