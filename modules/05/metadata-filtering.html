Metadata Filtering

Meaning isn't the only rule. A learner wants a beginner course under $500; a German learner needs German articles; a company must only see its own documents. Metadata filters apply those hard rules, and where you apply them matters: filter after ranking and you can end up with nothing at all. You'll see it happen.

1

Learn

Similarity ranks; filters rule.

Definition

Metadata filtering restricts a vector search to items whose structured fields meet exact conditions (for example level eq 'beginner' and price_usd le 500). With pre-filtering the condition is applied before or during the nearest-neighbour search, so you get the top k among matching items. With post-filtering you take the top k first and then drop non-matching items, which can leave fewer than k, or none.

In plain words

Embeddings handle "sounds like what I want". Filters handle "must be true": price, level, language, date, owner. You need both, and the filter should come first.

Imagine this

House hunting. You tell the agent "something cosy near a park, under $400,000". A good agent first sets aside everything over budget, then shows the three cosiest in what's left. A careless one picks the three cosiest houses in town, then crosses off the ones you can't afford, and ends up showing you nothing.

What metadata to store

FieldExample filterWhy
Category, level, formatlevel eq 'beginner'User choices in the UI
Price, dateprice_usd le 500, updated ge 2026-01-01Budgets and freshness
Language, regionlanguage eq 'es'Answer from the right version of a document
Kind of documentkind eq 'help'One index, several collections (Milestone 5 does this)
Tenant, permission groupgroup_ids/any(g: search.in(g, 'sales,all'))Security trimming: users only retrieve what they may see (Module 10)
  • Azure AI Search: mark fields filterable=True in the index, then pass an OData expression as filter=. For vector queries, filters are applied before the vector search by default.
  • Chroma: pass where={"$and": [{"level": "beginner"}, {"price_usd": {"$lte": 500}}]}.
  • Never build filter strings from raw user text. Map UI choices or enum values to filters in code; a filter is a query language, and injection applies.
In the real world

Enterprise "search your company's documents" products rely on security trimming: every chunk carries the groups allowed to see it, and every query adds a filter for the signed-in user's groups. Without it, a semantic search happily retrieves the salary spreadsheet for anyone who asks about pay.

Traditional developer view

"Filtering is a WHERE clause; I'll add it at the end."

GenAI developer view

"Filters change which neighbours exist. I store the fields I'll need, filter before ranking, and use filters for permissions, not just preferences."

Common trap

Asking the model to "only use beginner courses" instead of filtering. It might comply; it might not. Hard rules belong in the query as filters, where they are guaranteed.

Interview cue

"I store filterable metadata with each vector and apply pre-filters so the top k are the best among items that satisfy the rules. Filters also enforce security trimming, so retrieval only returns documents the user is allowed to see."

Drill 05.8

Pre-filter vs post-filter

~15 minAzure OpenAIAzure AI Search optional

Goal: run the same search three ways (no filter, post-filter, pre-filter) and see why the order matters.

  1. Run

    With your Drill 05.4 vector store

    """Drill 05.8: metadata filters. Filter BEFORE ranking (pre-filter) or AFTER (post-filter)?"""
from catalogue import COURSES
from embed import embed
from vector_store import VectorStore, matches

store = VectorStore()
texts = [f"{c['title']}. {c['description']}" for c in COURSES]
store.add(ids=[c["id"] for c in COURSES], vectors=embed(texts), texts=[c["title"] for c in COURSES],
          metadatas=[{"level": c["level"], "format": c["format"], "price_usd": c["price_usd"]} for c in COURSES])

query = "hands-on course about AI and language models"
where = {"level": "beginner", "price_usd": {"$lte": 500}}
q = embed([query])[0]


def show(title, hits):
    print(title)
    for h in hits:
        m = h["metadata"]
        print(f"  {h['score']:.2f}  {h['id']}  {h['text']:<40} {m['level']:<13} ${m['price_usd']}")
    if not hits:
        print("  (nothing left)")


print(f"query: {query!r}\nfilter: {where}\n")
show("No filter, top 3:", store.search(q, k=3))
show("\nPost-filter (top 3 first, then filter):", [h for h in store.search(q, k=3) if matches(h["metadata"], where)])
show("\nPre-filter (filter first, then top 3):", store.search(q, k=3, where=where))

  2. Verify

    The same filter on Azure AI Search

    If you built the index in Drill 05.5, the filter is an OData expression on filterable fields:

    $ python lab05_05_azure_search.py query "hands-on course about AI and language models" --mode vector --filter "level eq 'beginner' and price_usd le 500"
    • Azure returns three beginner courses under $500: it pre-filters vector queries by default.
    • Try a filter on a field that isn't filterable, like title eq 'x': the service rejects it. Filterability is decided when you design the index.
  3. Think

    Where should the filter values come from?

    In Milestone 5 the model calls search_courses(query, level, max_price_usd, format). Who decides those filter values, and how do they become a filter safely?

    Compare with my answer

    The model extracts them from the conversation ("beginner", "under $500"), but only as typed arguments: level is a Literal enum and max_price_usd an integer, validated by Pydantic. Code then builds the filter from those values, never by pasting text into a filter string. Permission filters (Module 10) never come from the model at all: they come from the signed-in user, like identity in Module 04.

3

Check

Filters.

1. Post-filtering returned 1 result instead of 5. Two fixes?

Switch to pre-filtering (filter inside the search), or over-fetch (ask for many more than k, then filter), which is wasteful and still not guaranteed.

2. Why is a filter better than telling the model "only use documents for the Sales team"?

A filter guarantees the rule: other documents never reach the model. An instruction is a request the model may not follow, and it still exposes the documents to the model.

Takeaway

Store the fields you'll need, filter before ranking, build filters from typed values, and let filters enforce permissions.
