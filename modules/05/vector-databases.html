Vector Databases

You could keep vectors in a Python list and compare against every one. That works for a few thousand items, and you'll build exactly that first, with tests. Then you'll move the catalogue into a real vector database, Azure AI Search, which adds fast approximate search, filters, keyword search and persistence. This page holds the module's hands-on exercise.

1

Learn

A list of vectors is a prototype. A vector database is a product.

Definition

A vector database (or a search service with vector support) stores embeddings together with their text and metadata, and answers nearest-neighbour queries quickly at scale, usually with an approximate nearest neighbour (ANN) index such as HNSW. Most also provide metadata filtering, keyword (full-text) search, hybrid ranking, persistence, updates and access control.

In plain words

Comparing a question with every stored vector is like reading every book in a library to find the right one. A vector index is the library's floor plan: go to the right section, then the right shelf, and only compare with the books there.

Imagine this

Finding the nearest open pharmacy. You could measure the distance to every pharmacy in the country (exact, slow). Or you could check your neighbourhood first, then the next one out (approximate, fast, and almost always right). HNSW works like that: a layered map of shortcuts, from "roughly the right region" down to "the closest few".

What a vector database adds

NeedA Python listA vector database
Speed at millions of vectorsSlow (compare with all)ANN index (HNSW)
Survive a restartSave a file yourselfPersistent, replicated
Filter by level, price, languageWrite it yourselfFilterable fields, applied efficiently
Exact words and codesNoFull-text search and hybrid ranking
Add, update, delete one documentRebuild arraysUpsert and delete by key
Who can see whatNoKeys, roles, and per-document security filters

Options you'll meet

  • Azure AI Search: a managed search service with vector, full-text and hybrid search, filters, and an optional semantic ranker. The main track in this handbook. The Free tier (one per subscription) is meant for learning and is enough for these labs.
  • Vectors inside your existing database: Azure Cosmos DB, Azure Database for PostgreSQL with pgvector, Azure SQL. Good when the data already lives there.
  • Open source: Chroma (simple, local, great for prototypes), Qdrant, Milvus, Weaviate, and others.
In the real world

Most companies don't buy a "vector database" as a separate thing first. They add vector search to what they already run: a search service for the website, PostgreSQL for the product catalogue, Cosmos DB for user data. A dedicated vector database earns its place when the scale, latency or features demand it.

Traditional developer view

"Search is a separate team's problem; I just call the search API."

GenAI developer view

"Retrieval quality decides answer quality, so the index is part of my design: what goes in each record, which fields are filterable, how text is analysed for keywords, and how I re-index when content or the embedding model changes."

Common trap

Storing only vectors. When a search returns id=17, score=0.82 you still need the text to show or send to the model, and the metadata to filter. Store the vector with its text and the fields you'll filter on, in the same record.

Interview cue

"A vector database stores embeddings with text and metadata and serves approximate nearest-neighbour search, typically HNSW, plus filtering, hybrid keyword-and-vector ranking, persistence and access control. On Azure I'd use Azure AI Search, or vector support in the database that already holds the data."

import pytest

from vector_store import VectorStore, matches


@pytest.fixture
def store():
    s = VectorStore()
    s.add(ids=["refunds", "labs", "vouchers"],
          vectors=[[1, 0, 0], [0, 1, 0], [0.7, 0, 0.7]],
          texts=["Refund rules", "Lab extensions", "Exam vouchers"],
          metadatas=[{"topic": "billing", "words": 180}, {"topic": "labs", "words": 120},
                     {"topic": "exams", "words": 90}])
    return s


def test_nearest_first(store):
    hits = store.search([0.9, 0.1, 0.1], k=2)
    assert [h["id"] for h in hits] == ["refunds", "vouchers"]
    assert hits[0]["score"] > hits[1]["score"]


def test_length_does_not_matter(store):
    assert store.search([10, 0, 0], k=1)[0]["score"] == pytest.approx(1.0)


def test_filter_before_ranking(store):
    hits = store.search([1, 0, 0], k=3, where={"words": {"$lte": 120}})
    assert [h["id"] for h in hits] == ["vouchers", "labs"]


def test_matches_operators():
    meta = {"level": "beginner", "price_usd": 290}
    assert matches(meta, {"level": "beginner", "price_usd": {"$lte": 300}})
    assert not matches(meta, {"level": {"$in": ["advanced", "intermediate"]}})
    assert not matches(meta, {"format": "classroom"})          # missing field never matches


def test_save_and_load(store, tmp_path):
    store.save(tmp_path / "idx")
    again = VectorStore.load(tmp_path / "idx")
    assert again.search([0, 1, 0], k=1)[0]["text"] == "Lab extensions"
    Create vector_store.py so that #file:test_vector_store.py passes. Don't edit the tests. Use numpy only.

- VectorStore.add(ids, vectors, texts, metadatas=None): normalise each vector to length 1 and keep
  ids, texts and metadata in parallel lists.
- search(query_vector, k=3, where=None): cosine similarity via a dot product, apply the `where`
  filter BEFORE ranking, return dicts {id, score (rounded to 4 places), text, metadata}, best first.
- matches(metadata, where): every condition must hold; a plain value means equality; support
  $eq, $ne, $lt, $lte, $gt, $gte and $in; a missing field never matches.
- save(folder) / load(folder): vectors.npy plus items.json.
Run pytest -q test_vector_store.py.
    Why this prompt works: the tests define behaviour; the prompt adds the design choices that make it a correct vector store: normalising at insert time (so a dot product is cosine), filtering before ranking (topic 7 explains why), and storing text and metadata with each vector.
    Reference solution
    """Drill 05.4 reference solution: a tiny in-memory vector store (about 60 lines).
Good enough for a few thousand items; a vector database adds indexes (HNSW), scale,
persistence, security and filtering at speed. The ideas are the same."""
import json
from pathlib import Path

import numpy as np

OPS = {"$eq": lambda a, b: a == b, "$ne": lambda a, b: a != b, "$lt": lambda a, b: a < b,
       "$lte": lambda a, b: a <= b, "$gt": lambda a, b: a > b, "$gte": lambda a, b: a >= b,
       "$in": lambda a, b: a in b}


def matches(metadata: dict, where: dict | None) -> bool:
    """where={"level": "beginner", "price_usd": {"$lte": 500}}: every condition must hold."""
    for field, cond in (where or {}).items():
        value = metadata.get(field)
        conditions = cond if isinstance(cond, dict) else {"$eq": cond}
        for op, expected in conditions.items():
            if value is None or not OPS[op](value, expected):
                return False
    return True


class VectorStore:
    def __init__(self):
        self.ids, self.texts, self.metadatas = [], [], []
        self.vectors = np.zeros((0, 0), dtype=np.float32)

    def add(self, ids, vectors, texts, metadatas=None):
        v = np.asarray(vectors, dtype=np.float32)
        v = v / np.linalg.norm(v, axis=1, keepdims=True)     # unit length: dot product == cosine
        self.vectors = v if self.vectors.size == 0 else np.vstack([self.vectors, v])
        self.ids += list(ids)
        self.texts += list(texts)
        self.metadatas += list(metadatas or [{} for _ in ids])

    def search(self, query_vector, k=3, where=None):
        """Top-k by cosine similarity among items whose metadata matches `where` (pre-filtering)."""
        if not self.ids:
            return []
        q = np.asarray(query_vector, dtype=np.float32)
        scores = self.vectors @ (q / np.linalg.norm(q))
        allowed = [i for i in range(len(self.ids)) if matches(self.metadatas[i], where)]
        best = sorted(allowed, key=lambda i: -scores[i])[:k]
        return [{"id": self.ids[i], "score": round(float(scores[i]), 4), "text": self.texts[i],
                 "metadata": self.metadatas[i]} for i in best]

    def save(self, folder):
        folder = Path(folder)
        folder.mkdir(parents=True, exist_ok=True)
        np.save(folder / "vectors.npy", self.vectors)
        (folder / "items.json").write_text(json.dumps(
            {"ids": self.ids, "texts": self.texts, "metadatas": self.metadatas}, ensure_ascii=False), encoding="utf-8")

    @classmethod
    def load(cls, folder):
        folder, store = Path(folder), cls()
        store.vectors = np.load(folder / "vectors.npy")
        items = json.loads((folder / "items.json").read_text(encoding="utf-8"))
        store.ids, store.texts, store.metadatas = items["ids"], items["texts"], items["metadatas"]
        return store

Run:  python lab05_05_azure_search.py create

Needs AZURE_SEARCH_ENDPOINT, AZURE_SEARCH_API_KEY and an embedding deployment (AZURE_OPENAI_EMBED_DEPLOYMENT)."""
import argparse
import os

from azure.core.credentials import AzureKeyCredential
from azure.search.documents import SearchClient
from azure.search.documents.indexes import SearchIndexClient
from azure.search.documents.indexes.models import (HnswAlgorithmConfiguration, SearchableField, SearchField,
                                                   SearchFieldDataType, SearchIndex, SimpleField, VectorSearch,
                                                   VectorSearchProfile)
from azure.search.documents.models import VectorizedQuery

from catalogue import COURSES
from embed import embed

ENDPOINT = os.getenv("AZURE_SEARCH_ENDPOINT", "")
INDEX = os.getenv("AZURE_SEARCH_INDEX", "courses")
credential = AzureKeyCredential(os.getenv("AZURE_SEARCH_API_KEY", ""))


def build_index(dims: int) -> SearchIndex:
    fields = [
        SimpleField(name="id", type=SearchFieldDataType.String, key=True),
        SearchableField(name="title", type=SearchFieldDataType.String),
        SearchableField(name="description", type=SearchFieldDataType.String),
        SimpleField(name="level", type=SearchFieldDataType.String, filterable=True, facetable=True),
        SimpleField(name="format", type=SearchFieldDataType.String, filterable=True, facetable=True),
        SimpleField(name="price_usd", type=SearchFieldDataType.Int32, filterable=True, sortable=True),
        SearchField(name="contentVector", type=SearchFieldDataType.Collection(SearchFieldDataType.Single),
                    searchable=True, vector_search_dimensions=dims, vector_search_profile_name="vprofile"),
    ]
    vector_search = VectorSearch(
        algorithms=[HnswAlgorithmConfiguration(name="hnsw")],             # approximate nearest neighbours
        profiles=[VectorSearchProfile(name="vprofile", algorithm_configuration_name="hnsw")])
    return SearchIndex(name=INDEX, fields=fields, vector_search=vector_search)


def create():
    dims = embed(["dimension check"]).shape[1]
    SearchIndexClient(ENDPOINT, credential).create_or_update_index(build_index(dims))
    print(f"Index '{INDEX}' ready ({dims}-dimension vectors).")


def upload():
    vectors = embed([f"{c['title']}. {c['description']}" for c in COURSES])
    docs = [{**{k: c[k] for k in ("id", "title", "description", "level", "format", "price_usd")},
             "contentVector": v.tolist()} for c, v in zip(COURSES, vectors)]
    results = SearchClient(ENDPOINT, INDEX, credential).merge_or_upload_documents(documents=docs)
    print(f"Uploaded {sum(r.succeeded for r in results)}/{len(docs)} courses.")


def query(text: str, mode: str, filter_: str | None, k: int = 3):
    search = SearchClient(ENDPOINT, INDEX, credential)
    vector_queries = None
    if mode in ("vector", "hybrid"):
        vector_queries = [VectorizedQuery(vector=embed([text])[0].tolist(), k_nearest_neighbors=k,
                                          fields="contentVector")]
    results = search.search(
        search_text=text if mode in ("keyword", "hybrid") else None,   # hybrid = both, merged with RRF
        vector_queries=vector_queries, filter=filter_, top=k,
        select=["id", "title", "level", "price_usd"])
    print(f"{mode} search: {text!r}" + (f"  filter: {filter_}" if filter_ else ""))
    for r in results:
        print(f"  {r['@search.score']:.4f}  {r['id']}  {r['title']}  ({r['level']}, ${r['price_usd']})")


if __name__ == "__main__":
    ap = argparse.ArgumentParser()
    ap.add_argument("action", choices=["create", "upload", "query"])
    ap.add_argument("text", nargs="?", default="")
    ap.add_argument("--mode", choices=["keyword", "vector", "hybrid"], default="hybrid")
    ap.add_argument("--filter", default=None, help="OData filter, e.g. \"level eq 'beginner' and price_usd le 500\"")
    a = ap.parse_args()
    {"create": create, "upload": upload}.get(a.action, lambda: query(a.text, a.mode, a.filter))()

3

Check

Vector databases.

1. You have 3,000 help sections. Do you need a vector database?

Not for speed: exact search over 3,000 vectors is a fraction of a millisecond. You might still want one for persistence, filters, keyword search, updates and access control, which is usually why teams adopt one.

2. What does HNSW trade away, and why is that acceptable?

A tiny chance of missing the true nearest neighbour, in exchange for searching a few dozen vectors instead of millions. The occasional near-miss is usually the second-best match anyway, and retrieval returns several results.

3. Why store text and metadata alongside each vector?

Results must be shown or sent to the model (the text) and narrowed by business rules (the metadata, for filters). A vector on its own can't do either.

Takeaway

A vector store compares a query with stored vectors; a vector database does it fast, filtered, persistent and secure. Store every vector with its text and filterable fields.
