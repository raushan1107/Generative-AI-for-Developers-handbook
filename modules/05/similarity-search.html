Similarity Search: Top-k by Meaning

Similarity search is the query half of the pipeline: embed the question with the same model, find the k nearest vectors, and return their text. It's where users stop needing your vocabulary. It's also where a new failure appears: vector search never says 'no results'. You'll compare it with keyword search on queries real learners would type.

1

Learn

Ask in your words, find in theirs.

Definition

Similarity search (semantic search, vector search, k-nearest-neighbour search) retrieves the k stored items whose embeddings are most similar to the query's embedding, returning each item's text, metadata and similarity score.

In plain words

Turn the question into a vector, then fetch the k closest documents. "Cheap intro to containers" lands next to "Docker Quick Start: build, run and share container images", even though the words barely overlap.

Imagine this

A knowledgeable shop assistant. You say "something to keep my coffee hot on the commute" and they hand you three insulated travel mugs, though you never said "insulated", "travel" or "mug". They match what you mean to what they have. They also never say "we have nothing"; ask for a lawnmower in a coffee shop and you'll still be shown the closest thing, which is your cue to add a threshold.

Decisions you make

  • k (how many): a search page shows 5 to 10. RAG (Module 06) usually sends 3 to 8 chunks to the model: too few misses the answer, too many adds cost and noise.
  • Threshold: vector search always returns k results, even for nonsense. Decide what "no good match" looks like for your model (calibrated on real queries), or combine with keywords (topic 8).
  • What to embed: for courses, title plus description; for articles, chunks with their headings (topic 6). Whatever you embed is what can be found.
  • Query side: questions are short and documents long; that asymmetry is normal. Some models want a query prefix (topic 3).
In the real world

Shops, streaming services and job sites all run semantic search behind their search boxes now, usually blended with keyword search and business rules (in stock, in your region, popular). The "no results" page has become rare, which is good for users and dangerous for chatbots: a weak match passed to a model becomes a confident wrong answer.

Traditional developer view

"No matching rows means no results."

GenAI developer view

"Vector search always returns its nearest k. Relevance is a score I have to interpret, so I set k deliberately, watch the scores, and handle 'nothing good' explicitly."

Common trap

Passing the top results to a model without checking relevance. Ask TrainCrest's help sections about "Docker" and vector search returns Ways to pay as the best match (Drill 05.9 shows it). A chatbot would then answer a Docker question with payment details.

Interview cue

"Similarity search embeds the query with the same model as the corpus and returns the top-k nearest items with scores. I tune k for the use case and handle low-relevance results, because vector search never returns an empty set."

"""Shared helper for every drill: returns an OpenAI-compatible client for
Azure OpenAI (Microsoft Foundry), OpenAI or Ollama, chosen in .env."""
import os

from dotenv import load_dotenv
from openai import OpenAI

load_dotenv()  # reads .env from the current folder

PROVIDER = os.getenv("LLM_PROVIDER", "ollama").lower()   # default: a free local model (Ollama)


def get_client() -> OpenAI:
    if PROVIDER == "azure":
        # Azure OpenAI v1 API: the standard OpenAI client, pointed at your resource
        return OpenAI(
            base_url=os.environ["AZURE_OPENAI_BASE_URL"],
            api_key=os.environ["AZURE_OPENAI_API_KEY"],
        )
    if PROVIDER == "openai":
        return OpenAI()  # reads OPENAI_API_KEY
    if PROVIDER == "ollama":
        return OpenAI(base_url="http://localhost:11434/v1", api_key="ollama")
    raise ValueError(f"Unknown LLM_PROVIDER: {PROVIDER!r}")


# On Azure this is the DEPLOYMENT name; elsewhere it's the model name.
MODEL = {
    "azure": os.getenv("AZURE_OPENAI_DEPLOYMENT", "chat"),
    "openai": os.getenv("OPENAI_MODEL", "gpt-5.4-mini"),
    "ollama": os.getenv("OLLAMA_MODEL", "llama3.2"),
}.get(PROVIDER, "")
Drill 05.6

Keyword vs semantic search on the course catalogue

~15 minAzure OpenAIPython · numpy

Goal: run five realistic learner requests through a basic keyword search and a semantic search, and see where each one wins.

  1. Run 
    """Drill 05.6: keyword search vs semantic search over the course catalogue.
The learner's words rarely match the words on your course pages."""
import re

import numpy as np

from catalogue import COURSES
from embed import embed

STOP = set("a an and the to for of in on my me i i'm im want is it with how do can at be what".split())
QUERIES = [
    "I want my app to recognise objects in photos",
    "cheap intro to containers",
    "not a coder, want to use chat assistants better at work",
    "get certified as a cloud admin",
    "make answers come from our own documents",
]


def words(text):
    return {w for w in re.findall(r"[a-z0-9-]+", text.lower()) if w not in STOP}


def keyword_top(query):
    """Count shared words between the query and each course: what a basic search box does."""
    q = words(query)
    scores = [len(q & words(c["title"] + " " + c["description"])) for c in COURSES]
    best = int(np.argmax(scores))
    return (COURSES[best]["title"], scores[best]) if scores[best] else ("(no match)", 0)


texts = [f"{c['title']}. {c['description']}" for c in COURSES]
docs = embed(texts)
docs /= np.linalg.norm(docs, axis=1, keepdims=True)
qs = embed(QUERIES)
qs /= np.linalg.norm(qs, axis=1, keepdims=True)

for query, row in zip(QUERIES, qs @ docs.T):
    title, overlap = keyword_top(query)
    best = int(np.argmax(row))
    print(f"\n{query}")
    print(f"  keyword : {title}  ({overlap} shared words)")
    print(f"  semantic: {COURSES[best]['title']}  (cosine {row[best]:.2f})")

  2. Think

    Read the misses

    1. Why did keyword search pick Docker for "recognise objects in photos", and Machine Learning Essentials for "cloud admin"?
    2. Two queries tied. What do those queries have in common?
    3. Invent a query where you'd expect keyword search to beat semantic search.
    Compare with my answers
    1. One accidental shared word each time: "app" appears in the Docker description, and "as" (from "such as") in Machine Learning Essentials. AZ-900 shares "cloud" too, but with one word each, the first course in the list wins the tie. Keyword search counts words, not meaning.
    2. The learner happened to use the catalogue's own words ("documents", "work", "teams"). When vocabularies match, both methods work.
    3. Exact identifiers and rare terms: a course code like C113 (if it were in the text), an error code like LAB-503, a product name. Drill 05.9 tests exactly this, with some surprises.
3

Check

Similarity search.

1. A learner asks Traincrest Assist about something TrainCrest doesn't offer. What does vector search return?

Still the k nearest items, just with lower scores. The application must notice low relevance (threshold, keyword check, or the model being told to say "not covered") rather than present them as answers.

2. Why embed a course's title and description together, rather than only the title?

Titles are short and use internal names; descriptions contain the words and ideas learners use. What you embed is what can be found.

Takeaway

Embed the query with the same model, take the top k, and remember vector search never says "nothing found": that part is your job.
