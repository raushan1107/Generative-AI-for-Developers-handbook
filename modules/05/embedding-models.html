Embedding Models: Choosing and Using One

There are dozens of embedding models, and leaderboards rank them on other people's data. What matters is how well one finds the right answer in your data, in your users' languages, at a size and price you can live with. You'll compare settings on TrainCrest's own help questions and learn why switching models later means re-embedding everything.

1

Learn

Pick on your data, not on a leaderboard.

Definition

An embedding model is a neural network trained to map text (and sometimes images or code) to vectors so that related inputs are close together. Models differ in quality for a domain and language, dimensions, maximum input length, cost and where they run.

In plain words

All embedding models do the same job, like all translators do. Some are better with legal text, some with Spanish, some are cheaper, some run on your laptop. You choose by testing on your own material.

Imagine this

Choosing a map for a hiking trip. A world atlas, a country road map and a detailed trail map all show the same land at different detail, size and price. The best map isn't the most detailed one; it's the one that gets you to your trail without weighing down your bag.

The choices that matter

  • Quality on your data: build 20 to 50 real questions with known answers (like data/help_questions.json) and measure how often the right document comes first. That number beats any leaderboard.
  • Languages: if users write in Spanish and Hindi, test in Spanish and Hindi (Drill 05.2 showed a mostly-English model missing a Spanish paraphrase).
  • Dimensions and storage: 1,536 float32 numbers take about 6 KB, so a million chunks is about 6 GB of vectors before indexes. The text-embedding-3 models accept a dimensions parameter to return shorter vectors (for example 256) that keep most of the quality.
  • Input length: text-embedding-3 accepts up to 8,191 tokens per input, but retrieval usually works better on shorter, focused chunks (topic 6).
  • Task prefixes: some models (like nomic-embed-text) expect search_query: on questions and search_document: on documents. Skipping them still works, just less well.
  • Switching cost: changing model means re-embedding every document. Store the model name with the index and plan re-indexing like a database migration.
In the real world

Teams usually start with a cheap general model, build a small labelled test set from real user questions, and only move to a bigger or specialised model when the test set shows a real gain. Large indexes often use shortened vectors to cut storage and latency, accepting a small quality loss measured on that same test set.

Traditional developer view

"Pick the top model on the benchmark and move on."

GenAI developer view

"Benchmarks shortlist; my test set decides. I weigh hit rate against cost, size and languages, record the model with the index, and treat a model change as a migration."

Common trap

Changing the dimensions setting (or the deployment behind embed) for new documents only. Old and new vectors no longer match in size or space, and the index either errors or quietly returns nonsense. Any change to the model or its settings means rebuilding the whole index.

Interview cue

"I choose an embedding model by measuring retrieval on our own labelled questions, considering language coverage, dimensions (storage and latency), input limits and cost. Changing models requires re-embedding the corpus, so the model is versioned with the index."

"""Shared helper for every drill: returns an OpenAI-compatible client for
Azure OpenAI (Microsoft Foundry), OpenAI or Ollama, chosen in .env."""
import os

from dotenv import load_dotenv
from openai import OpenAI

load_dotenv()  # reads .env from the current folder

PROVIDER = os.getenv("LLM_PROVIDER", "ollama").lower()   # default: a free local model (Ollama)


def get_client() -> OpenAI:
    if PROVIDER == "azure":
        # Azure OpenAI v1 API: the standard OpenAI client, pointed at your resource
        return OpenAI(
            base_url=os.environ["AZURE_OPENAI_BASE_URL"],
            api_key=os.environ["AZURE_OPENAI_API_KEY"],
        )
    if PROVIDER == "openai":
        return OpenAI()  # reads OPENAI_API_KEY
    if PROVIDER == "ollama":
        return OpenAI(base_url="http://localhost:11434/v1", api_key="ollama")
    raise ValueError(f"Unknown LLM_PROVIDER: {PROVIDER!r}")


# On Azure this is the DEPLOYMENT name; elsewhere it's the model name.
MODEL = {
    "azure": os.getenv("AZURE_OPENAI_DEPLOYMENT", "chat"),
    "openai": os.getenv("OPENAI_MODEL", "gpt-5.4-mini"),
    "ollama": os.getenv("OLLAMA_MODEL", "llama3.2"),
}.get(PROVIDER, "")

Run:  python lab05_03_models.py                    (your EMBED_MODEL, full size)

import sys
import time
from pathlib import Path

import numpy as np

from embed import EMBED_MODEL, embed

ARTICLES = {p.stem: p.read_text(encoding="utf-8") for p in sorted((Path(__file__).parent / "data" / "help").glob("*.md"))}
QUESTIONS = {
    "Can I get my money back if I cancel next week?": "refunds-and-cancellations",
    "The sandbox won't start, what do I do?": "labs-and-sandboxes",
    "My certificate has a typo in my surname": "certificates",
    "Can my company pay in three parts?": "payments-and-invoices",
    "Do you offer captions for deaf learners?": "accessibility",
    "¿Cuánto tiempo es válido mi voucher de examen?": "exam-vouchers",
}


def run(dims=None, prefix=False):
    q_texts = [("search_query: " if prefix else "") + q for q in QUESTIONS]
    d_texts = [("search_document: " if prefix else "") + t for t in ARTICLES.values()]
    start = time.perf_counter()
    docs, qs = embed(d_texts, dimensions=dims), embed(q_texts, dimensions=dims)
    took = time.perf_counter() - start
    docs /= np.linalg.norm(docs, axis=1, keepdims=True)
    qs /= np.linalg.norm(qs, axis=1, keepdims=True)
    scores = qs @ docs.T
    names = list(ARTICLES)
    correct = 0
    label = f"{EMBED_MODEL} dims={docs.shape[1]}{' +prefix' if prefix else ''}"
    print(f"\n{label}   ({took:.1f}s, cached calls are instant)")
    for (q, expected), row in zip(QUESTIONS.items(), scores):
        best = names[int(np.argmax(row))]
        correct += best == expected
        print(f"  {'OK ' if best == expected else 'MISS'} {row.max():.2f}  {q[:46]:<46} -> {best}")
    print(f"  {correct}/{len(QUESTIONS)} questions matched the right article")


if __name__ == "__main__":
    if "--dims" in sys.argv:
        for d in sys.argv[sys.argv.index("--dims") + 1:]:
            run(dims=int(d))
    else:
        run(prefix="--prefix" in sys.argv)

  2. Think

    What did you learn, and what didn't you?

    1. Prefixes raised most scores but didn't change any answer. Is that an improvement?
    2. On Azure, did 256 dimensions get the same 6/6 as 1,536? What would you save at a million chunks?
    3. Is 6/6 on six questions enough to choose a model?
    Compare with my answers
    1. Higher scores alone aren't the goal; correct rankings are. A wider gap between the right article and the rest does make retrieval more robust on harder questions, so it's worth keeping, but prove it on a bigger set.
    2. If shortened vectors keep the same hits, you store about a sixth of the data (roughly 1 KB instead of 6 KB per chunk, about 5 GB saved per million chunks) and search faster.
    3. No. Six easy questions, each answered by a whole article, is a smoke test. Drill 05.7 uses 20 questions with a required phrase in the retrieved chunk; real projects use hundreds of real user questions.
3

Check

Choosing models.

1. Two models score 92% and 94% on a public leaderboard. How do you choose for TrainCrest?

Run both on TrainCrest's own labelled questions, in the languages learners use, and weigh the hit rate against cost, dimensions and hosting. Leaderboard gaps that small often vanish or reverse on your data.

2. You want to move from text-embedding-3-small to -large. What has to happen?

Re-embed every document with the new model, build a new index (dimensions change from 1,536 to 3,072), switch queries over at the same moment, and compare hit rates before and after.

Takeaway

Choose the embedding model with your own test set, version it with your index, and budget a re-index for every change.
