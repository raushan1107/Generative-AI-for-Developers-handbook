Foundation Models, and How to Choose One

The industry builds a few huge general models and everyone adapts them. Your real decision is which one to use for which job, and the honest answer comes from measuring, not from leaderboards. You'll race two models on a real bank support task and let the numbers decide.

1Learn→2Do→3CheckLearn 12 min · Do 20 min
1

Learn

Build once, adapt many times.

Definition

A foundation model is a large model trained on broad data that can be adapted, through prompting, grounding or fine-tuning, to a wide range of downstream tasks. LLMs such as the GPT, Claude, Llama and Phi families are foundation models.

In plain words

Instead of one model per task, there are a few huge general models, and everyone adapts them. The same model can summarise a ticket, write SQL, translate Spanish and draft an email. You choose a foundation model, then shape it with prompts and data.

Imagine this

A foundation model is a fresh graduate from a top university: broadly trained, quick to learn, not yet specialised. You don't send them back to university for every new task. You give them a brief (prompt), reference material (RAG) and, for long-term roles, some on-the-job training (fine-tuning).

The model landscape, simplified

TierExamples (at the time of writing)How you use it

Name check

Model names change every few months. In the last year Azure retired whole families and added new tiers such as GPT-5.6 Sol, Terra and Luna. Don't memorise names: learn the tiers, and check the Foundry model catalogue and its retirement schedule when you start a project.

How to choose: the questions that matter

QuestionWhy it mattersLeans towards
How hard is the task?Multi-step reasoning, tricky code and nuanced writing need capable modelsFrontier for hard reasoning; small for classify, extract, route
How fast must it answer?Chat users notice delays before the first wordSmall models, streaming, low reasoning effort
How many calls a day?Cost = volume × tokens × priceSmall models for high volume; route only hard cases up
How much context?Long documents need big windowsLarge-context models, or better retrieval
Which inputs?Images, audio, PDFsMultimodal models (next topic)
Where may data be processed?Regulation and contractsData Zone or regional deployments, or self-hosted open-weight
In the real world
In finance

Model choice in a bank has two extra questions: where the data goes and who signs off. Customer data often must stay in a region, so teams pick regional or data-zone deployments, or self-host an open-weight model for the most sensitive work. And under model risk management rules (for example SR 11-7 in the US, or similar guidance elsewhere), each model used for a business decision is inventoried, validated and monitored. In practice that pushes banks towards a short list of approved models, chosen per task from their own evaluation results, with the model name in configuration so a re-validated replacement can be swapped in.

Many products quietly use several models. GitHub Copilot, for example, lets you pick between models from different providers for chat. Production systems often route: a small, cheap model handles routine requests and a larger one handles the hard ones (Module 11). Teams pick models from their own evaluation results, because public benchmarks rarely match a company's actual tasks.

Traditional developer view

"Use the biggest, newest model. Best is best."

GenAI developer view

"Use the smallest model that passes my evaluation for this task, and keep the model name in configuration so I can switch when a better or cheaper one ships."

Interview cue

"How do you choose a model?" "Task difficulty, latency, cost at our volume, context length, modality and data residency, validated with an evaluation set on our own data."

Before you run this code

Run every drill from your genai-labs folder with its virtual environment active. Two files must be there: .env (settings) and llm.py (the shared helper every drill imports). By default they use a free local model with Ollama: install Ollama, then ollama pull llama3.2; no key is needed. To use Azure OpenAI or OpenAI instead, change LLM_PROVIDER in .env.

Easiest: download the genai-labs starter kit (every helper, data file and drill script), unzip it, copy .env.example to .env, and run pip install -r requirements.txt. Full walkthrough: Helpers and smoke test.

llm.py
"""Shared helper for every drill: returns an OpenAI-compatible client for
Azure OpenAI (Microsoft Foundry), OpenAI or Ollama, chosen in .env."""
import os

from dotenv import load_dotenv
from openai import OpenAI

load_dotenv()  # reads .env from the current folder

PROVIDER = os.getenv("LLM_PROVIDER", "ollama").lower()   # default: a free local model (Ollama)


def get_client() -> OpenAI:
    if PROVIDER == "azure":
        # Azure OpenAI v1 API: the standard OpenAI client, pointed at your resource
        return OpenAI(
            base_url=os.environ["AZURE_OPENAI_BASE_URL"],
            api_key=os.environ["AZURE_OPENAI_API_KEY"],
        )
    if PROVIDER == "openai":
        return OpenAI()  # reads OPENAI_API_KEY
    if PROVIDER == "ollama":
        return OpenAI(base_url="http://localhost:11434/v1", api_key="ollama")
    raise ValueError(f"Unknown LLM_PROVIDER: {PROVIDER!r}")


# On Azure this is the DEPLOYMENT name; elsewhere it's the model name.
MODEL = {
    "azure": os.getenv("AZURE_OPENAI_DEPLOYMENT", "chat"),
    "openai": os.getenv("OPENAI_MODEL", "gpt-5.4-mini"),
    "ollama": os.getenv("OLLAMA_MODEL", "llama3.2"),
}.get(PROVIDER, "")
Drill 01.11

Same prompt, two models: measure, then extend the benchmark

~20 minAzure OpenAIOllama · Claude (optional)

Goal: compare latency, tokens and quality on a real bank support task (an angry customer and an overdraft fee), then have your assistant turn the script into a small, repeatable benchmark.

Before you start: you need a second model. Deploy a larger model in the same Foundry resource (for example a "sol" tier or gpt-5.4) as chat-big, or have Ollama running. Add COMPARE_DEPLOYMENT=chat-big and/or COMPARE_WITH_OLLAMA=1 to .env.

  1. Run

    Race the models

    """Drill 01.11: one prompt, several models. Compare latency, tokens and quality."""
import os
import time

from openai import OpenAI

from llm import get_client, MODEL

targets = [("main", get_client(), MODEL)]
if os.getenv("COMPARE_DEPLOYMENT"):
    targets.append(("compare", get_client(), os.environ["COMPARE_DEPLOYMENT"]))
if os.getenv("COMPARE_WITH_OLLAMA") == "1":
    local = OpenAI(base_url="http://localhost:11434/v1", api_key="ollama")
    targets.append(("local", local, os.getenv("OLLAMA_MODEL", "llama3.2")))

PROMPT = ("A customer writes: 'You charged me a $29 overdraft fee! I was only $80 short for one night "
          "because my salary was late. Give it back now!!' RR Finance Bank's policy: $29 fee when overdrawn by "
          "more than $50 at the end of the day; one courtesy fee refund per account every 12 months, and this "
          "customer hasn't used it. Reply as a kind contact-centre agent in under 80 words.")

for label, client, model in targets:
    start = time.perf_counter()
    r = client.chat.completions.create(model=model, messages=[{"role": "user", "content": PROMPT}])
    secs = time.perf_counter() - start
    u = r.usage
    print(f"\n=== {label} · {model} · {secs:.1f}s · {u.prompt_tokens} in / {u.completion_tokens} out")
    print(r.choices[0].message.content.strip())
    $ python lab01_11_compare.py
    Real output with only Ollama configured (llama3.2 on a laptop CPU) 
    === main · llama3.2 · 17.7s · 119 in / 87 out
"I apologize for the concern, and I'm happy to help. I've checked our policy, and a $29 overdraft fee is standard for being overdrawn by more than $50, even if it's just for one night. We can't waive this fee, but I can offer you a courtesy fee refund per account, as per our policy. I can process this refund for you today, if you'd like."

    Run it twice (latency varies). Score each answer 1–5: follows the policy (explains the fee, offers the one courtesy refund instead of promising every fee back), kind tone, under 80 words. The answer above scores about 3: it gets the policy right but says "we can't waive this fee" and then offers to refund it, which would confuse a customer.

  2. Your prompt

    Turn it into a benchmark

    One run proves little. Ask your assistant to extend the script: several runs per model, averages, and a table you could paste into a design document.

    Goal:        extend #lab01_11_compare.py into …
Context:     it already builds a list of (label, client, model) targets
Constraints: N runs per model; measure …; estimate cost from …;
             keep the existing targets logic; no new dependencies
Done when:   it prints a markdown table with one row per model

    Hint: ask for --runs 3, averages of latency, input tokens and output tokens, an estimated cost using PRICE_IN_PER_M / PRICE_OUT_PER_M from .env, and the shortest answer printed under the table for a quick quality check.

    Compare with my prompt
    Extend #lab01_11_compare.py into a small benchmark. Keep the existing targets logic.
Add argparse with --runs (default 3). For each target, call the model --runs times with PROMPT
and record latency, prompt_tokens and completion_tokens. Then print a markdown table with
columns: target | model | avg latency (s) | avg tokens in | avg tokens out | est. $ per call,
where cost uses PRICE_IN_PER_M and PRICE_OUT_PER_M from .env (USD per 1M tokens, defaults
0.40 and 1.60). Under the table, print each target's first answer. No new dependencies.
  3. Verify
    • The table has one row per target and plausible numbers (latency in seconds, not milliseconds).
    • On a reasoning model, output tokens are much higher than the visible answer suggests: they include hidden reasoning tokens, which you pay for.
    • Decide: for this focused task, is the bigger model worth its cost and latency? Write one sentence, as you would in a design review.

3

Check

Model choice.

1. RR Finance Assist must classify 40,000 customer messages a month into 8 categories. Which tier first, and why?

A small, cheap model: focused task, high volume, latency matters. Validate on labelled samples and move up a tier only if it fails your quality bar.

2. Why keep the model name in configuration rather than in code?

Models are retired and replaced every few months. Configuration lets you switch or A/B test without a code change (and Module 12 adds model fallbacks).

Takeaway

The best model is the smallest one that passes your evaluation. Measure it.
