Generative AI vs Traditional AI/ML

GenAI didn't replace machine learning; it sits inside it. Knowing where it sits tells you when an LLM is the right tool, and when a classic model or a plain if-statement is faster, cheaper and more reliable. You'll prove it by racing the two on the same bank customer messages.

Learn

Russian dolls, and how to pick the right doll.

AspectTraditional MLGenerative AI (LLMs)
OutputA label, a number or a scoreOpen-ended content: text, code, images
TrainingYou train a model on your labelled dataYou usually use a pre-trained model through an API
Data neededHundreds to thousands of labelled examples per taskZero to a handful of examples, written in the prompt
Tasks per modelOneThousands
Speed and cost per predictionMilliseconds, almost freeHundreds of milliseconds to seconds, pay per token
Handles new wording or languagesPoorly, unless trained on themWell, out of the box
Main failureWrong predictionFluent, confident, wrong answer (hallucination)
In the real world
In finance

Card-fraud detection is the classic example of traditional ML in banking: a model scores every card payment in a few milliseconds from structured features (amount, merchant, country, time since the last payment), billions of times a year. Credit scoring is similar. Generative AI sits next to these systems, not in place of them: it reads the customer's free-text dispute, drafts the letter explaining a declined payment, or summarises an investigation for the fraud analyst. Regulators also expect lending and fraud decisions to be explainable, which a fixed, well-documented model makes much easier than a free-text answer.

Most production systems are hybrids. Card-fraud scoring and product recommendations are still classic ML because they need millisecond decisions on structured data at huge volume. LLMs sit on top for the language parts: explaining a decision to a customer, summarising a case for an analyst, understanding a free-text complaint. Search products work the same way: classic ranking finds results, a language model writes the summary.

Common trap

Using an LLM for everything. Calculating interest, validating an IBAN or an email address, checking whether a customer ID exists, sorting transactions by date: these have exact answers. Plain code does them perfectly, instantly and for free. Use the LLM for the fuzzy part (understanding the customer's message) and code for the exact part (looking up the account). Module 04 wires the two together.

Traditional developer view

"We need a model, so we need a data scientist, a labelled dataset and three months."

GenAI developer view

"A pre-trained model already understands language, so I can prototype with a prompt this afternoon. If volume, latency or cost demand it later, I can train a small classic model, using the LLM to help label the data."

Interview cue

"When would you not use an LLM?" Say: "When the task has an exact answer, needs millisecond latency at high volume, or is a narrow classification with plenty of labelled data. There, plain code or a small classic model is cheaper, faster and more predictable."

Before you run this code

Run every drill from your genai-labs folder with its virtual environment active. Two files must be there: .env (settings) and llm.py (the shared helper every drill imports). By default they use a free local model with Ollama: install Ollama, then ollama pull llama3.2; no key is needed. To use Azure OpenAI or OpenAI instead, change LLM_PROVIDER in .env.

Easiest: download the genai-labs starter kit (every helper, data file and drill script), unzip it, copy .env.example to .env, and run pip install -r requirements.txt. Full walkthrough: Helpers and smoke test.

llm.py
"""Shared helper for every drill: returns an OpenAI-compatible client for
Azure OpenAI (Microsoft Foundry), OpenAI or Ollama, chosen in .env."""
import os

from dotenv import load_dotenv
from openai import OpenAI

load_dotenv()  # reads .env from the current folder

PROVIDER = os.getenv("LLM_PROVIDER", "ollama").lower()   # default: a free local model (Ollama)


def get_client() -> OpenAI:
    if PROVIDER == "azure":
        # Azure OpenAI v1 API: the standard OpenAI client, pointed at your resource
        return OpenAI(
            base_url=os.environ["AZURE_OPENAI_BASE_URL"],
            api_key=os.environ["AZURE_OPENAI_API_KEY"],
        )
    if PROVIDER == "openai":
        return OpenAI()  # reads OPENAI_API_KEY
    if PROVIDER == "ollama":
        return OpenAI(base_url="http://localhost:11434/v1", api_key="ollama")
    raise ValueError(f"Unknown LLM_PROVIDER: {PROVIDER!r}")


# On Azure this is the DEPLOYMENT name; elsewhere it's the model name.
MODEL = {
    "azure": os.getenv("AZURE_OPENAI_DEPLOYMENT", "chat"),
    "openai": os.getenv("OPENAI_MODEL", "gpt-5.4-mini"),
    "ollama": os.getenv("OLLAMA_MODEL", "llama3.2"),
}.get(PROVIDER, "")
Drill 01.3

Train a classic classifier, then race it against an LLM

~20 minAzure OpenAIscikit-learn · AI assistant

Goal: feel the difference in data needs, speed, cost and robustness between classic ML and an LLM, on the same 12 bank customer messages.

  1. Run

    Create the shared ticket file

    This file holds 12 labelled test tickets and RR Finance Bank's house rules. Module 03 reuses it.

    """Synthetic RR Finance Bank contact-centre tickets (fictional bank, no real customer data).
Shared by drills in Module 01 and Module 03."""

CATEGORIES = ["card", "dispute", "fraud", "fees", "transfers", "loans", "account", "other"]

# RR Finance Bank house rules the model can't know unless you tell it:
#   - a charge the customer recognises but is wrong (twice, wrong amount, never delivered) is "dispute";
#     a charge they don't recognise at all is "fraud"
#   - asking for a fee to be refunded is "fees", even when it mentions a card or a transfer
TEST_TICKETS = [
    ("I was charged twice for the same flight on my credit card.", "dispute"),
    ("My debit card is missing, I think I left it in a taxi.", "card"),
    ("There's a $640 payment to a shop in another country I've never been to.", "fraud"),
    ("Why did you charge me $29? I was only overdrawn for one night.", "fees"),
    ("My transfer to my sister has been pending since Monday.", "transfers"),
    ("Can I take a payment holiday on my personal loan?", "loans"),
    ("I can't log in, the one-time code never arrives.", "account"),
    ("Do you have a branch open on Sundays?", "other"),
    ("Please refund the $45 fee you took for my international wire.", "fees"),
    ("Quiero bloquear mi tarjeta, me la robaron ayer.", "card"),
    ("The online shop charged me $89 but the order was cancelled.", "dispute"),
    ("Someone texted me a link and now money is missing from my savings.", "fraud"),
]

# Few-shot examples: different from the test tickets, covering the house rules.
FEW_SHOT_EXAMPLES = [
    ("The supermarket charged me twice for one shop.", "dispute"),
    ("I don't recognise a payment to an online casino.", "fraud"),
    ("Can you give me back the overdraft fee on my card account?", "fees"),
    ("My card was stolen at the gym.", "card"),
    ("How long does a wire to Canada take?", "transfers"),
]
  2. Your prompt

    Ask your assistant to generate training data

    Classic ML needs labelled examples. Instead of writing 40 by hand, have your AI assistant generate them. Write the prompt yourself:

    Goal:        create data/train_tickets.json with … labelled customer messages
Context:     the categories are in #tickets.py; the company is …
Constraints: format …; how many per category …; style …;
             must NOT copy or paraphrase the tickets in TEST_TICKETS
Done when:   …

    Hint: ask for a JSON array of objects with exactly text and label, 6 per category (48 total), short realistic messages, varied wording, English only (that's deliberate: you'll see why later), and a quick check you can run.

    Compare with my prompt
    Create data/train_tickets.json: a JSON array of 48 synthetic customer-support messages for
RR Finance Bank, a retail bank. Each item is {"text": ..., "label": ...} with exactly those
two keys. Use the 8 labels in CATEGORIES from #tickets.py, exactly 6 messages per label.
Follow the house rules in the comments of #tickets.py. No real names, card or account numbers. Messages should be short (5-20 words), realistic and varied in wording.
English only. Do not copy or paraphrase anything in TEST_TICKETS. Afterwards, give me a
one-line Python command that prints the count per label.

    If your assistant struggles, use the reference file: data/train_tickets.json.

  3. Verify

    Check the generated data before training on it

    $ python -c "import json,collections; d=json.load(open('data/train_tickets.json',encoding='utf-8')); print(len(d), collections.Counter(x['label'] for x in d))"
    • 48 rows, 6 per label, only the 8 known labels.
    • Skim 10 rows: are the labels actually right? Generated data can be wrong too.
  4. Run

    Race the two approaches

    """Drill 01.3: a classic ML classifier vs an LLM, on the same bank contact-centre tickets."""
import json
import time
from pathlib import Path

from sklearn.feature_extraction.text import TfidfVectorizer
from sklearn.linear_model import LogisticRegression
from sklearn.pipeline import make_pipeline

from llm import get_client, MODEL
from tickets import CATEGORIES, TEST_TICKETS

# ---------- 1) Classic ML: learn from labelled examples ----------
train = json.loads(Path("data/train_tickets.json").read_text(encoding="utf-8"))
texts = [t["text"] for t in train]
labels = [t["label"] for t in train]

start = time.perf_counter()
classifier = make_pipeline(TfidfVectorizer(ngram_range=(1, 2)), LogisticRegression(max_iter=1000))
classifier.fit(texts, labels)
train_secs = time.perf_counter() - start

start = time.perf_counter()
ml_preds = list(classifier.predict([text for text, _ in TEST_TICKETS]))
ml_secs = time.perf_counter() - start

# ---------- 2) LLM: no training, just an instruction ----------
client = get_client()
instruction = f"Classify the bank customer's message into one of: {', '.join(CATEGORIES)}. Reply with the category only."
llm_preds, tokens = [], 0
start = time.perf_counter()
for text, _ in TEST_TICKETS:
    r = client.chat.completions.create(model=MODEL, messages=[
        {"role": "system", "content": instruction},
        {"role": "user", "content": text},
    ])
    llm_preds.append(r.choices[0].message.content.strip().lower())
    tokens += r.usage.total_tokens
llm_secs = time.perf_counter() - start

# ---------- 3) Compare ----------
print(f"{'ticket':46} {'expected':13} {'classic ML':13} {'LLM':13}")
for (text, expected), ml, llm in zip(TEST_TICKETS, ml_preds, llm_preds):
    print(f"{text[:44]:46} {expected:13} {ml:13} {llm:13}")

n = len(TEST_TICKETS)
ml_ok = sum(p == e for p, (_, e) in zip(ml_preds, TEST_TICKETS))
llm_ok = sum(p == e for p, (_, e) in zip(llm_preds, TEST_TICKETS))
print(f"\nClassic ML: {ml_ok}/{n} correct · trained in {train_secs:.2f}s on {len(train)} examples · "
      f"all predictions in {ml_secs * 1000:.1f} ms · $0 per call")
print(f"LLM:        {llm_ok}/{n} correct · no training · {llm_secs:.1f}s for all · {tokens} tokens")

  5. Think

    Read the results like an engineer

    Answer before opening: (1) Why did classic ML miss the Spanish ticket and the "$45 fee for my international wire" ticket? (2) Why did the LLM mix up dispute and fraud? (3) RR Finance Bank gets 40,000 messages a month. Which approach would you put in production, and why?

    Compare with my answers
    1. Classic ML only knows the words it was trained on. The training data was English only, so the Spanish message was a guess; and "wire" appears in many transfers examples, so word statistics beat the meaning ("refund the fee"). The LLM understood Spanish and the fee request for free.
    2. "Money is missing after a text with a link" sounds like a payment problem, and "charged but the order was cancelled" mentions a card. RR Finance Bank's house rule (recognised but wrong = dispute; not recognised = fraud) decides which team handles it, and the bank's fraud team works to different deadlines. The LLM can't know a house rule you didn't tell it; Module 03 fixes this with clear instructions and few-shot examples. A small local model also makes more mistakes than a large hosted one: compare yours.
    3. It depends, and that's the real answer. The LLM is more robust to wording and language with zero training; classic ML is thousands of times faster and free per call. Banks have run classic models for card-fraud scoring for decades for exactly that reason. A common production pattern: an LLM to label historical tickets, then a small classic model for high-volume routing, with the LLM as a fallback for low-confidence cases.
3

Check

Pick the right tool.

1. RR Finance Bank wants to reject payment forms with an invalid IBAN (the checksum fails). LLM or code?

Code. It's an exact rule with a known answer. An LLM would be slower, cost money and occasionally be wrong.

2. Customers write free-text complaints in 12 languages and you have no labelled data. Classic ML or an LLM to start?

An LLM: no training data needed and it handles many languages. Revisit with classic ML later if volume and cost justify it.

Takeaway

The best GenAI developers are the ones who know when not to use GenAI.
