Monitoring, Incidents and Drift

A service can be available while its answers are wrong. Monitor both operational health and quality signals, define who responds, and control how feedback is used so the system does not learn from unreviewed harm.

Operational signalsQuality driftIncident runbookPrivacy
1Learn→2Do→3CheckLearn 15 min · Do 15 min
1

Learn

Availability is necessary, but it does not measure answer quality.

Definition

Operational monitoring tracks availability, latency, errors, capacity and cost. Quality monitoring samples or evaluates outputs for relevance, groundedness, safety and task success. Drift is a change in input patterns or system behavior that can reduce performance. An incident runbook defines detection, owner, containment, communication, recovery and review steps.

In plain words

Watch whether the app is running and whether it is still doing the right thing. Know who can stop it and what to do next.

Imagine this

A branch may be open on time but still route every fraud report to the wrong desk. Service uptime and service quality need different checks.

SignalExampleResponse question
Operationalp95 latency, error rate, token useCan customers use the service within the SLO?
QualityFraud recall, citation ID failures, review sampleIs the workflow still safe and useful?
SafetySecret-request indicators, unsafe escalation rateDoes the team need to disable or constrain a capability?
DriftNew language, merchants or policy changesDoes the evaluation set need new reviewed cases?
In the real world

Microsoft Foundry observability describes production monitoring for operational measures and quality signals, alongside tracing and evaluation. Use monitoring with service-specific alerts, a retention policy and human review of sampled outputs; do not treat dashboards as proof of correctness. See Microsoft Learn: generative AI observability.

In finance

If fraud recall drops after a prompt or product change, pause the affected route, preserve the release and evaluation records, notify the accountable operations and risk owners, and use the approved fallback or human-only path until reviewed.

Traditional developer view

"Alert when the API returns too many 500s."

GenAI developer view

"Also sample quality and safety, monitor input drift and know when a human must take over."

Common trap

Logging full prompts and responses to debug a quality issue. Start with trace IDs, versions, scores and carefully selected metadata; use a separate, access-controlled process for any content review.

Interview cue

"I alert on operational SLOs and quality regressions separately, use reviewed samples to detect drift, assign incident owners and keep a tested human-only or rollback path."

Drill 12.2

Evaluate operational health thresholds

~15 minPython · pytestoffline

Goal: detect latency, service errors and citation-ID failures that exceed configured limits or are not measured.

  1. Run

    Check health thresholds

    """Local release and health checks; these do not deploy or monitor Azure resources."""

import math
import re
from collections.abc import Mapping


_REQUIRED_ARTIFACTS = (
    "release_id",
    "model_deployment",
    "prompt_version",
    "evaluation_dataset",
    "image_digest",
    "rollback_image_digest",
)
_IMAGE_DIGEST = re.compile(r"^sha256:[0-9a-f]{64}$")
_HEALTH_METRICS = ("p95_latency_ms", "error_rate", "citation_id_failure_rate")


def validate_release_manifest(manifest: Mapping[str, str]) -> list[str]:
    failures = [
        name
        for name in _REQUIRED_ARTIFACTS
        if not isinstance(manifest.get(name), str) or not manifest[name].strip()
    ]
    for name in ("image_digest", "rollback_image_digest"):
        value = manifest.get(name, "")
        if isinstance(value, str) and value and not _IMAGE_DIGEST.fullmatch(value):
            failures.append(name)
    return failures


def health_failures(
    observed: Mapping[str, float], limits: Mapping[str, float]
) -> list[str]:
    failures: list[str] = []
    for name in _HEALTH_METRICS:
        value = observed.get(name)
        limit = limits.get(name)
        if (
            not isinstance(value, (int, float))
            or isinstance(value, bool)
            or not isinstance(limit, (int, float))
            or isinstance(limit, bool)
            or not math.isfinite(value)
            or not math.isfinite(limit)
            or value < 0
            or limit < 0
            or value > limit
        ):
            failures.append(name)
    return failures
    from app.release_checks import health_failures, validate_release_manifest


def test_release_requires_versioned_artifacts_and_rollback_digest():
    manifest = {
        "release_id": "2026-10-17.1",
        "model_deployment": "chat",
        "prompt_version": "assist_system@v6",
        "evaluation_dataset": "eval-2026-10-17",
        "image_digest": "sha256:" + "a" * 64,
        "rollback_image_digest": "sha256:" + "b" * 64,
    }
    assert validate_release_manifest(manifest) == []


def test_release_rejects_missing_or_malformed_artifacts():
    failures = validate_release_manifest(
        {"release_id": "r1", "image_digest": "latest"}
    )
    assert failures == [
        "model_deployment",
        "prompt_version",
        "evaluation_dataset",
        "rollback_image_digest",
        "image_digest",
    ]


def test_health_thresholds_report_each_regression():
    observed = {
        "p95_latency_ms": 1200,
        "error_rate": 0.03,
        "citation_id_failure_rate": 0.01,
    }
    limits = {
        "p95_latency_ms": 1000,
        "error_rate": 0.02,
        "citation_id_failure_rate": 0.02,
    }
    assert health_failures(observed, limits) == ["p95_latency_ms", "error_rate"]


def test_missing_health_measurement_fails_closed():
    assert health_failures({}, {}) == [
        "p95_latency_ms",
        "error_rate",
        "citation_id_failure_rate",
    ]

3

Check

Production operations.

1. What should the team do if the API is healthy but fraud recall falls?

Treat it as a quality incident: investigate the change, pause or roll back the affected path if required, and route cases to the approved human process.

2. Why should a feedback signal not automatically retrain or change the prompt?

Feedback may be noisy, malicious or unrepresentative. Review and label it before using it as evaluation or training data.

Takeaway

Monitor operations and quality separately, define owners and escalation paths, and keep sensitive content out of routine telemetry.
