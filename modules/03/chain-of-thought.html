Chain-of-Thought Considerations

Asking for intermediate steps can help on some tasks, but it does not guarantee a correct answer or a faithful account of the model's internal process. Some reasoning models use hidden reasoning tokens. You'll compare outputs on a refund case and verify the result independently.

1

Learn

Ask for an explanation when useful, then verify it.

Definition

Chain-of-thought (CoT) prompting asks a model to write intermediate steps before a final answer. It can help on some multi-step tasks, but results vary by task and model, and a generated explanation is not proof that the answer is correct. Some reasoning models use hidden reasoning tokens without returning those internal steps in the visible response; Azure OpenAI counts these tokens in the context window and bills them as output tokens.

Imagine this

Maths exams at school: "show your working". Written steps can help someone review a solution, but they don't guarantee the answer is right. Some reasoning models use hidden tokens that aren't returned as a readable transcript; in Azure OpenAI, these are billed as output tokens.

Model typeHow to get step-by-step reasoningWatch out for
Standard chat modelFor a learning exercise, you can ask for a brief explanation before the answer.Explanations can be incomplete or unfaithful; evaluate the answer separately.
Reasoning modelSome APIs expose an effort or thinking control. State the goal, constraints and output you need.Controls and usage accounting vary. Do not assume hidden reasoning is available or correct.

Rules for CoT in an application

  • Keep customer-facing output separate from internal records. Return the answer and any concise, evidence-based explanation you need; don't treat free-form reasoning as a verified trace.
  • Don't request long reasoning where it isn't needed. Classifying "charged twice" doesn't need five steps.
  • Reasoning isn't proof. Convincing steps can still be wrong. Verify critical results in code (dates, amounts) or with evaluation.
In the real world

Some reasoning-model APIs provide an effort or thinking control, while others use different parameters. For auditability, keep reproducible inputs, tool traces, cited evidence and a concise explanation; don't rely on raw chain-of-thought as evidence.

In finance

Fee and interest calculations, dispute deadlines and eligibility checks are multi-step problems, which is exactly where models can make confident mistakes. Banks can use a model to help interpret a case, but should keep authoritative arithmetic in tested code. For an audit trail, record the input, model and prompt versions, cited policy, tool calls, output and human decision; a generated chain of thought is not a verified record of how the model reached its answer.

Reasoning features and token accounting are model-specific. See the current OpenAI reasoning guide and Microsoft Foundry reasoning-model documentation.

Common trap

Treating raw reasoning as reliable internal notes or customer text. Return a concise explanation only when it is useful, and verify any factual claims in it.

Interview cue

"Step-by-step prompting can help on some multi-step tasks, but it doesn't prove correctness. Some reasoning models offer an effort control and don't return hidden reasoning. I verify critical results in code."

llm.py
"""Shared helper for every drill: returns an OpenAI-compatible client for
Azure OpenAI (Microsoft Foundry), OpenAI or Ollama, chosen in .env."""
import os

from dotenv import load_dotenv
from openai import OpenAI

load_dotenv()  # reads .env from the current folder

PROVIDER = os.getenv("LLM_PROVIDER", "ollama").lower()   # default: a free local model (Ollama)


def get_client() -> OpenAI:
    if PROVIDER == "azure":
        # Azure OpenAI v1 API: the standard OpenAI client, pointed at your resource
        return OpenAI(
            base_url=os.environ["AZURE_OPENAI_BASE_URL"],
            api_key=os.environ["AZURE_OPENAI_API_KEY"],
        )
    if PROVIDER == "openai":
        return OpenAI()  # reads OPENAI_API_KEY
    if PROVIDER == "ollama":
        return OpenAI(base_url="http://localhost:11434/v1", api_key="ollama")
    raise ValueError(f"Unknown LLM_PROVIDER: {PROVIDER!r}")


# On Azure this is the DEPLOYMENT name; elsewhere it's the model name.
MODEL = {
    "azure": os.getenv("AZURE_OPENAI_DEPLOYMENT", "chat"),
    "openai": os.getenv("OPENAI_MODEL", "gpt-5.4-mini"),
    "ollama": os.getenv("OLLAMA_MODEL", "llama3.2"),
}.get(PROVIDER, "")
Drill 03.7

Chain-of-thought on a multi-step overdraft-fee case

~15 minAzure OpenAIOllama shows the gap best

Goal: compare direct and step-by-step answers, and extract only the customer-facing part.

  1. Run 
    """Drill 03.7: direct answer vs step-by-step reasoning on a multi-step overdraft-fee case."""
import re

from llm import get_client, MODEL

client = get_client()

POLICY = """<policy>
- Account overdrawn by more than $50 at the end of the day: $29 fee per overdrawn payment, at most 3 fees per day.
- Account overdrawn by $50 or less at the end of the day: no fee.
- Fees charged against these rules are bank errors and are always refunded.
- Courtesy refund: one more overdraft fee per account every 12 months, on request.
</policy>"""

CASE = """<case>
Customer RR-10577 (Everyday Checking) was charged five $29 overdraft fees: four on 9 March, when
the account ended the day $212 overdrawn, and one on 10 March, when it ended the day $31 overdrawn.
They have not used a courtesy refund this year and ask for all $145 back.
</case>"""

DIRECT = f"{POLICY}\n{CASE}\nHow much should we refund? Answer in one sentence."
STEPWISE = f"""{POLICY}
{CASE}
Work through this inside <reasoning> tags: check each day against the fee rules, find any fees
charged in error, then apply the courtesy rule. Then give the customer-facing answer in one
sentence inside <answer> tags."""

for label, prompt in (("DIRECT", DIRECT), ("STEP BY STEP", STEPWISE)):
    r = client.chat.completions.create(model=MODEL, messages=[{"role": "user", "content": prompt}])
    text = r.choices[0].message.content.strip()
    print(f"\n===== {label} · {r.usage.completion_tokens} output tokens =====\n{text}")

# In an app, the customer sees only the <answer> part.
match = re.search(r"<answer>(.*?)</answer>", text, re.S)
print("\nShown to the customer:", match.group(1).strip() if match else "(no <answer> tag: handle this case!)")

  2. Verify

    Check against the correct answer

    9 March: the account ended the day more than $50 overdrawn, so fees apply, but at most 3: the fourth $29 fee was charged in error. 10 March: $31 overdrawn is $50 or less, so that $29 fee was charged in error too. Errors are always refunded: $58. The customer hasn't used the courtesy refund, so one more fee comes back: $29. Total $87, not the $145 requested; three fees of $29 on 9 March, minus the courtesy one, leave $58 that stands.

    • Compare both outputs with the known correct result; a reasoning model is not guaranteed to be right. Check hidden-token usage only when the provider exposes it.
    • On a small local model both can be wrong, as above. The direct answer simply repeated the customer's $145. Step by step found the two fees charged in error (with muddled reasoning about 9 March) and then mishandled the courtesy rule. It also forgot the closing </answer> tag, so the extraction code correctly refused to show anything.
    • "Shown to the customer" contains only the answer, never the reasoning, and nothing at all when the format is broken. That fallback is the most important line of the script.
  3. Think

    Which part of this task should never be left to the model in production?

    Compare with my answer

    The date arithmetic and the money. Code should apply the daily cap, the $50 threshold and the courtesy rule and compute "$87" exactly; the model should explain the result kindly. In Module 04 the model calls a fee_refund_quote() function instead of doing maths.

3

Check

Reasoning.

1. You ask a reasoning model to "think step by step" and print its reasoning to customers. What's wrong?

It already reasons internally, so you add visible tokens and cost; and reasoning isn't customer text. Keep reasoning separate from the answer, and tune reasoning_effort instead.

2. When is visible reasoning still useful?

For auditability and debugging: storing why a decision was suggested, for a human reviewer, not for the end user.

Takeaway

Let the model reason, keep the reasoning backstage, and let code do the exact maths.
