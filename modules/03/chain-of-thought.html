Chain-of-Thought Considerations

Because the model writes one token at a time, it 'thinks' by writing. Give it room to work step by step, or use a reasoning model that does it silently, and multi-step answers get better. You'll compare a direct and a step-by-step answer on a refund case, and keep the reasoning away from the learner.

1

Learn

Show your working, but not to the customer.

Definition

Chain-of-thought (CoT) prompting asks a model to produce intermediate reasoning steps before its final answer, which can improve accuracy on multi-step problems such as arithmetic, logic and policy application. Reasoning models perform this kind of reasoning internally before responding.

Imagine this

Maths exams at school: "show your working". A student who writes each step makes fewer mistakes, and when they're wrong the teacher can see where. Reasoning models are students who always do rough work on a hidden sheet: you see only the final answer, but you're charged for the sheet.

Model typeHow to get step-by-step reasoningWatch out for
Non-reasoning chat modelAsk for it: "Work through it step by step inside <reasoning>, then give the answer inside <answer>."More output tokens and latency; you must separate reasoning from the answer
Reasoning modelBuilt in. Raise reasoning_effort for harder problems; no need for "think step by step"Hidden reasoning tokens are billed. Over-prescribing steps can make results worse; state the goal and constraints instead.

Rules for CoT in an application

  • Separate thinking from answering. Reasoning in one field or tag, the final answer in another; show users only the answer.
  • Don't use visible CoT where it isn't needed. Classifying "charged twice" doesn't need five steps.
  • Reasoning isn't proof. Convincing steps can still be wrong. Verify critical results in code (dates, amounts) or with evaluation.
In the real world

Reasoning models made explicit CoT prompting far less necessary: products now expose an "effort" or "thinking" setting instead. Where teams still ask for visible reasoning, it's usually for auditability, for example storing why an AI recommended a refund decision for a human reviewer, never shown to the customer.

Common trap

Showing raw reasoning to the customer: "Step 1: the learner seems annoyed. Step 2: policy says no refund…". Reasoning is a working note for your system, not customer text.

Interview cue

"CoT helps on multi-step problems by giving the model room to reason. With reasoning models it's internal and controlled by reasoning effort. In apps I keep reasoning separate from the answer and verify critical results in code."

llm.py
"""Shared helper for every drill: returns an OpenAI-compatible client for
Azure OpenAI (Microsoft Foundry), OpenAI or Ollama, chosen in .env."""
import os

from dotenv import load_dotenv
from openai import OpenAI

load_dotenv()  # reads .env from the current folder

PROVIDER = os.getenv("LLM_PROVIDER", "ollama").lower()   # default: a free local model (Ollama)


def get_client() -> OpenAI:
    if PROVIDER == "azure":
        # Azure OpenAI v1 API: the standard OpenAI client, pointed at your resource
        return OpenAI(
            base_url=os.environ["AZURE_OPENAI_BASE_URL"],
            api_key=os.environ["AZURE_OPENAI_API_KEY"],
        )
    if PROVIDER == "openai":
        return OpenAI()  # reads OPENAI_API_KEY
    if PROVIDER == "ollama":
        return OpenAI(base_url="http://localhost:11434/v1", api_key="ollama")
    raise ValueError(f"Unknown LLM_PROVIDER: {PROVIDER!r}")


# On Azure this is the DEPLOYMENT name; elsewhere it's the model name.
MODEL = {
    "azure": os.getenv("AZURE_OPENAI_DEPLOYMENT", "chat"),
    "openai": os.getenv("OPENAI_MODEL", "gpt-5.4-mini"),
    "ollama": os.getenv("OLLAMA_MODEL", "llama3.2"),
}.get(PROVIDER, "")
Drill 03.7

Chain-of-thought on a multi-step refund case

~15 minAzure OpenAIOllama shows the gap best

Goal: compare direct and step-by-step answers, and extract only the customer-facing part.

  1. Run 
    """Drill 03.7: direct answer vs step-by-step reasoning on a multi-step policy case."""
import re

from llm import get_client, MODEL

client = get_client()

POLICY = """<policy>
- Cancel 14 or more days before the start date: 100% refund of the course fee.
- Cancel 7 to 13 days before the start date: 50% refund of the course fee.
- Cancel less than 7 days before: no refund, one free reschedule instead.
- Retake Pass add-on: refunded in full whenever the course is cancelled.
</policy>"""

CASE = """<case>
Enrolment TC-10577: 'Generative AI for Developers' starting on 20 March, course fee $1,200,
plus a Retake Pass bought for $180. On 9 March the learner cancels and asks for a full
refund of $1,380.
</case>"""

DIRECT = f"{POLICY}\n{CASE}\nHow much should we refund? Answer in one sentence."
STEPWISE = f"""{POLICY}
{CASE}
Work through this inside <reasoning> tags: count the days between the cancellation and the start,
find the matching rule for the course fee, then handle the add-on. Then give the customer-facing
answer in one sentence inside <answer> tags."""

for label, prompt in (("DIRECT", DIRECT), ("STEP BY STEP", STEPWISE)):
    r = client.chat.completions.create(model=MODEL, messages=[{"role": "user", "content": prompt}])
    text = r.choices[0].message.content.strip()
    print(f"\n===== {label} · {r.usage.completion_tokens} output tokens =====\n{text}")

# In an app, the learner sees only the <answer> part.
match = re.search(r"<answer>(.*?)</answer>", text, re.S)
print("\nShown to the learner:", match.group(1).strip() if match else "(no <answer> tag: handle this case!)")

    Then run it again with LLM_PROVIDER=ollama.

  2. Verify

    Check against the correct answer

    Cancelled on 9 March for a 20 March start: 11 days before, so the 7–13 day rule applies: 50% of $1,200 = $600. The Retake Pass is refunded in full: $180. Total $780, not the $1,380 requested.

    • On a reasoning model both versions are usually right; compare output tokens (hidden reasoning is included).
    • On a small local model the direct answer is often fooled by the learner's request or miscounts days; step by step does better.
    • "Shown to the learner" contains only the answer, never the reasoning.
  3. Think

    Which part of this task should never be left to the model in production?

    Compare with my answer

    The date arithmetic and the money. Code should compute "11 days, 50%, $780" exactly; the model should explain the result kindly. In Module 04 the model calls a refund_quote() function instead of doing maths.

3

Check

Reasoning.

1. You ask a reasoning model to "think step by step" and print its reasoning to learners. What's wrong?

It already reasons internally, so you add visible tokens and cost; and reasoning isn't customer text. Keep reasoning separate from the answer, and tune reasoning_effort instead.

2. When is visible reasoning still useful?

For auditability and debugging: storing why a decision was suggested, for a human reviewer, not for the end user.

Takeaway

Let the model reason, keep the reasoning backstage, and let code do the exact maths.
