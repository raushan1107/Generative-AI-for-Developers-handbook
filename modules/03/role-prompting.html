Role Prompting

Telling the model who it is changes how it talks. It doesn't change what it knows. 'You are TrainCrest's senior certification expert' doesn't give it TrainCrest's policies. You'll prove both halves of that sentence in one drill.

PersonaTone and audienceNot knowledgeDrill 03.3
1Learn→2Do→3CheckLearn 8 min · Do 12 min
1

Learn

The costume, not the script.

Definition

Role prompting assigns the model a persona or perspective (for example "You are a senior support agent at TrainCrest") to shape its tone, vocabulary, level of detail and focus for the task.

Imagine this

Give an actor a doctor's costume and they'll speak like a doctor, walk like a doctor and use the right words. You still wouldn't let them operate. The role is the costume. The knowledge has to come from the script you hand over: the context.

Roles help with

  • Tone and register (warm, formal, playful)
  • Audience level (learner vs engineer)
  • Perspective (reviewer, critic, tester)
  • A consistent persona across a conversation

Roles don't help with

  • Facts the model doesn't have
  • Accuracy on hard reasoning ("world-class mathematician" adds little)
  • A format you never specified
  • Security: a role is not a boundary
In the real world

Product assistants nearly always have a short persona ("You are Contoso's helpful billing assistant…"), but the bulk of their system prompt is rules, context and format. Roles are also used deliberately for perspective: teams ask one model to act as a strict code reviewer or a sceptical evaluator of another model's answer, which you'll see again in evaluation (Module 09).

Common trap

Three paragraphs of flattering persona ("the world's greatest, most experienced, award-winning…") and one line of actual task. Spend those words on context, constraints and examples instead.

Interview cue

"Role prompting shapes style and perspective, not knowledge. I use a short role in the system message and put the facts in the context."

Do

Four roles, same question.

Before you run this code

Run every drill from your genai-labs folder with its virtual environment active. Two files must be there: .env (settings) and llm.py (the shared helper every drill imports). By default they use a free local model with Ollama: install Ollama, then ollama pull llama3.2; no key is needed. To use Azure OpenAI or OpenAI instead, change LLM_PROVIDER in .env.

Easiest: download the genai-labs starter kit (every helper, data file and drill script), unzip it, copy .env.example to .env, and run pip install -r requirements.txt. Full walkthrough: Helpers and smoke test.

llm.py
"""Shared helper for every drill: returns an OpenAI-compatible client for
Azure OpenAI (Microsoft Foundry), OpenAI or Ollama, chosen in .env."""
import os

from dotenv import load_dotenv
from openai import OpenAI

load_dotenv()  # reads .env from the current folder

PROVIDER = os.getenv("LLM_PROVIDER", "ollama").lower()   # default: a free local model (Ollama)


def get_client() -> OpenAI:
    if PROVIDER == "azure":
        # Azure OpenAI v1 API: the standard OpenAI client, pointed at your resource
        return OpenAI(
            base_url=os.environ["AZURE_OPENAI_BASE_URL"],
            api_key=os.environ["AZURE_OPENAI_API_KEY"],
        )
    if PROVIDER == "openai":
        return OpenAI()  # reads OPENAI_API_KEY
    if PROVIDER == "ollama":
        return OpenAI(base_url="http://localhost:11434/v1", api_key="ollama")
    raise ValueError(f"Unknown LLM_PROVIDER: {PROVIDER!r}")


# On Azure this is the DEPLOYMENT name; elsewhere it's the model name.
MODEL = {
    "azure": os.getenv("AZURE_OPENAI_DEPLOYMENT", "chat"),
    "openai": os.getenv("OPENAI_MODEL", "gpt-5.4-mini"),
    "ollama": os.getenv("OLLAMA_MODEL", "llama3.2"),
}.get(PROVIDER, "")
Drill 03.3

What a role changes, and what it doesn't

~12 minAzure OpenAIPython

Goal: show that a role changes tone and audience, while only the context supplies facts.

  1. Run 
    """Drill 03.3: a role changes style; only context adds knowledge."""
from llm import get_client, MODEL

client = get_client()

QUESTION = "What is the Retake Pass and should I buy it?"
FACTS = ("<policy>Retake Pass (fictional TrainCrest add-on): one free exam retake voucher. "
         "Costs 15% of the course price. Must be bought before the course ends. "
         "Refunded in full if the course is cancelled.</policy>")

ROLES = {
    "no role": None,
    "certification expert, no facts": "You are TrainCrest's most senior certification expert.",
    "friendly agent + facts": "You are a friendly TrainCrest support agent writing to a learner taking "
                              f"their first certification. Use simple words, under 80 words. {FACTS}",
    "trainer + facts": "You are training a new TrainCrest support agent on their first day. "
                       f"Be precise and list what the agent must check before selling it. {FACTS}",
}

for label, system in ROLES.items():
    messages = ([{"role": "system", "content": system}] if system else []) + [{"role": "user", "content": QUESTION}]
    r = client.chat.completions.create(model=MODEL, messages=messages)
    print(f"\n===== {label} =====\n{r.choices[0].message.content.strip()}")
    $ python lab03_03_roles.py
  2. Verify

    Mark each answer for tone and facts

    • "Certification expert, no facts" sounds confident and is generic or wrong about the Retake Pass: the costume without the script.
    • The two roles with facts give the same facts (one free retake, 15% of course price, buy before the course ends, refunded if cancelled) in completely different styles.
    • "No role" is fine but generic. The role earned its place only once facts were present.
3

Check

One question.

1. A colleague adds "You are a world-renowned warranty lawyer" to fix wrong policy answers. Will it work?

No. A role changes style, not knowledge. Put the actual policy in the context (and later retrieve it with RAG).

Takeaway

One line of role, many lines of context. The role sets the voice; the context sets the facts.
