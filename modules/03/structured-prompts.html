Structured Prompts

A wall of text makes the model guess where the rules end and the data begins. Headings and tags turn a prompt into a well-organised form, easy for the model to follow and easy for your teammate to edit. You'll rewrite a real messy prompt and let automatic checks score both versions.

1

Learn

From a wall of text to a form.

Definition

A structured prompt organises content into clearly labelled sections, using markdown headings, XML-style tags or other delimiters, so that instructions, context, examples, input data and output requirements are unambiguous to the model and maintainable by humans.

Unstructured

you are a support bot for traincrest and you
should be nice and here is the lab policy labs
are available 30 days after the course ends and
learners can get one free 7 day extension if
they ask and after that it costs $49 for 14 more
days and the learner wrote … reply in under 90
words and dont offer refunds

Structured

## Role
Traincrest Assist, learner support.

## Policy
<policy>
- Labs: 30 days after the course ends.
- One free 7-day extension on request.
- Then 14 more days cost $49.
</policy>

## Rules
- Only the policy above. Never offer refunds.
- Under 90 words, warm.

<learner_message>…</learner_message>

Facts worth remembering

  • Markdown headings and XML-style tags both work well with current models; pick one convention as a team.
  • Tags around data (<policy>, <learner_message>) are also your first defence against prompt injection (topic 10).
  • For long documents, put the document first and the task last; models tend to follow the most recent instruction best.
  • You can refer to sections by name: "Using only the facts in <policy>…".
In the real world

Provider prompting guides recommend this kind of structure, and production system prompts look like small specifications with headed sections and tagged context blocks. Structure also makes prompts diffable: a reviewer can see that only the Rules section changed in a pull request.

Interview cue

"I structure prompts into labelled sections (role, policy, rules, examples, input, output format) and wrap untrusted data in delimiters so it's never confused with instructions."

Before you run this code

Run every drill from your genai-labs folder with its virtual environment active. Two files must be there: .env (settings) and llm.py (the shared helper every drill imports). By default they use a free local model with Ollama: install Ollama, then ollama pull llama3.2; no key is needed. To use Azure OpenAI or OpenAI instead, change LLM_PROVIDER in .env.

Easiest: download the genai-labs starter kit (every helper, data file and drill script), unzip it, copy .env.example to .env, and run pip install -r requirements.txt. Full walkthrough: Helpers and smoke test.

llm.py
"""Shared helper for every drill: returns an OpenAI-compatible client for
Azure OpenAI (Microsoft Foundry), OpenAI or Ollama, chosen in .env."""
import os

from dotenv import load_dotenv
from openai import OpenAI

load_dotenv()  # reads .env from the current folder

PROVIDER = os.getenv("LLM_PROVIDER", "ollama").lower()   # default: a free local model (Ollama)


def get_client() -> OpenAI:
    if PROVIDER == "azure":
        # Azure OpenAI v1 API: the standard OpenAI client, pointed at your resource
        return OpenAI(
            base_url=os.environ["AZURE_OPENAI_BASE_URL"],
            api_key=os.environ["AZURE_OPENAI_API_KEY"],
        )
    if PROVIDER == "openai":
        return OpenAI()  # reads OPENAI_API_KEY
    if PROVIDER == "ollama":
        return OpenAI(base_url="http://localhost:11434/v1", api_key="ollama")
    raise ValueError(f"Unknown LLM_PROVIDER: {PROVIDER!r}")


# On Azure this is the DEPLOYMENT name; elsewhere it's the model name.
MODEL = {
    "azure": os.getenv("AZURE_OPENAI_DEPLOYMENT", "chat"),
    "openai": os.getenv("OPENAI_MODEL", "gpt-5.4-mini"),
    "ollama": os.getenv("OLLAMA_MODEL", "llama3.2"),
}.get(PROVIDER, "")
Drill 03.10

Restructure a messy prompt and score both versions

~20 minAzure OpenAIPython

Goal: turn a real "wall of text" prompt into a structured one, and prove it's better with automatic checks, not opinion.

  1. Run

    Save the messy prompt

    Save as messy_prompt.txt. It uses $message as the placeholder, and $$ for a literal dollar sign (Python's string.Template syntax).

    you are a support bot for traincrest and you should be nice and here is the lab policy labs are available 30 days after the course ends and learners can get one free 7 day extension if they ask and after that it costs $$49 for 14 more days and the learner wrote $message reply in under 90 words and dont offer refunds and if its not about labs say youll pass it to the team
  2. Your prompt

    Write the structured version yourself

    Create structured_prompt.txt. This time you are the prompt engineer; no assistant needed. Use this skeleton:

    ## Role
…

## Task
…

## Policy
<policy>
…
</policy>

## Rules
- …

<learner_message>
$message
</learner_message>

    Hint: keep every fact from the messy version, add what it left implicit (what to do with non-lab questions, no refunds), and remember $$49 for a literal "$49".

    Compare with my structured prompt
    ## Role
You are Traincrest Assist, the learner-support assistant of TrainCrest, a technical training company.

## Task
Reply to the learner message in <learner_message> about access to hands-on labs.

## Policy
<policy>
- Labs stay available for 30 days after the course ends.
- One free 7-day extension is available on request.
- After that, 14 more days cost $$49.
</policy>

## Rules
- Use only the policy above. Never offer or promise refunds.
- If the message is not about labs, say you'll pass it to the support team, and nothing else.
- Warm and practical. Under 90 words.

<learner_message>
$message
</learner_message>
  3. Run

    Score both on the same three messages

    """Drill 03.10: run the messy prompt and your structured rewrite on the same messages, with simple checks."""
import sys
from pathlib import Path
from string import Template

from llm import get_client, MODEL

client = get_client()

MESSAGES = [
    "My lab expired yesterday and I still have the final project to do. Help!",
    "I already used my free extension, can I get more lab time? Or a refund for the lab days I missed?",
    "Where is my exam voucher?",
]


def checks(reply, message):
    """Cheap automatic checks. They don't prove quality, but they catch the obvious failures."""
    words = len(reply.split())
    results = [("under 90 words", words < 90), ("no refund promised", "refund" not in reply.lower()
                                                or "no refund" in reply.lower() or "not offer" in reply.lower())]
    if "voucher" in message.lower():
        results.append(("hands off non-lab topics", "team" in reply.lower()))
    if "free extension" in message.lower():
        results.append(("mentions the $49 option", "49" in reply))
    return words, results


files = sys.argv[1:] or ["messy_prompt.txt", "structured_prompt.txt"]
for name in files:
    template = Template(Path(name).read_text(encoding="utf-8"))
    print(f"\n==================== {name} ====================")
    passed = total = 0
    for message in MESSAGES:
        r = client.chat.completions.create(
            model=MODEL, messages=[{"role": "user", "content": template.substitute(message=message)}])
        reply = r.choices[0].message.content.strip()
        words, results = checks(reply, message)
        passed += sum(ok for _, ok in results)
        total += len(results)
        print(f"\n> {message}\n{reply}\n  [{words} words] " +
              "  ".join(f"{'PASS' if ok else 'FAIL'}: {label}" for label, ok in results))
    print(f"\n{name}: {passed}/{total} checks passed")
    $ python lab03_10_structured.py
  4. Verify
    • The structured prompt passes at least as many checks as the messy one, usually more (often on "hands off non-lab topics" and "mentions the $49 option").
    • Read the replies too. Automatic checks catch obvious failures; your judgement catches tone.
    • Run twice. If a check flips between runs, the prompt still leaves room to guess: tighten that rule.

Check

Structure.

1. Name two benefits of tags around data, beyond readability.

The model can be told text inside the tags is data, not instructions (an injection defence), and you can refer to sections by name in your rules.

Takeaway

Structure your prompts like a form: labelled sections, tagged data, rules you can point to.
